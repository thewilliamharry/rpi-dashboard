<interfaces>
Existing contracts to preserve:
- `migrations._write_recovery_marker(...)` writes `failed_target_version`, `reason_class`, `backup_catalog_id`, and `timestamp`; `backup_catalog_id` may be null when no verified pre-migration snapshot exists.
- `restore_backup(data_dir, catalog_id, ...) -> RestoreResult` accepts an opaque catalog ID, never a filesystem path.
- `list_verified_backups(data_dir)` returns only regular, integrity-checked catalog entries.
- Restore takes the upgrade lock before `exclusive_database_maintenance()`, completes a zero-busy WAL checkpoint, removes only the exact WAL/SHM sidecars, uses same-filesystem staging plus atomic replacement, fsyncs every durability boundary, and validates the replacement read-only.
- The supported operator surface remains `docker compose run --rm recovery restore --latest`; no browser recovery action exists.

Authorization contract introduced by this plan:
- A valid marker is a non-symlink regular file with exactly the migration fields plus optional boolean `restore_in_progress`; JSON booleans are not accepted as integer fields.
- `failed_target_version` is a positive integer matching the `-pre-vN` catalog suffix, `reason_class` is a non-empty string, `backup_catalog_id` is one opaque valid catalog name, and `timestamp` is a positive integer not in the future.
- The current database must still be the exact pre-version transition for that catalog target. If it has reached/passed the target version, the marker is stale and restore refuses. Marker age alone is not staleness.
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator/automation → recovery CLI | An accidental or hostile invocation can request destructive replacement of the current database. |
| recovery marker → backup catalog | Filesystem state must authorize exactly one verified automatic backup, never an arbitrary path or fallback snapshot. |
| marker/catalog → current database state | A leftover marker must not authorize rollback after the failed target is no longer pending. |

## STRIDE Threat Register — OWASP ASVS L1

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-66 | Tampering / Elevation of Privilege | `restore_backup()` and recovery CLI | high | mitigate | Require a valid pre-existing failure authorization before any catalog, lock, sidecar, staging, or replacement operation; prove healthy bytes remain unchanged. |
| T-01-67 | Tampering | marker-to-catalog selection | high | mitigate | Bind failed target, exact opaque catalog ID, verified record, requested selector, and current pre-version state; forbid fallback for `--latest` and `--id`. |
| T-01-68 | Repudiation / Denial of Service | malformed, stale, or interrupted marker | medium | mitigate | Strict regular-file/type/state validation, redacted refusals, preserved in-progress binding, consumed authorization, and deterministic retry semantics. |
</threat_model>
