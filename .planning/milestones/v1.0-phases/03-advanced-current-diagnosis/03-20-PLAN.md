## Finding: worker_process_scan_requests (J5) does not share CR-01's defect class

Requested explicitly by this round's gap contract ("Check `worker_process_scan_requests` for the same class of error, and state your finding"). Verified against the live source at planning time, not assumed.

`worker_process_scan_requests` computes `status = 'failed' if outcome == 'failed' or state.get('last_error') else 'completed'` and returns `status == 'completed'` (unchanged by this plan). The `state.get('last_error')` clause reads `scan_state`'s `last_error` field, which `_legacy_do_discovery` sets in exactly two places: to `None` on that function's own successful completion (`_update_scan_state(..., last_error=None)` at its final success line), and to `f'{exc.__class__.__name__}: {exc}'[:240]` inside its own top-level `except Exception as exc:` handler -- i.e. only when the discovery PROCESS ITSELF raised (a database write failure, a `TimeoutError` from exceeding `DISCOVERY_TIMEOUT_SECONDS`, or any other unhandled exception during the port-scan, probe, or database phase of that one function). A single candidate service being unreachable during discovery is written to the `services` table's own per-row `last_error` column via `_handle_state_transition`, never to `scan_state['last_error']` -- there is no code path from one downstream service's content into this field.

Every exit path of `_legacy_do_discovery` sets `scan_state['last_error']` fresh on its own completion (success clears it, failure sets it), so it cannot carry a stale value from a prior run once a subsequent discovery has completed, and `_scan_lock` (`_legacy_run_discovery`'s `if not _scan_lock.acquire(blocking=False): return 'busy'`) ensures only one discovery runs at a time process-wide, so no concurrent write can leave it stale either. `state.get('last_error')` is therefore always the discovery JOB's own execution failing, never a signal about one downstream service's content -- the opposite of CR-01's `warning`, which specifically encodes a single previewed service's reachability or page content, independent of whether the poller's own claim/capture/transaction succeeded.

**Conclusion: J5 is correct as shipped by 03-18 and is deliberately NOT touched by this plan.** The asymmetry 03-19-REVIEW.md's own CR-01 text already names ("J5's `status='failed'` comes from `outcome == 'failed'`, i.e. `do_discovery` itself raised -- a genuine worker fault. J6's comes from the content of a third-party service.") is confirmed against the live code, not merely asserted.
