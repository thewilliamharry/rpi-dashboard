# Phase 03.1 Plan 12: Migration Contention Backoff and Pending-Work Fast Path Summary

**A pending-work fast path skips the exclusive maintenance lock on every ordinary reboot, and a bounded contention retry with a distinct `MigrationContended` condition replaces the terminal thirty-second timeout that turned a transient startup race into a five-minute misdiagnosis on the Pi.**

## Performance

- **Duration:** ~35 min
- **Tasks:** 2
- **Files modified:** 2 (`dashboard/beacon/migrations.py`, `tests/test_migrations.py`)

## Accomplishments

- `run_migrations` now checks the recorded schema version under the already-held upgrade lock, before ever requesting the exclusive maintenance lock; a database with nothing pending returns immediately without escalating.
- The `exclusive_database_maintenance` acquisition is now retried within a bounded, derived budget (`CONTENTION_BUDGET_SECONDS = 240`) with exponential backoff (0.1s → 2s cap) and a `WARNING`-level log per wait, instead of dying on the first refusal.
- A new `MigrationContended` exception (sibling to, not derived from, `MigrationPreparationError`) surfaces an exhausted contention budget without writing a recovery marker or backup.
- The retry's busy handler is scoped, via `contextlib.ExitStack`, to wrap only the maintenance-context *entry* — the extracted `_apply_pending_migrations` work function is invoked outside the `try`, so a real migration error (e.g. `UnsupportedSchemaError`) structurally cannot be caught and reported as contention.
- `_is_empty_database` and `_recorded_version` are hardened with an explicit busy timeout (`READ_BUSY_TIMEOUT_SECONDS = 30`, pinned to `connect_db`'s own 30s convention) and a `finally`-scoped close, since both now run on a hot path outside exclusive maintenance where an ordinary writer can be live.
- Six regressions reproduce both halves of the Pi's failure plus the two failure modes the fast path newly exposes (racing a live writer, leaking a connection handle).

## Decisions Made

- `MigrationContended(RuntimeError)` is a sibling of `MigrationPreparationError`, not a subclass — its docstring states explicitly that contention is not a migration failure (no backup, no marker, bytes untouched).
- The contention budget and read busy-timeout constants derive their values entirely from facts owned by other modules (`connect_db`'s 30s flock wait + 30s SQLite busy timeout, and the compose healthcheck's 10s interval), documented in-comment, never from anything defined in `migrations.py` itself.
- Both hardened read helpers reference `READ_BUSY_TIMEOUT_SECONDS` as a bare module-global inside the function body (as an inline `timeout=` argument at call time), never as a parameter default — this is what makes the constant observable to patching in regression 3b's two-direction assertion.
- The busy handler around `exclusive_database_maintenance`'s acquisition is scoped via `ExitStack`: `stack.enter_context(...)` sits inside the `try/except MaintenanceBusy`, and `return _apply_pending_migrations(...)` is called only after that `try` block completes successfully — structurally, not just by exception-type discipline, ensuring the work function's own errors can never be caught by the busy handler.

## Issues Encountered

- **Thread-affinity bug in the first draft of regressions 1 and 2:** SQLite connections (and the `ManagedConnection`-held flock lease) are thread-affine — opening the shared-lease connection in the test's main thread and closing it from a background release thread raised `sqlite3.ProgrammingError: SQLite objects created in a thread can only be used in that same thread`. Fixed by moving both the `connect_db(...)` open and the `.close()` call into the same background thread function (an `Event` signals readiness to the main thread before it calls `run_migrations`). Confirmed no thread-exception warnings on rerun with `-W error::pytest.PytestUnhandledThreadExceptionWarning`.
