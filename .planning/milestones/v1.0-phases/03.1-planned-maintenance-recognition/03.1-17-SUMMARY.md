# Phase 03.1 Plan 17: Midnight-straddling maintenance suggestions Summary

**`detect_suggestion` and `suggestion_overlaps_enabled_window` now compare minute-of-day as a position on a dial that closes at 1440, with a circular anchor-relative median for the reported start time and duration left strictly linear, closing G-03.1-70 (03.1-REVIEW.md WR-04).**

## Performance

- **Duration:** ~45 min
- **Tasks:** 2/2 completed
- **Files modified:** 2

## Accomplishments
- Added `_circular_minute_distance(a, b)` in `dashboard/beacon/maintenance.py`: a single private helper returning `min(raw, 1440 - raw)`, documented as clock-position-only, deliberately never applied to duration.
- `detect_suggestion`'s clustering anchor loop now measures start-minute distance circularly; the winning cluster's anchor is retained and the reported `start_minute` is a circular median computed relative to that anchor (signed offset in `[-720, 720)`, ordinary median of offsets, add back to anchor, reduce onto the dial with `%` before `int()`).
- `suggestion_overlaps_enabled_window`'s start comparison now uses the same helper, so a midnight-straddling suggestion is withheld by a comparable enabled window and still offered when that window is disabled.
- **Both non-vacuity perturbations mandated by the plan were run and observed, not merely claimed:**
  - **(a) distance-only revert** (circular median left in place): `test_a_nightly_pattern_straddling_midnight_clusters_and_names_a_time_near_midnight` failed with `AssertionError: unexpectedly None` -- the cluster does not form at all without the circular distance.
  - **(b) median-only revert** (distance fixed, median reverted to naive `median()`): the SAME test failed on its start-minute assertion with **`AssertionError: 720 != 1439`** -- the naive median reported **720 (midday)** for the midnight-straddling cluster `[1435, 0, 5, 1438]`, exactly the "confidently wrong instead of merely silent" failure mode the plan exists to prevent. This is the perturbation that separates this fix from one that only relocates the defect.
  - **(withholding) revert**: reverting only `suggestion_overlaps_enabled_window`'s comparison to a linear `abs()` failed both `test_a_midnight_straddling_cluster_is_withheld_by_an_enabled_window_across_the_boundary` (`AssertionError: False is not true`) and the end-to-end `test_the_detector_and_withholding_rule_agree_across_the_midnight_boundary` (the suggestion was returned instead of withheld).
- **Anchor-independence verified by hand** (re-derived, not trusted) for `[1435, 0, 5, 1438]`: every one of the four possible anchors (1435, 0, 5, 1438) produces the identical circular median 1439.
- Nine new regressions added: four in `DetectorTests`, four in `SuggestionOverlapTests`, one end-to-end case in `SuggestionLifecycleTests`.
- Full suite: 557 passed / 468 subtests passed, up from the 548/468 baseline this plan started from (+9, all new tests are not subTest-based so the subtest count is unchanged as expected).

## Decisions Made
- **New module constant, not a refactor of the existing `1440` literal.** `Window.__post_init__`'s `0 <= self.start_minute < 1440` bound check already establishes the day length as `1440`; rather than replacing that literal with a reference to the new `_MINUTES_PER_DAY` constant (which would widen the diff beyond what the plan's acceptance criteria scope to), the new constant is introduced adjacent to the new helper with a comment tying it to that existing validated range. `git diff` confirms `Window.__post_init__` is untouched.
- **Single commit per TDD task**, matching 03.1-16's documented precedent: each task's tests and the minimal production change are verified together (including the mandated non-vacuity perturbations) before one commit, rather than separate RED/GREEN commits, given the substantial verification work (anchor-independence, two/three separate perturbations) that sits between "tests exist" and "task done."
- **Two-day spacing in the end-to-end lifecycle test.** The first draft of the end-to-end withholding case spaced the four midnight-straddling occurrences one calendar day apart (mirroring the pure-unit `DetectorTests` case), which produced `occurrence_count == 3` instead of 4 -- because a 30-minute-duration outage starting at 23:55 recovers at 00:25 the next day, which is *after* the next occurrence's 00:00 down transition on that same next day. The repository's sequential down/recovery pairing (`get_maintenance_suggestion_evidence`) misattributed the recovery to the wrong down event. Spacing occurrences two days apart eliminates this overlap while preserving the exact clock-time values `[1435, 0, 5, 1438]` the fix is being tested against.
