# Phase 03.1: Planned Maintenance Recognition - Context

**Gathered:** 2026-08-21
**Status:** Ready for planning

<domain>
## Phase Boundary

Beacon learns which recurring service restarts are expected and lets the operator confirm or define them per service, so routine transition noise is suppressed without hiding downtime, reducing availability, or overlooking an overrun. The phase delivers: operator-managed recurring local-time maintenance windows with an explicit grace period; a detector that proposes an inactive candidate window after three similar daily restart outages; suppression of expected down/recovered event entries and transition alerts only; and a truthful single outage event plus alert when a service is still down past its window and grace.

Every probe remains stored. Planned downtime still lowers availability. Historical charting and range investigation (Phase 4), the broader visual redesign and theme parity (Phase 5), and any remote control action remain outside this phase.

</domain>

<decisions>
## Implementation Decisions

### Window Definition and Edit Surface

- **D-01:** Maintenance windows are created, edited, disabled, and removed through the main dashboard's existing service metadata editor, extending the `PUT /api/service-meta/<int:port>` route (`dashboard/app.py:2510`). The `/advanced` workspace stays strictly GET-only with no mutation endpoint, exactly as PROJECT.md's Key Decision records and `03-SECURITY.md` verified across 46 blocking threats. No new mutation boundary is introduced. — **Reversibility:** costly — moving the write later means re-threat-modelling a second mutation surface and revisiting the read-only decision PROJECT.md publishes as validated.

- **D-02:** Local-time windows are evaluated as wall-clock literals. On a spring-forward date a window whose start time does not exist is skipped; on a fall-back date a window whose start time occurs twice is honored both times. This matches the behavior of the cron entry or systemd timer on the Pi that typically causes the restart, so the window keeps lining up with the real event instead of drifting an hour for half the year. — **Reversibility:** costly — the evaluation rule is baked into window matching, the suggestion detector's day boundaries, and every window-coverage test.

- **D-03:** A window is a start time, a duration, and a set of active weekdays. A start time plus a duration crosses midnight naturally (23:50 + 30m), so no separate midnight rule is needed. No cron-style expression field. — **Reversibility:** one-way — the shape becomes the stored schema (migration 9) and the editor contract; widening it later needs a migration.

- **D-04:** Every window carries its own explicit overrun grace period. The field is required and always visible in the editor, prefilled with a sensible default the operator can change. Grace is not a global setting and is never derived from window duration — the effective overrun boundary must be readable off the window itself. — **Reversibility:** costly — a per-window column is easy to add to but hard to collapse into a global once operators have set per-service values.

- **D-05:** A service may have several windows, each with its own time, weekday set, and grace, so a nightly restart and a longer weekly patch window coexist without one being widened to cover the other. "Is this service in maintenance now?" resolves to "does any enabled window cover now?". Where windows overlap, the longest grace applies. — **Reversibility:** one-way — a list-per-service schema cannot be reduced to one row per port without discarding operator data.

### Active Maintenance and Overrun Presentation

- **D-06:** A service that is offline while covered by an active confirmed window displays a distinct, visually calm `In maintenance` state on both the dashboard card and the advanced services table — not the treatment a real failure receives. The stored fact stays `offline`; the displayed state is derived from (offline AND covered by an active enabled window) and discloses that derivation on inspection. The service is never removed from the failure surface entirely.

- **D-07:** Active confirmed maintenance is kept out of the advanced workspace's global active-exceptions list (`compose_active_exceptions`, `dashboard/beacon/diagnosis.py:451`) and is presented in the Services section detail instead. This follows Phase 3's D-12 precedent — promote to the global exception summary only while actionable, keep non-actionable evidence in the owning section. Expected maintenance is by definition not actionable. — **Reversibility:** reversible — a projection-level ordering change.

- **D-08:** The single overrun outage event required by MNT-04 carries the true down-since timestamp as its outage start (available from `services.state_since`) plus an explicit separate record of when it was raised at grace expiry. Both are durable and neither is inferred, so Phase 4 can present the full outage or only the fault period without reconstruction. — **Reversibility:** one-way — the event record shape is consumed by Phase 4 history and cannot be back-filled for outages already written.

- **D-09:** Availability continues to count planned downtime in full and the headline figure is never adjusted. Expanded detail attributes the portion of the loss caused by confirmed maintenance. No second "excluding maintenance" figure is presented at equal weight anywhere. — **Reversibility:** reversible — presentation-layer attribution over an unchanged computation.

### Suppression Mechanism

- **D-10:** Expected down/recovered event entries are **written and tagged, then filtered at read** — never withheld from the database. Phase 2 D-03 (individual events retained in full for 90 days, never aggregated away) and D-05 (every unavailable interval carries one explicit reason) make never-writing a regression against decisions already locked. The main dashboard events feed hides tagged entries by default behind a visible reveal control, and that control states how many entries are hidden so a suppressed night can never read as an uneventful one. — **Reversibility:** one-way — the tag is written into durable event rows; changing to suppress-at-write loses evidence that cannot be recovered.

### Suggestion Lifecycle

- **D-11:** A suggested window surfaces only inside that service's metadata editor, alongside the fields it would populate. It is not shown on the service card and not listed in `/advanced`. It remains inactive and changes no event or alert behavior until the operator confirms or edits it.

  *Noted consequence:* the editor is opened infrequently, so a suggestion may sit unseen for a long time. D-12 is what keeps that from producing a stale proposal. If discoverability proves to be a problem in use, adding a passive card indicator is a later, additive change — it does not invalidate this decision.

- **D-12:** An unconfirmed suggestion persists indefinitely rather than expiring, and is recomputed against the service's recent outage evidence rather than frozen at first detection. Whenever the operator opens the editor they see a proposal matching what the service has actually been doing lately. If the pattern stops recurring, the suggestion stops being offered.

### Claude's Discretion

Research and planning own the following, subject to the decisions above:

- The schema for maintenance windows and suggestions, and the migration 9 implementation, using the verified-backup and rollback path Phase 1 established (`dashboard/beacon/migrations.py`, `MIGRATIONS` currently ends at version 8).
- The detector's similarity thresholds — start-time tolerance and duration-match tolerance for "three similar daily restart outages" — grounded in the configured probe cadence the same way Phase 2 grounded `collection_gap` in stream cadence. Note the observed cadence asymmetry in `dashboard/beacon/diagnosis.py:201` (60s when offline, 300s when online).
- The default prefill value for the grace-period field (D-04).
- How the window evaluator obtains its clock and runs inside the worker's existing job authority and write-transaction machinery, without giving the web process any background ownership (Phase 1 constraint).
- Where in the suppression path the tag is applied — at `handle_state_transition` versus at alert dispatch — and how it interacts with the existing `alert_cooldown_seconds` (300s) and `alert_only_critical` filters.
- Behavior when the operator edits or disables a window while it is actively covering a live outage.
- Whether a suppressed transition still counts as evidence toward the suggestion detector.
- Module boundaries, editor markup and styling within the existing calm-light/dense-dark direction, and the test surface.

</decisions>

### Established Patterns

- Web and worker are separate processes sharing SQLite; all scheduled evaluation belongs to the worker under its existing authority and write-transaction machinery. The web process must not gain background ownership.
- Cross-process coordination is persisted in SQLite (`runtime_state`, queue tables), never in module-level locks or globals.
- The browser is dependency-free vanilla JavaScript polling same-origin `/api/*` endpoints; the editor additions follow that with no new client dependency.
- Displayed state is derived from the durable row it describes and discloses its derivation — the labelling discipline Phase 3 spent nine verification rounds establishing. D-06's `In maintenance` and D-10's suppression tag are both subject to it.
- Operator-facing vocabularies fail closed and loud on an unrecognised literal (Phase 3 gap-closure round 6, WR-01).

### Integration Points

- Migration 9 adds maintenance-window and suggestion storage keyed by port, alongside `service_meta`.
- `PUT /api/service-meta/<int:port>` accepts and validates window definitions; `GET` returns them plus any current suggestion for the editor to render.
- Suppression tagging applies inside the state-transition funnel, ahead of or alongside the existing alert-due gating.
- The overrun evaluator runs as worker-owned scheduled work and writes the MNT-04 outage event through the existing worker write-transaction path.
- `compose_active_exceptions` gains maintenance awareness; the Services section detail gains the maintenance evidence D-07 relocates there.
- `dashboard/app.js` events rendering gains the default-hidden filter and reveal control with hidden count (D-10); `dashboard/index.html` and `dashboard/style.css` gain the editor fields and the calm `In maintenance` treatment in both themes.

<specifics>
## Specific Ideas

- The window should match whatever cron entry or systemd timer on the Pi actually causes the restart — that is the reasoning behind wall-clock-literal DST handling (D-02), and it is the test to apply when a window's behavior is in doubt.
- A nightly restart and a longer weekly patch window are separate facts about the same service and should be stored as separate windows rather than merged into one over-wide window (D-05).
- A suppressed night must never read as an uneventful one — the reveal control states the hidden count for exactly this reason (D-10).
- One availability number, always true. Attribution explains a dip; it never softens it (D-09).

</specifics>
