### Recorded divergence — `compose_active_exceptions` stays structurally untouched

This table originally classified `dashboard/beacon/diagnosis.py — compose_active_exceptions
(maintenance-aware)`, i.e. teaching the exception composer about maintenance. **Plan `03.1-07`
Task 2 deliberately does not do that, and its approach supersedes the classification above.**

Plan 03.1-07 resolves maintenance *upstream*, at the point where the advanced snapshot's
availability field is derived, and leaves `compose_active_exceptions` a pure projection over what
it is handed. That honours the D-07 precedent of keeping the projection pure — the same reason
`gap_exception_kind` fails closed on an unrecognised literal instead of growing a branch per
caller. It also means the maintenance-availability constant never has to be imported into
`diagnosis.py` at all, which is exactly what that plan's acceptance gate asserts:
`awk '/^def compose_active_exceptions/,/^def _settings_payload/' dashboard/beacon/diagnosis.py | grep -c MAINTENANCE_AVAILABILITY`
returns 0. (That gate's end pattern differs from its start pattern, so it does not self-terminate —
verified: the range emits the real 64-line body.)

Treat plan 03.1-07's approach as authoritative. Do not "fix" it back toward this table by adding a
maintenance branch inside `compose_active_exceptions`; that would reintroduce the coupling D-07
rules out and would fail the gate above.
