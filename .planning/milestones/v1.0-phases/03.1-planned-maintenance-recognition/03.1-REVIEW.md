### Disposition of prior findings

**WR-03 (`default_grace_minutes` never reached the client) — RESOLVED.**
`dashboard/beacon/web.py:40-81` (`metadata_response`) now takes a required
`default_grace_minutes` keyword and publishes `row['default_grace_minutes'] =
int(default_grace_minutes)` (`web.py:67`) unconditionally on every response —
verified it is the only call site (`dashboard/app.py:2306-2319`,
`_service_meta_row`) and that both `GET` and `PUT`
`/api/service-meta/<port>` route through it (`app.py:2728-2829`), so the
value is published on both verbs as the round's summary claims.
`dashboard/app.js` replaced the `MAINTENANCE_DEFAULT_GRACE_MINUTES` constant
with a mutable `currentDefaultGraceMinutes` binding (`app.js:417`), consumed
at all three prefill sites — the Add-row default (`app.js:503`), the

(`app.js:591-593`), never reset by a later failure. Regression-tested by
`tests/test_maintenance_windows.py::DefaultGraceMetadataTests` (server side,

All pass.

**WR-04 (linear median misreports midnight-straddling clusters) —
RESOLVED.** `_circular_minute_distance` (`maintenance.py:200-211`) is now
used for the clustering distance test in `detect_suggestion`
(`maintenance.py:295`) and the start comparison in
`suggestion_overlaps_enabled_window` (`maintenance.py:352`); duration
comparisons in both functions remain plain `abs()` magnitude comparisons
(`maintenance.py:296`, `maintenance.py:354`) — never passed through the
circular helper, matching the docstring's explicit warning against doing so.
The reported start minute is now an anchor-relative circular median
(`maintenance.py:306-312`): signed per-member offsets to the anchor are
computed on the closed dial, median-averaged, added back to the anchor, and
reduced onto the dial (`% _MINUTES_PER_DAY`) **before** `int()` truncates —
correct, since Python's `%` with a positive divisor always yields a
non-negative result, so truncation after reduction is equivalent to a floor
on an already-non-negative value (reducing after `int()` would have been
wrong for a negative sum, as the round's brief flagged). I independently
re-computed this by hand for the shipped test fixture
(`start_minute` values `[1435, 0, 5, 1438]`): every one of the four possible
anchors converges on the same result, 1439, confirming anchor-independence.
The non-wrapping control case (`[235, 240, 245, 238]`) reproduces the plain
linear median (239) exactly, confirming the fix is a no-op off the wrap.
Regression-tested by four new `DetectorTests` cases, four new
`SuggestionOverlapTests` cases, and one end-to-end
`SuggestionLifecycleTests` case exercising both fixes together through the
live API. All pass.

**WR-05 (fixed 64-step anchor bound silently truncated attribution past ~129

ceiling only (`maintenance.py:386`, raised 64 → 4096); the working budget is

When the derived budget does exceed the ceiling, `_covering_boundaries` logs

## Warnings

### WR-06: The boundary-discovery ceiling warning is unthrottled inside a per-service, per-request loop

**File:** `dashboard/beacon/maintenance.py:433-442`
**Issue:**

`_covering_boundaries` is called once per enabled window per offline
interval, from inside `attributed_downtime_seconds`, which is itself called
once per service from `get_current_diagnosis`
(`dashboard/beacon/diagnosis.py:636-643`) — the handler behind
`/api/advanced/current`, a route that is re-evaluated fresh on every
request, per the round's own framing of it as "a live deployment." The
interval width fed into `_anchor_step_budget` there is
`settings.expire_days * 86400` (`diagnosis.py:628-629`), and
`EXPIRE_DAYS` is deliberately never clamped to fit the 4096-step / ~22.4-year
ceiling (the accompanying comment at `maintenance.py:380-385` states this is
intentional, to avoid a second silent truncation one layer down). With the
documented default (`EXPIRE_DAYS=7`) the ceiling is never approached, so this
is not reachable in a normally configured deployment. But it is reachable by
an operator typo (an extra digit on `EXPIRE_DAYS`, e.g. `70000`) without any
other validation catching it first, and once reachable, the warning fires
**every time** the advanced-diagnosis endpoint is loaded, once per enabled
window per service with an offline interval in scope, with no
de-duplication or rate-limiting. On a deployment with a dozen monitored
services and an admin dashboard that auto-refreshes this endpoint, that is
a sustained per-poll log flood rather than a one-time diagnostic, undermining
the "non-silent, not decorative" intent the comment states for this warning.

**Fix:** Rate-limit or de-duplicate the warning — for example, log it at most
once per process (or once per `(port, interval_start, interval_end)` tuple
per some cooldown window) rather than unconditionally on every call:

```python
_last_ceiling_warning_ts = 0  # module-level, or thread through a small cache

def _covering_boundaries(window, interval_start, interval_end, tz):
    ...
    if required_steps > _ATTRIBUTION_MAX_ANCHOR_STEPS:
        global _last_ceiling_warning_ts
        now = time.monotonic()
        if now - _last_ceiling_warning_ts > 300:  # at most once per 5 minutes
            _last_ceiling_warning_ts = now
            requested_days = (interval_end - interval_start) / 86400
            covered_days = MAINTENANCE_OCCURRENCE_LOOKBACK_DAYS * _ATTRIBUTION_MAX_ANCHOR_STEPS + 1
            log.warning(...)
```

Alternatively, move the check up to `attributed_downtime_seconds` (or its
caller) and log once per top-level call rather than once per
window-per-interval, since the underlying condition (an oversized
`EXPIRE_DAYS`) is the same for every window/interval pair in a given
request.

## Info

### IN-01: Docstring says "rounding to a whole minute"; the implementation truncates

**File:** `dashboard/beacon/maintenance.py:276-280`, `dashboard/beacon/maintenance.py:312`
**Issue:** The `detect_suggestion` docstring states the circular median
result is "reduced onto the dial and rounded to a whole minute"
(`maintenance.py:280`), but `circular_start_minute = int((anchor_start_minute
+ median(offsets)) % _MINUTES_PER_DAY)` (`maintenance.py:312`) truncates
toward zero, not round-to-nearest — a cluster whose true circular median is
`x.5` minutes always reports `x`, never `x+1`. This is not a regression (the
pre-existing linear-median code this replaces did the same truncation via
`int(median(...))`), so it is not a behavior change worth blocking on, but
the word "rounded" in the docstring could lead a future reader to expect
round-half-up semantics that the code does not provide.

**Fix:** Either change the docstring wording to "truncated to a whole
minute" / "floored", or switch to `round()` if round-to-nearest is actually
the intended behavior (would require updating the two clustering tests that
assert exact truncated values).
