`parseLocalRangeInput(text)` interprets the entered wall-clock text **in the Pi's configured
timezone** (`state.timezone`), not the browser's, so the fields agree with the axis, the tooltips
and the incident rows. Build the epoch value by formatting a candidate instant back through

`validateCustomRange(startTs, endTs)` applies exactly the bounds the server applies, so the UI
and the server never disagree about what is legal:
- Either field blank, whitespace-only, or unparseable → the message
  `Enter both a start and an end time.` and **no request is issued**. A blank field never falls
  back to a default range or to the current preset — silently substituting a range the operator
  did not ask for is the failure this branch exists to prevent.
- `startTs` equal to `endTs`, or `startTs` after `endTs` → surface the server's own
  `start_ts must be before end_ts` message. Reversed input is rejected, never silently swapped:
  the operator stated an intention and it was wrong, so say so.
- A span longer than 90 days → surface the server's own `requested span exceeds 90 days` message.
- `endTs` in the future → surface the server's own `end_ts must not be in the future` message.
Read every one of these strings from the server behaviour rather than inventing a paraphrase, so
a change on either side shows up as a failing test rather than as two different wordings.

Applying a valid custom range routes through the single `setInvestigationRange({start_ts,
end_ts, origin: 'manual'})` entry point that Task 2 introduces, writes
`state.preferences.historyRange = {custom: {start_ts, end_ts}}`, persists it, and re-renders.

  <action>
Make every narrowing gesture share one memory model.

`setInvestigationRange(next)` is the single entry point every range change flows through. It
takes `{start_ts, end_ts, origin, label}` where `origin` is `manual`, `drag` or `incident`, and
it owns the stack:
- `origin: 'manual'` (a preset button or `Apply custom range`) calls `clearRangeStack()` first —
  a manual range change is a fresh investigation, not a continuation of the drill-down chain.
- `origin: 'drag'` or `'incident'` calls `pushRange({range: <the range being left>, origin,
  label})` before adopting the new range, so `Back` returns to what the operator was scanning.
- A push whose resulting range is exactly equal to the current range — both bounds identical — is
  a no-op: no entry is recorded and `Back` does not appear for it, because there is nothing to
  return to.

`pushRange` / `popRange` / `clearRangeStack` operate on `state.rangeStack`, bounded by
`RANGE_STACK_LIMIT` (drop the oldest entry beyond the limit rather than growing without bound).
`popRange` restores exactly one entry, so N pushes followed by N pops restore the original range
exactly.

`renderBackControl()` adds a `range-back` button to the range-control header **only while the
stack is non-empty** — when the stack is empty the element is absent from the DOM entirely, not
present and disabled, so there is no reachable pop. Its label is exactly
`Back to {previous range label}` where the label describes the range being returned to (a preset
id such as `24h`, or the custom range in words). A long label truncates with a full-string
`title` rather than pushing the header layout. On desktop the control sits on its own row above
the presets so a pushed focus is never confused with the operator's own preset choice.

`INCIDENT_PAD_FRACTION = 0.15` and `INCIDENT_PAD_FLOOR_SECONDS = 300` are declared here — the
padding rule plan 04-07 applies when it pushes an incident window: 15 percent of the episode's own
duration on each side, with a floor of five minutes per side, so a one-minute blip stays legible
and a long outage is not padded into an unreasonably wide window.

The stack is in-memory and browser-local. Nothing about it — and nothing about the range it
carries — is written to the document URL (D-18).

Tests: pushing three ranges and pressing `Back` three times returns to the original range with
the fields showing it at each step; `#range-back` is absent from the DOM with an empty stack and
present after one push; a push of an identical range creates no entry and leaves `#range-back`
absent; choosing a preset after two pushes removes `#range-back` and adopts the preset; the stack
never exceeds `RANGE_STACK_LIMIT` entries after many pushes.

Let the operator narrow the range by dragging across any host chart (and, once plan 04-06 adds
it, the service latency chart), landing on exactly the same range state the fields describe.

`beginDragSelect(event)` records the pointer-down x position against the chart's time scale.
`updateDragSelect(event)` coalesces every `pointermove` through `requestAnimationFrame` and
updates **only** the `history-drag-overlay` rectangle's geometry — chart `<path>` `d` attributes
are never regenerated during a drag, which is the single largest Pi-performance hazard in this
phase (R-01). `commitDragSelect(event)` converts the two x positions to timestamps, orders them
so a right-to-left drag produces the same range as a left-to-right one, and calls
`setInvestigationRange({start_ts, end_ts, origin: 'drag', label})` — the same entry point the
preset buttons use, so the fields update to show what was selected and the previous range is
pushed onto the stack. `cancelDragSelect` clears the overlay on pointer-cancel, on Escape, and on
a drag that ends where it began.

Reject a degenerate drag: if the two timestamps are equal, or the selection is narrower than one
rendered pixel, cancel rather than applying a zero-width range — the server would reject it and
the operator's gesture was almost certainly a click.

The overlay uses a low-opacity accent tint with an accent border (never a solid fill), per the
UI-SPEC accent reservation. It is a single absolutely-positioned element reused across all
charts rather than one per chart.

Record the accessibility debt explicitly in a comment at the drag entry point: this gesture has
no keyboard equivalent in this phase, and the canonical start/end fields remain the fully
keyboard-operable path to any range. R-03 already carries this to Phase 5 (UX-06) as a known
obligation rather than a discovery.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator text input → history request URL | Free-text start/end values become the `start_ts` and `end_ts` parameters of a server read |
| localStorage → advanced.js | A stored custom range and stack state are read back as trusted-looking configuration |
| pointer events → range state | An uncontrolled event stream drives repeated DOM updates on Pi-class hardware |
