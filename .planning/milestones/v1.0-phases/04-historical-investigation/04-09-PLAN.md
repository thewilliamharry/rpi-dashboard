## Anchor candidate universe — option (a), derived from `events`

The plan-checker found the first draft void in exactly the CR-01 case and offered two universes.
**Option (a) is chosen: the universe is the durable `events` record, never the `services` table.**
This is not a test-fixture convenience — a `services` universe is wrong in production:

- `dashboard/app.py:1420` runs `DELETE FROM services WHERE last_seen < ?` with
  `expire_cutoff = now - EXPIRE_DAYS * 86400`, and `EXPIRE_DAYS` defaults to **7**
  (`dashboard/beacon/config.py:230`). The very next statement deletes the matching `service_meta`
  row, so **both** join tables lose the service.
- `events` outlive that by design: `dashboard/beacon/telemetry.py:1061` prunes at the configured
  retention (90 days) and `dashboard/app.py:1266` at 14 days.

So a service that went down and was never probed successfully again loses both join rows after a
week while its down `state_change` survives for months. That service is precisely the long-silent,
still-open outage CR-01 exists to surface — a `services`-derived universe would make the phase's
own worst case *permanently* invisible, and would do so silently. It also explains why the module
already reads through `LEFT JOIN services` (`dashboard/beacon/incidents.py:59-63`): a joined row is
optional by construction, which is exactly why the 37 existing tests pass without one.

Consequences carried through this revision rather than left to execution:
- The cost story is re-derived from scratch in `T-04-09-02` — the universe is no longer bounded by
  configured service count.
- The query-plan gate is replaced by a **behavioural** seek-count bound
  (`test_anchor_seek_is_index_backed_and_open_port_discovery_is_bounded`), which pins the property
  that actually matters instead of a plan string that could pass while the cost grew.
- Task 2 and Task 3 `<behavior>` fixtures are unchanged and remain correct: they seed `events`
  rows only, and `tests/test_incidents_api.py` gains no `services` fixture row.
- The first draft's claim that including `episode_rows` in the union "guarantees this can never
  resolve fewer anchors than the previous behaviour for a service that has no `services` row" was
  false where it mattered and has been removed.

<assumption_delta_decision>
- **Primary noun:** the **incident episode**. Before this plan, an episode's identity was
  implicitly "a grouping of whatever rows this request's filters returned". After it, an episode's
  identity is "a grouping of the durable state_change record for an in-scope service over the
  requested range", with the operator's `event_type`/`maintenance` selections applied *to* episodes
  rather than *underneath* them.
- **Decision: `promote`.** The durable-record grouping becomes the one definition of an episode.
  The filtered-row-set grouping is not kept alongside it — keeping both would leave two competing
  notions of "an incident" in one response, and only one of them can represent a state machine.
- **Invariant test (accepted, implemented in Task 2):**
  `test_episode_scope_discloses_grouping_source_and_applied_narrowing` pins
  `episode_scope.grouped_from` to `EPISODE_GROUPING_SOURCE` on every request shape, so any future
  change that reintroduces grouping from the filtered row set goes red immediately.
- Advisory only; nothing in this plan blocks on it.
</assumption_delta_decision>

**3. Add `anchor_candidate_ports(conn, *, start_ts, port=None, criticality=None, episode_rows)`.**
Returns the sorted set of ports eligible for an anchor lookup, computed independently of what
matched inside the window. When `port` is supplied the result is exactly `[port]` — an explicit
per-service investigation always reaches the anchor seek whether or not the window returned a single
row for it, which is the direct CR-01 fix on the per-service path. Criticality is deliberately not
applied in this function on either path: item 1 applies it to the anchor row, so `port=X` under a
mismatching criticality still reaches the seek and is then correctly dropped, and `episodes` can
never disagree with `events` about which services are in criticality scope. When `port` is not
