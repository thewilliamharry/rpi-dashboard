<objective>
Make the relocated thumbnail store genuinely bounded — a documented TTL, a documented total-byte
budget, and an hourly reap that enforces both.

Purpose: 06-01 moved the blobs off the primary telemetry table but left them immortal. OPS-03 asks
for storage *and expiry* that "remain bounded", so relocation alone does not satisfy it: an
unbounded `thumbnails` table is the same disk-pressure failure one table to the left. This plan
supplies the two bounds and the job that enforces them.

The schema and support-floor half of migration 10 is deliberately **not** here — it landed whole in
06-01, because the migration and the contract that pins the newest migration version cannot be
separated across a wave boundary without leaving the repository red in between.

Output: the `THUMBNAIL_TTL_DAYS` and `THUMBNAIL_STORE_MAX_BYTES` settings (D-02), the three bounded
store functions, and a TTL + byte-budget reap wired into J8's existing hourly transaction.
</objective>

  <action>
Give the thumbnail store its two bounds and enforce them on the hourly cleanup job.

**The D-02 values and why (record this rationale in the code comments, not only here).** No code
precedent fixes these numbers, so they are chosen here and made configurable:
- `THUMBNAIL_TTL_DAYS = 7`. `THUMB_REFRESH_DAYS = 1` means a live, discoverable service has its
  preview re-captured daily, so a 7-day TTL survives six consecutive missed refresh cycles — a week
  of worker downtime or an unreachable service — before evicting. It also equals `expire_days = 7`,
  the horizon after which a service disappears from `/api/services` entirely (`app.py` `EXPIRE_DAYS`),
  so a thumbnail can never outlive its own service's visibility window.
- `THUMBNAIL_STORE_MAX_BYTES = 67_108_864` (64 MiB). Worst case without a budget is
  `THUMB_MAX_BYTES` (2 MiB) times the ~85 ports the discovery sweep can find, roughly 170 MiB on a Pi
  whose whole telemetry store is capped at `telemetry_db_max_bytes = 536_870_912`. 64 MiB matches the
  existing `telemetry_backlog_reserve_bytes` reserve, holds ~32 full-size captures, and keeps the
  preview store an order of magnitude below the telemetry store it shares a disk with.

**`dashboard/beacon/repositories.py`** — add three module functions beside the thumbnail store:
- `thumbnail_store_bytes(conn)` → `SELECT COALESCE(SUM(LENGTH(data)), 0) AS bytes FROM thumbnails`.
- `delete_expired_thumbnails(conn, *, now)` → `DELETE FROM thumbnails WHERE expires_ts IS NOT NULL AND
  expires_ts <= ?`, returning `cursor.rowcount`.
- `evict_thumbnails_over_budget(conn, *, max_bytes, scan_limit=THUMBNAIL_EVICTION_SCAN_LIMIT)` →
  returns 0 immediately when `thumbnail_store_bytes(conn) <= max_bytes`; otherwise walks
  `SELECT port, LENGTH(data) AS bytes FROM thumbnails ORDER BY captured_ts ASC, port ASC LIMIT ?`
  accumulating until the running total would bring the store to or below `max_bytes`, then deletes
  those ports with a single parameterized `DELETE FROM thumbnails WHERE port IN (...)` built from `?`
  placeholders — never string-interpolated values. Clamp `max_bytes` with `max(0, int(max_bytes))`.

  The `LIMIT` is not decorative and is not there because the table is expected to be large. It is the
  `06-PATTERNS.md` § Shared Patterns rule — *bounded/clamped `limit` parameters on read projections*,
  sourced from `read_background_job_health`'s `max(1, min(int(limit), 128))` clamp — applied to the one
  listing projection this phase adds. Introduce module constant
  `THUMBNAIL_EVICTION_SCAN_LIMIT = 512` beside the three functions, with a comment recording the
  reasoning: the store is keyed by `port`, so its natural ceiling is the discovery sweep's port
  universe (roughly 85 ports today, 65535 in the worst conceivable case), and 512 is comfortably above
  the former and safely below the latter. Clamp the parameter the same way the precedent does —
  `max(1, min(int(scan_limit), 4096))` — so a caller cannot widen it without bound.

  Because the walk is bounded, a single pass may not reach the budget when the store is pathologically
  oversized. That is correct and must be explicit, not accidental: the function deletes what its
  bounded walk selected, returns the count, and the next hourly J8 pass continues from the new state.
  Eviction converges across passes rather than in one unbounded scan. Record that in the docstring so
  a future reader does not "fix" it by removing the `LIMIT`.
All three use `?` placeholders and are called by a caller that owns the transaction, matching every
other function in this module. `thumbnail_store_bytes` needs no clamp — it is a single-row aggregate,
not a listing projection.
