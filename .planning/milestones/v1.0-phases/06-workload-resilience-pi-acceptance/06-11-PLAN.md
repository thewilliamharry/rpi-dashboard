<objective>
Make the acceptance harness's CPU column an actual measurement.

Purpose: `06-VERIFICATION.md` root-caused `D-DEBT-06-06` by direct code read. `_live_role_processes`
(`tests/pi_load_acceptance.py:498`) constructs a fresh `psutil.Process(target.root_pid)` on every
sampling tick, and `psutil.Process.cpu_percent(interval=None)` diffs against state stored on that
specific instance — so every call is effectively psutil's meaningless first call and returns `0.0`.
`_prime_cpu_percent` (line 519) primes a different, run-start-only set of objects that
`_sample_resources_tick` never reuses, so the priming is discarded. The consequence is not a low
reading: it is that the CPU half of the phase's own "resource-budget compliance" clause has never
been measured on any run this phase has produced, and `D-DEBT-06-02`'s revisit trigger has now failed
to be evaluable for two consecutive rounds.

This plan is one half of the measurement slice this gap-closure round leads with. It changes nothing
about what the harness asserts — it changes only whether one of the numbers it prints is true.

Prior-phase decision disposition: `06-CONTEXT.md` `D-01` (WAL only, `_db_lock`'s scope untouched) is
honoured here by construction — this plan touches only `tests/`, no line of `dashboard/app.py`, and no
lock call site. `06-CONTEXT.md` `D-02` (preview retry budget and thumbnail TTL values) was implemented
in `06-01`/`06-02`/`06-03` and is untouched by this round.

Output: a harness whose `peak_cpu_percent` / `mean_cpu_percent` reflect real process CPU, a report that
states whether its own CPU column is trustworthy, and regressions that fail against the pre-fix shape.
</objective>
