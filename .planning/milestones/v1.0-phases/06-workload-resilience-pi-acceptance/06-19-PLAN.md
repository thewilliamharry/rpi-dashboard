<plan_review>

`D-DEBT-06-10` and `D-DEBT-06-14` both bind this plan's design. This section states how, and what
would make each choice wrong.

**Three guards this phase has shipped that asserted what they could not detect.** `CR-01` mandated a
mechanism and its guard asserted SQL text plus a `200`, never a value — it shipped a Critical
regression green. `services_median_hold_in_band` encoded an absolute millisecond band tied to a
row count, and broke when the row count grew 2.24x while the relational check over the same data
held. `test_disabled_wrapper_path_costs_nothing_measurable` claims to guard against the lock being
wrapped with the flag off and stays green under exactly that mutation. Each is the same defect: the
assertion is about shape, and the shape survives the defect.

**Clauses in this plan that genuinely mandate a MECHANISM, why, and what makes each wrong:**

1. **Task 1 requires an AST invariant over `dashboard/app.py` source, not a behavioural test.**
   *Why a mechanism:* the outcome — "no route has unserialized database access" — is not observable
   from any single request. It is a property of every path through the module, and the only way to
   assert it over all 28 sites without executing all 28 is to read the source. *What would make it
   wrong:* an access path that does not go through a name bound by `database_access(...) as conn`
   — a helper that opens its own connection, a module-level connection, a `get_db()` call. Task 1's
   acceptance criteria therefore require the invariant to also fail when a `connect_db`/`get_db`
   call appears in a `_db_lock`-owning function outside its with-block, and require the audit table
   to name every site the invariant found so a site the AST cannot see is visible as a count
   mismatch rather than as silence.

2. **Task 3 requires `evaluate_narrowing_outcome` to gate on `clamped_python_count == 0` before
   reading `python_share`.** *Why a mechanism:* `python_ns` is a derived remainder
   (`hold - connect - sql_execute - sql_fetch`). `06-16`'s own mutation proved the summing identity
   survives a thread-local leak that pushed `clamped_python_count` to 706/3255 — so the share can be
   arithmetically consistent and still be garbage. The clamp counter is the mutation-verified signal
   that the remainder is trustworthy. *What would make it wrong:* a defect that corrupts the split
   without ever producing a negative remainder. That is why the verdict on a clamped run is
   INCONCLUSIVE and never CONFIRMED — a suspect measurement must not read as success.

**Every threshold in this plan is relational or a share; none is an absolute millisecond value.**

| New constant | Form | Why it does not repeat `D-DEBT-06-14` |
|---|---|---|
| `services_min_hold_over_scan_status_hold_ratio` | ratio of two holds measured in the same run | Both terms come from one run. As stored rows grow, `/api/services`' hold grows while `/api/scan-status`' does not, so the ratio moves *away* from the floor — the failure direction is safe, which is exactly what the absolute band got wrong when it failed on the high side. |
| `services_max_python_share_of_hold` | a share of the same run's own hold | Dimensionless. A dataset twice the size produces the same share if the fix worked. |
| `services_min_sql_share_of_hold` | a share of the same run's own hold | Same. |
| `max_utilisation_after_narrowing` | held nanoseconds / window nanoseconds | Already dimensionless by construction; unchanged from `06-17`'s form, which is the one that held. |

**Every new test is mutation-verified and its observed failure value is recorded in the SUMMARY.**
The bar this phase set is `{'_uptime_summary'} is not false`, `acquisitions 1 != 2400`, `1.2682x` —
a named mutation with the number it produced, not the assertion that one was performed.

**No timing comparison in this plan uses summed totals.** Task 2's oracle comparison is a value
equality, not a duration. Nothing here compares two elapsed times, so the minima-with-alternating-
order rule has no application in this plan; `06-20` Task 2 is where it binds.
