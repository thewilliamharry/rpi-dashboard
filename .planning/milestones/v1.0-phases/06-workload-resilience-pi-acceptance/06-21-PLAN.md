`06-20` narrowed `api_services`' critical section to database reads only. Its predicted effect is
recorded in `06-19`'s `NARROWING_OUTCOME_PREDICTIONS`, written before the change and before this
measurement, with a REFUTED branch that fires if the Python work did not actually leave the lock.

**Why this measurement is separate.** Landing both halves and measuring once would destroy the
attribution this phase has protected across four rounds. Round 4 built the instrument precisely so a
reading could be taken between two changes. `06-22` changes the second thing; this plan reads the
first.

0.745-0.82 post-fix utilisation (`D-DEBT-06-15`), derived from shares measured under load, and
`06-LOCK-DIAGNOSTIC.md` §4 itself cautions that it assumes a linear translation from Python share to
hold reduction and that all other routes hold constant — neither of which was measured. A measured
result outside that range is a real finding about the estimate, not a run to be re-explained.

`/api/services` holding its SQL time, and `/api/advanced/current` — 0.0ms lock wait across 880
requests — untouched. `overall_passed: false` on this pass is not a failure of the change; it is the
predicted state, and `06-22` is the second half.

<plan_review>

**A hardware plan is where `D-DEBT-06-10` bites hardest, because a documentation task can state a
conclusion without measuring one.** `06-18` had exactly this exposure and handled it by requiring
every numeric claim to name the report field it came from. This plan carries the same requirement,
plus one more that round 4's own artifact needed and did not have in advance.

**Clauses that mandate a MECHANISM, why, and what makes each wrong:**

1. **Both passes must run against one build in one session, with the git SHA recorded from the Pi.**
   *Why:* the outcome — the narrowing's effect isolated from everything else — is unobtainable if the
   two passes hit different code or materially different stored data. *What would make it wrong:* a
   `git pull` between passes, or a dataset that grew materially mid-session. The acceptance criteria
   require the SHA once and the row count at both ends, and require the growth to be stated.

2. **A concurrency-1 control pass is required even though the question is about load.** *Why:*
   `06-LOCK-DIAGNOSTIC.md` §4 measured the held-region split differently at concurrency 1 (`.001 /
   .423 / .576`) and concurrency 8 (`.002 / .748 / .250`) — the SQL share rises under contention. A
   post-narrowing Python share read only under load would be flattered by that same effect and could
   read as success while the control pass still showed Python inside the lock. *What would make it
   wrong:* nothing; it costs two minutes and removes a confound the previous round discovered
   the hard way.

**Every comparison in the artifact is relational or explicitly dataset-scaled:**

- Utilisation, held-nanoseconds over window-nanoseconds, is dimensionless.
- The held-region split is a set of shares of the same run's own hold.
- The round-4 comparison states both runs' `service_checks` counts alongside every absolute
  millisecond figure, and any absolute-figure comparison carries the growth ratio explicitly —
  `D-DEBT-06-14`'s stated failure was an absolute band compared across a 2.24x dataset change.
- The `/api/services` hold check is now `services_hold_dominates_scan_status_hold`, a same-run
  ratio, per `06-19` Task 3.

**Guards assert consequences.** The verdict is computed by `evaluate_narrowing_outcome` from measured
fields, not composed in prose at write-up time; a `clamped_python_count` above zero forces
INCONCLUSIVE rather than being noted and worked around; and the artifact's REFUTED path is specified
in the same detail as its CONFIRMED path, so a refutation cannot be softened while writing.

**No timing comparison uses summed totals as a gate.** The absolute totals recorded from
`requests[*]` are transcribed as evidence, not compared as a pass/fail threshold. The one comparison
that does gate — the narrowing-outcome verdict — is entirely shares and ratios.
