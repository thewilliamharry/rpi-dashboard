<objective>
Measure the shipped remedy on the hardware that gates it — cheaply first, then for the record.

**Which build this measures, restated as of round 7.** Not option C. Option C — `06-25`'s bulk SQL
aggregation, as reshaped by `06-29` — was refuted at the route level twice (236.265ms, then
69.191ms, against a 56.820ms bar) and `06-31` reverted its route wiring. `/api/services` is back on
the Python producer `_uptime_summary`, now fed a **state-change-only reduction** of `checks_by_port`
landed in the same commit. That is the build this plan measures: `06-31`'s `83f9ce5` (the
revert-plus-reduction) and `bcfc73f` (its guards). `06-PROFILE-5.md` measured it on the dev host at
**34.927ms against the 56.820ms bar — a PASS**, the first time any round of this phase has beaten
the pre-`06-25` baseline at the route level.

**Two segments, one Pi session, one build, with a stop between them.**

*Segment A* is the guard this phase has never had. `tests/services_route_profile.py` seeds its own
temporary database and measures `/api/services` in-process; it runs in minutes and needs no
deployment. Run on the Pi at `79e051e` (the pre-`06-25` parent) and at the current build, it answers
the one question that decides whether a ten-minute acceptance run is worth taking: **did per-request
cost actually fall on this hardware?** `06-PROFILE-5.md`'s PASS is a *dev-host* answer and is not
Pi-class evidence (`PROH-OPS-07-09`); it is what makes spending Pi time defensible, not a substitute
for spending it. Round 5 did not ask this question, landed two changes, ran the 600-second pass, and
measured `/api/services` **68.4% worse** — a full round and a revert (`ea8689e`) for a fact a
two-minute measurement would have shown. `PROH-OPS-07-20` makes not asking it a recorded error.

*Segment B* is the gating acceptance run: uninstrumented, `run_kind acceptance`, `--concurrency 3
--duration 600`, every declared route budget unchanged, per criterion 5 as amended by
`D-DEBT-06-20`. It runs only if segment A clears.

**What the run is measured against.** `/api/services` has now missed twice at concurrency 3 on
independent runs — 635.6ms p95 (`06-ACCEPTANCE-C3.md`, confounded) and 679.3ms p95
(`06-ACCEPTANCE-C3-RUN2.md`, clean) against a 500ms budget. Run 2's confound was resolved and was
not the explanation; the route degraded rather than improved. The shortfall to close is **179.3ms**,
and the record must state the third run's figure next to both, together with the `service_checks`
row count, because `D-DEBT-06-14` is the entry in this phase's own debt register created by
comparing an absolute figure across a dataset that had grown 2.24x. Both prior runs predate `06-25`,
so they measure a route whose producer this build has since made 38.53% cheaper on the dev host —
which is the reason this run is worth taking and not a prediction of its result.

**What this plan may not do.** It may not promote OPS-07 (`PROH-OPS-07-08`) — that belongs to an
independent verification round, following the `TEL-06` precedent. It may not touch a budget, a
threshold or a limit in response to what it measures (`PROH-OPS-07-01`, `PROH-OPS-07-10`). And if the
route still misses, it may not scope the next remedy: **the `service_rollups` path is refuted twice,
independently, and `D-DEBT-06-21`'s round-7 addendum upgrades the rejection from "not currently
populated" to "not reconstructible"** — the rollup ladder's fixed hour-aligned grid cannot losslessly
render this strip's sliding-origin boundaries at any retention setting (168/168 buckets straddle an
epoch hour, worst error 0.461). `PROH-OPS-07-29` requires that finding to be read and re-verified
against source before any rollup-backed remedy is proposed a third time. This plan proposes none, and
records the miss instead.

Purpose: produce the hardware evidence OPS-07 will eventually close on, honestly, either way.
Output: a Pi-class cost verdict, an admissible acceptance report, and a runbook that stops the next
round rediscovering the command path.
</objective>
