<objective>
Fix the join shape that made `06-25` four times slower, without moving one byte of the rendered
strip — then measure it against the bar it actually has to clear, and say so out loud before the
number arrives.

**What is broken.** `06-26` measured `/api/services` at **236.265ms** mean `wall_ms_unprofiled`
against a pre-`06-25` baseline of **56.820ms** — **+315.8%**, with run-to-run spreads of 0.230ms and
2.902ms against a 179ms delta. `06-PROFILE-3.md` names the cause in the query text:
`bucket_totals` materializes `requested_ports CROSS JOIN buckets` (`ports x 168` rows) and
`LEFT JOIN ordered_points` on a **range** predicate — `sg.effective_ts < bk.bucket_start + ?
AND sg.end_ts > bk.bucket_start`. `ordered_points` is a CTE, so no index serves that predicate, and
cost scales as `buckets x ports x segments_per_port`. The Python sweep it replaced was linear in
rows.

**The fix.** Invert the join. Compute each segment's overlapping bucket *range* arithmetically —
`first_idx` from `seg_start`, `last_idx` from `seg_end - 1`, both by integer division against
`bucket_seconds` — and expand only those buckets through a recursive CTE. A port's segments
partition `[start, now]` contiguously, so almost every segment lands in exactly one bucket and the
expansion is near-linear in segments. The `ports x 168` scaffold then LEFT JOINs onto the expanded
aggregate on an **equality** predicate, which SQLite can serve.

**This is measured, not reasoned.** Before writing this plan the planner built the reshaped query
against a synthetic database matching this route's real index shape (`idx_checks_port_ts`,
`migrations.py:311`), seeded 8 ports x 8 days = 31,580 rows, and ran both shapes:

| | min over 3 runs | rows returned |
|---|---|---|
| Current shape (range join) | **254.4ms** | 1,344 |
| Reshaped (index arithmetic) | **47.4ms** | 1,344 |

**5.4x, with an EXACT match on every one of the 1,344 `(port, idx, online_seconds,
offline_seconds, null_count)` tuples.** That bench is calibrated: it reproduces the measured route
regression to within a few milliseconds when the removed Python work is added back
(`56.820 - ~25 + ~204 = ~236`, against the measured 236.265ms).

**And the same bench says this fix probably does not clear the bar — which is stated here, before
the measurement, so it cannot be settled afterwards.** On that same synthetic data,
`_legacy_uptime_summary` over all 8 ports — the exact Python work `06-25` removed — costs
**23.1ms**, and the reshaped query costs **47.4ms**. The SQL formulation's floor is already above
the Python sweep it replaced: the `ordered_points` LEAD window alone costs 23.4ms, half the
reshaped query, before a single bucket is computed. Projecting to the route:
`236.265 - ~204 + ~38 ≈ 70ms`, against a pass bar of **56.820ms**.

**Pre-registered projection: ~70ms, band 55-90ms. Projected verdict: FAIL** — a ~3.4x improvement
on `06-25`, and still short of the pre-`06-25` baseline. If the run comes in under 56.820ms this
projection is refuted and that is recorded as such. If it does not, the projection was right and
`06-30`'s checkpoint decides between keeping the reshape and reverting the route wiring. Either way
the number is not reinterpreted after it arrives (`PROH-OPS-07-26`).

**Why plan it anyway, given the projection.** Because the alternative is reverting option C on an
argument rather than a measurement, which is the failure mode this phase has repeated five times.
The reshape is the best available version of option C; if the best version still loses to the
Python sweep, that is a finding worth having on the record, and it is only obtainable by landing
the best version and measuring it.

**What is deliberately NOT in scope.** The `ordered_points` restructure. The same bench measured a
LEAD taken directly off the `idx_checks_port_ts`-ordered base table at **12.8ms** versus **22.9ms**
through the current CTE-plus-UNION-ALL indirection — a real ~10ms saving. It is not taken here
because it restructures the single `admitted` CTE that `06-25` chose specifically so the retention
floor cannot be applied to the in-window scan while silently missing the boundary lookup
(`PROH-OPS-07-22`). A 10ms saving does not close a 13ms gap at the cost of the mechanism that
enforces a rendered-contract invariant. It is recorded as held-in-reserve in `06-30`'s debt entry.

Purpose: give option C its best shot, on a measurement, without moving the rendered contract.
Output: a reshaped `UPTIME_STRIP_QUERY`, two new standing guards, and `06-PROFILE-4.md`.
</objective>

    **Replace the single `bucket_totals` CTE with four CTEs, then a reduced `bucket_totals`.**

    `clamped` — selects from `ordered_points`: `port`; `MAX(effective_ts, ?)` aliased `seg_start`,
    binding `start`; `MIN(end_ts, ?)` aliased `seg_end`, binding `now`; and `online`. This performs
    once per segment the clamping the current query re-performs inside every bucket's overlap
    expression.

    `spans` — selects from `clamped` with `WHERE seg_end > seg_start`, which drops the zero-width
    boundary segment the `sort_key` ordering deliberately creates when a real check lands exactly at
    `start`. It carries `port`, `seg_start`, `seg_end`, `online`, plus two integer-division
    expressions: `first_idx` as `(seg_start - ?) / ?` binding `start` then `bucket_seconds`, and
    `last_idx` as `(seg_end - 1 - ?) / ?` binding the same two. Both dividends are provably
    non-negative — `seg_start >= start` by the clamp, and `seg_end > seg_start >= start` gives
    `seg_end - 1 >= start` — so SQLite's truncate-toward-zero integer division equals floor division
    on every row this query can produce. Record that proof in the block comment above the constant,
    because it is the reason no clamping of `first_idx`/`last_idx` into `[0, bucket_count-1]` is
    needed.

    `expanded` — a recursive CTE declared with the column list `(port, idx, seg_start, seg_end,
    online, last_idx)`. Its seed arm selects `port, first_idx, seg_start, seg_end, online, last_idx`
    from `spans`; its recursive arm selects `port, idx + 1, seg_start, seg_end, online, last_idx`
    from `expanded` where `idx + 1 <= last_idx`. `WITH RECURSIVE` is already declared at the top of
    the constant for `buckets`; a second recursive CTE needs no further keyword.

    `bucket_sums` — selects from `expanded`, `GROUP BY port, idx`, with the same two
    `SUM(CASE WHEN online IS NOT NULL AND online <> 0 THEN ... ELSE 0 END)` and
    `SUM(CASE WHEN online IS NOT NULL AND online = 0 THEN ... ELSE 0 END)` arms the current query
    uses, aliased `online_seconds` and `offline_seconds`. The overlap expression inside each arm
    becomes `MAX(0, MIN(seg_end, ? + (idx + 1) * ?) - MAX(seg_start, ? + idx * ?))`, binding `start`
    then `bucket_seconds` in each of the two positions. This is multiplication only — the bucket's
    own boundaries are reconstructed from its index, never derived by dividing a timestamp. The
    `MAX(0, ...)` is retained even though every expanded row provably overlaps its bucket, because
    it costs nothing and it is the expression the oracle uses.

    `bucket_totals` — reduced to a scaffold with no aggregate of its own:
    `FROM requested_ports rp CROSS JOIN buckets bk LEFT JOIN bucket_sums bs ON bs.port = rp.port
    AND bs.idx = bk.idx`, selecting `rp.port`, `bk.idx`, `COALESCE(bs.online_seconds, 0)` and
    `COALESCE(bs.offline_seconds, 0)`. The join predicate is now pure equality on two integer
    columns over an at-most-1,344-row aggregate, which SQLite can serve with an automatic index —
    unlike the range predicate it replaces.

    **The scaffold stays in SQL. This is a decision, and here is the evidence for it.** The
    alternative — emit only non-empty buckets and reconstruct the fixed 168 array in Python — is
    cheaper by a measured 4.2ms of the reshaped query's 47.4ms, and it is wrong for two independent

    port whose only row is NULL, silently disabling the NULL guard as a side effect. The scaffold is
