<objective>
Close criteria 3 and 5 by measurement, and fence the shortcut this phase creates.

Two plans have built the toggle and proven it gates. What is left is the part that is easiest to fake
and hardest to do honestly: proving it **costs nothing**, proving it **changes nothing**, and making
sure it can never be used to buy a Pi acceptance pass.

**Criterion 3, stated honestly.** "With the toggle off, a request to the services front page performs
none of the work advanced diagnostics would have required" is, read literally against today's code,
close to vacuous: `/` is a static `send_file` that performs no diagnosis work with the feature fully
enabled. A guard that asserted only that would be exactly the defect class Phase 6 found six times —
strong-looking and unable to fail. The criterion acquires real content only when it is read as a
constraint on *this phase's own implementation*: whatever mechanism tells the front page about the
toggle must not cost the front page anything. `07-02` chose a server-side transform partly for that
reason, and this plan measures the result — a full front-page boot request set, statement-counted on
both sides of the toggle, asserted **equal**.

**Criterion 5, as a round trip rather than an assertion.** "Reversible by restarting with it on" is
provable directly: exercise a disabled deployment against a seeded database, confirm the database's
logical content is unchanged, then reopen the same file with the toggle on and get `07-01`'s captured
bytes back. That is a stronger statement than "we wrote no migration", and it is the statement the
operator actually needs before they turn the feature off on a live Pi.

**The shortcut, and the fence.** `/api/advanced/current` is one of three routes failing Phase 6's Pi
acceptance budgets, and by a distance the most expensive in the mix — 584s CPU and 1,090,992ms
off-CPU across 750 requests in round 5b. Turning it off makes an acceptance run dramatically easier.
That is a legitimate deployment option for an operator and an illegitimate way to pass OPS-07;
`PROH-OPS-07-01` and `PROH-OPS-07-10` already forbid reaching a pass by asking less of the
deployment. This plan mints `PROH-DIA-09-01` for the specific case and guards the deployed default.

**A live hole this phase must not pretend it closed.** `tests/pi_load_acceptance.py`'s `_load_worker`
issues each request and records only elapsed time; it never inspects the response status. A 404 is
therefore recorded as a sub-millisecond success and passes `/api/advanced/current`'s 2000ms budget
trivially. So a run performed with the toggle off would not merely be easier — it would *report a
pass while measuring nothing*, and nothing in the harness would say so. This phase is forbidden from
modifying `tests/pi_load_acceptance.py`, so it cannot close that hole. It records it as measured
evidence with observed numbers and names its owner. Recording a hole is not closing it, and this plan
says which it did.

**Purpose:** make the last two criteria measured facts, and leave the OPS-07 boundary honestly
documented rather than quietly weakened — a recorded hole with a named owner beats an unrecorded one.
**Output:** the cost-equality and reversibility measurements, the deployed-default guard,
`07-DECISIONS.md`, `07-DEBT.md`, and the ROADMAP plan list.
</objective>

<plan_review>
**The one criterion this phase weakens openly.** Criterion 3 is not fully satisfiable as literally
worded, and this plan says so in its objective rather than dressing up a passing guard. `/` performs
no diagnosis work today, so "the front page performs none of the work advanced diagnostics would have
required" cannot be made to fail by any defect this phase could plausibly ship — except one: a
toggle-delivery mechanism that costs the front page something. That single failure mode is what the
cost-equality measurement targets, and it is the entire honest content of the criterion. The
alternative — asserting zero statements on `/` and calling criterion 3 satisfied — would be a guard
that reads as a proof and cannot fail. It is included in `07-01` as a standing tripwire and labelled
as such there.

**How this plan's central measurement could have been vacuous, and what stops it.** The cost equality
is an equality, so it passes whenever both sides do the same amount of work — including when both
sides are the *same* configuration. `tests/helpers.py`'s `load_app` makes that easy to reach by
accident: it writes `extra_env` into `os.environ` and never removes it, so an enabled application
built without an explicit value, after this test's own disabled build, is disabled too. Both totals
would agree, the per-path status subtest would agree, and criterion 3 would be reported satisfied by
a comparison of two identical disabled runs. The explicit `'1'` prevents it; the settings-pair
assertion before the first request detects it if the prevention is ever undone; and acceptance
criterion (i) requires the vacuous pass be *demonstrated* once, with its totals recorded, so the
hazard is on the record as an observation rather than as an argument.

**Why equality rather than a bound.** Comparing the disabled front-page cost to a millisecond or
statement ceiling would tie the guard to the seeded dataset and the executing machine, which
`D-DEBT-06-14` records as the exact defect that produced Phase 6's one INCONCLUSIVE hardware check.
Both terms of the equality are measured in the same run, over the same database, so dataset growth
moves both sides together and the guard keeps meaning what it meant.

**Why `iterdump` and not file bytes.** The deployment runs SQLite in WAL mode, so read-only traffic
touches the sidecar files. A file-bytes oracle would fail for reasons that have nothing to do with
stored data and would be silenced by the first person who hit it — a guard that gets disabled is
worse than no guard. `iterdump`'s logical content is the property criterion 5 actually names.

**Where this plan stops short, stated plainly.** `PROH-DIA-09-01` and the deployed-default guard
raise the cost of using the toggle to buy an OPS-07 pass; they do not make it impossible. The
harness's own blindness to a 404 is the mechanism that would let it happen and this phase is
forbidden from touching the file that contains it. So the boundary is left with the hole *documented
and measured* rather than closed, and `D-DEBT-07-01` names the owner and the fix. Presenting the
compose guard as though it closed the hole would be the same defect class in a different costume:
the guard detects one specific act — flipping the shipped default — and would not detect an operator
exporting a disabling shell variable before an acceptance run.

**Mutation verification.** Every new guard in both tasks has a named mutation and observed values to
record. Task 2's reproduction is explicitly the reverse: it is evidence recorded once, not a standing
assertion, because what it demonstrates must not remain true.

**Reversibility.** Nothing here is one-way: test classes and planning records. Across the whole
phase, no task has a `costly` or `one-way` rating, so `REVERSIBILITY_GATES` produces no
`checkpoint:decision`. That is the conclusion criterion 5 predicted and this plan's Task 1 is what
turns the prediction into a measurement.
