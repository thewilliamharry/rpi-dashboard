<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| production database → inventory report | Potentially sensitive persisted data is reduced to sanitized structural evidence. |
| inventory/support manifest → migration runner | Untrusted or incomplete classification input controls whether a database is eligible for writes. |
| worker startup → on-disk schema | Schema-changing operations can affect all retained Beacon data and later process safety. |
| migration runner → backup directory | Verified recovery artifacts are created and pruned on the shared writable volume. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-16 | Information disclosure | inventory CLI | high | mitigate | Read-only URI access and an allowlisted structural report exclude row values, URLs, tags, events, thumbnails, and secrets. |
| T-01-17 | Tampering | support-floor manifest | high | mitigate | Deterministic fingerprints, checked-in fixture/report provenance, and unknown-shape rejection precede all writes. |
| T-01-18 | Tampering / Denial of service | migration transaction | high | mitigate | Verified backup before each schema change, one transaction per version, rollback tests, and worker-start failure propagation. |
| T-01-19 | Tampering / Denial of service | concurrent migration runners | high | mitigate | Linux inter-process lock plus post-lock version re-read prevents duplicate/overlapping application. |
| T-01-20 | Repudiation | backup catalog/retention | medium | mitigate | Timestamp/version filenames and verified catalog metadata identify the backup used for every migration attempt. |
</threat_model>
