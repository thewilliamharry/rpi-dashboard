<objective>
Expand the tracer to the one case the transition funnel cannot see: a service that never comes back.

A restart that overruns its window produces no new transition — only the passage of time — so
suppression alone would leave a real, continuing failure silent forever. This plan raises exactly
one truthful outage event and alert when a covered service is still down past its window's end plus
that window's own grace period, carrying both the true down-since instant and the explicit
raised-at instant as separate durable fields.

Purpose: satisfy MNT-04 without hiding the continuing failure and without letting the overrun fire
twice, fire for a down period that was never suppressed, or miss a service's second outage.

Output: the two bookkeeping repository functions, the overrun evaluation folded into the existing
down-only probe loop under the transaction that already updates the service row, the bookkeeping
reset on transition, and alert dispatch through the existing sender.
</objective>

  <name>Task 1: Confirm the overrun outage record shape (one-way door)</name>
  <decision>What the single MNT-04 overrun outage event durably records, and how it is distinguished from an ordinary state change.</decision>
  <context>
D-08 is rated one-way in 03.1-CONTEXT.md: the event record shape is consumed by Phase 4's historical
investigation and cannot be back-filled for outages already written. Once a real Pi has recorded
overruns in this shape, changing it means every already-written outage is missing information that
no migration can reconstruct.

The proposed shape (Option A), matching D-08 and the researcher's verified plan:

  A row in `events` with a dedicated `event_type` of `maintenance_overrun`, `port` set, `online` 0,
  `previous_online` 0, `ts` = the raised-at instant (the moment window end plus grace expired and
  the service was still down), `down_since_ts` = the true outage start read from
  `services.state_since`, and `details` carrying the Copywriting Contract's overrun detail string.
  `suppressed_reason` is left NULL — the overrun is never expected. Idempotency for the current down
  period is held in `services.overrun_raised_ts`.

Both timestamps are stored, neither is inferred: Phase 4 can render the whole outage from
`down_since_ts` or only the fault portion from `ts`, without reconstruction.

The undo cost if this is wrong: outages already written on a running Pi carry only whichever
timestamps this shape captured. There is no source to recover the missing one from.
  </context>
  <options>
    <option id="option-a">
      <name>Dedicated event type carrying both timestamps as separate durable fields (recommended)</name>
      <pros>Satisfies D-08 literally — both instants durable and independently legible; a distinct event_type keeps the overrun trivially separable from ordinary state changes in every later read; suppressed_reason stays NULL so the row can never be filtered away by the events reveal control.</pros>
      <cons>Adds a fourth event type the browser must know about; the down-since value duplicates services.state_since at the instant of writing (deliberately — the services row moves on, the event row must not).</cons>
    </option>
    <option id="option-b">
      <name>Reuse the state_change type with a marker column</name>
      <pros>No new event type for the browser to learn.</pros>
      <cons>An overrun is not a state change — the state did not change — so every consumer would have to special-case it; it would also risk being caught by state-change filters, which is exactly the softening MNT-04 forbids.</cons>
    </option>
    <option id="option-c">
      <name>Store only the raised-at instant and derive down-since at read time</name>
      <pros>One fewer column.</pros>
      <cons>Directly contradicts D-08. services.state_since moves on the next transition, so the true outage start becomes unrecoverable for every already-written overrun.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c</resume-signal>
