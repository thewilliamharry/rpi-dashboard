<objective>
Close the first and largest defect behind G-03.1-2: on the Pi, gunicorn began serving — and taking
shared maintenance leases — while the worker was still trying to migrate, and `flock` gave the
exclusive waiter no fairness, so steady shared traffic starved it until it died at P0. Stopping the
web container let the worker take the lock immediately. The contention was not incidental; it was
structural, because `docker-compose.yml` gives `web` and `worker` the same single `depends_on`.

This plan removes the contention class rather than narrowing its window: pending migrations run in
their own one-shot step that completes before either long-running service is created. Nothing holds
an ordinary connection while that step runs, so there is nothing to starve. The step is a real
command, not an inline shell fragment, so its failure output is the migration layer's own exception —
the schema version, the rejected fingerprint, and the inventory command — landing in a dedicated log
stream instead of being replaced five minutes later by a lock-timeout message in the worker's.

The same pass closes the small fourth artifact in the gap: the `recovery` service has no `profiles:`
key, so `docker compose up` starts an offline restore command that exits 2 with no arguments and
adds noise to every startup.

Purpose: make a real deployment's first boot apply migration 9 at all, which every one of MNT-01
through MNT-04 depends on, and make a refused upgrade legible on sight.

Output: the one-shot migration command, the compose startup ordering that guarantees it runs alone,
the recovery profile, and a regression module that pins both the command's behaviour and the compose
contract.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Container startup order → database schema state | Whether a process may read or write the database before its schema has been brought current. |
| Migration failure output → operator diagnosis | The only channel through which a refused upgrade explains itself. |
| `docker compose up` default service set → destructive commands | Which commands the operator's routine startup is permitted to launch unattended. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03.1-41 | Denial of Service | Ordinary shared maintenance leases taken by `web` and `worker` starving the exclusive migration acquisition | high | mitigate | Pending migrations run in a one-shot step that must exit successfully before either long-running service is created, so no ordinary lease can exist during migration; pinned by the two compose dependency regressions. |
| T-03.1-42 | Repudiation | A refused upgrade reaching the operator as a lock-timeout message instead of its real cause | high | mitigate | The migration step installs no exception handling, so the migration layer's own class, message, fingerprint, and remediation command are the process's final output; pinned by the refusal regression including its explicit no-lock-timeout assertion. |
| T-03.1-43 | Elevation of Privilege | The offline restore command being launched unattended by a routine `docker compose up` | medium | mitigate | The recovery service is placed behind a compose profile so it starts only on an explicit `docker compose run`; pinned by the profile regression. |
| T-03.1-44 | Information Disclosure | The migration step's traceback exposing database contents in the compose log | low | accept | The migration layer's failure messages carry schema version numbers and structural fingerprints only — `collect_inventory` is sanitized by construction and emits no row values (verified in Phase 1, `test_inventory_reports_only_structural_metadata`). |
| T-03.1-45 | Denial of Service | The one-shot migration step restart-looping and holding the upgrade lock indefinitely | medium | mitigate | The step overrides the shared anchor's restart policy to the literal no, matching the two existing one-shot services; pinned by the migration service block regression. |

No package-manager install occurs in this plan; no new Python or system dependency is added, so the
package-legitimacy gate does not apply.
