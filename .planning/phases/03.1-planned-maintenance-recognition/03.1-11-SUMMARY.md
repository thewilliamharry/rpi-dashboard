# Phase 03.1 Plan 11: One-shot migration gate closes G-03.1-2's lease-starvation defect Summary

**A dedicated `migrate` compose service, gated on data-init and gating both web and worker, plus a real `python -m beacon.migrate` command with no exception handling so a refused upgrade reports the migration layer's own error verbatim -- closing the largest defect in G-03.1-2 (web taking shared maintenance leases while the worker was still migrating) and moving the offline recovery command behind a compose profile.**

## Performance

- **Duration:** ~30 min
- **Tasks:** 2/2 completed
- **Files modified:** 4 (2 created, 2 modified)

## Accomplishments

- `dashboard/beacon/migrate.py`: a genuine, runnable one-shot command that calls the existing `prepare_database` boundary once, prints applied versions and backup names as JSON on success, and installs no exception handling -- an unhandled exception's traceback carries the migration layer's own class, message, schema version, rejected fingerprint, and `beacon.inventory` remediation command as the process's final output.
- `docker-compose.yml`: a new `migrate` service runs that command, gated on `data-init` completing successfully; `worker` and `web` now depend on `migrate` completing instead of depending on `data-init` directly, so no ordinary shared database-access lease can exist while migrations are being applied. The service is placed between `recovery` and `web` -- the one position of four candidates that pollutes none of the three pre-existing compose text-slicing tests -- with an in-file comment marking that position load-bearing.
- `docker-compose.yml`: `recovery` gets a `profiles: ["recovery"]` key, so a plain `docker compose up` no longer starts the offline restore command; it remains reachable via `docker compose run`, which activates a service's own profile implicitly.
- `tests/test_ui_contract.py`: the one pre-existing assertion this plan genuinely invalidates (the web block naming the data-ownership initializer) is updated to name the migration service instead -- the block's other two assertions (completed-successfully condition present, web never names worker) are unchanged.
- `tests/test_startup_ordering.py`: 10 new regressions -- 4 driving the migrate command as a genuine child process (full current, no-op repeat, legible refusal, no exception handling via AST), and 6 building a structural compose-dependency contract (block extraction terminated on the next service header, not a hard-coded sibling name; a depends_on walker reading name/condition pairs by indentation).

## Decisions Made

- **No try/except in migrate.py:** deliberate per the plan; documented in the module docstring so a later reader does not "improve" it into one. Confirmed by AST parsing (no `ast.Try` nodes) rather than a source grep, since a grep's literal also appears in this plan's own text.
- **Insertion point between `recovery` and `web`:** the plan specified this position after reasoning about all four candidates against the three existing slicers; verified directly by evaluating the `data-init:`→`worker:` slice and the `worker:`→`recovery:` slice against the edited file (neither contains the migrate service's own body).
- **`migrate` depends on `data-init`, not the other way around; `web`/`worker` depend on `migrate`, not `data-init`:** re-establishes the full transitive chain (initializer → migration → long-running services) as three separate, individually pinned assertions rather than one assumed-implied dependency.
- **Backup names, not full paths, in the JSON output:** `migrate.py` prints `backup.name` for each verified backup rather than the full temp-directory path, keeping the operator-facing output stable regardless of where the database lives.
