<objective>
Close the second defect behind G-03.1-2: the thirty-second exclusive-lock wait was terminal, so a
transient startup contention window became a permanent outage — and, worse, an actively misleading
one. The worker reported `migration maintenance lock timeout` and died at P0, restart-looped into the
same starvation, and for roughly five minutes the operator saw a lock message while the true cause
was an `UnsupportedSchemaError` that only surfaced once the web container was stopped.

Two changes, both about when the exclusive lock is requested and what happens when it is refused.

First, stop asking for it when there is nothing to do. Today every call escalates to exclusive
maintenance merely to read the recorded version. That is the steady state on every host reboot, where
Docker restarts the long-running services directly and plan 03.1-11's one-shot step does not re-run:
the worker asks for an exclusive lock it does not need while the web process is already serving. With
the pending-work check moved ahead of the escalation, that path stops contending entirely.

Second, when the lock genuinely is needed and genuinely is held, wait for it. A contention window
that ends is survived within a bounded budget, each wait is logged as a wait, and — the part that
matters most — the moment the lock is obtained, the migration layer's own error propagates unchanged.
The five-minute misdiagnosis becomes impossible: contention delays the answer, it never substitutes
for it.

Purpose: make migration 9 reach a real deployment on the reboot path as well as the first-boot path,
which every one of MNT-01 through MNT-04 depends on, and make contention legible as contention.

Output: the pending-work fast path, the bounded backoff and its named condition, and four regressions
that fail against today's code for the exact reasons the Pi failed.
</objective>
