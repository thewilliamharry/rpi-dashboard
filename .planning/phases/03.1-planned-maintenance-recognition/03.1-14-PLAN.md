<objective>
Three consecutive gap-closure rounds have chased one defect class: a SQLite connection whose
shared maintenance lease and file handle are not released on every exit path. Each round fixed the
instances it happened to enumerate, then wrote a regression gate recognising only the syntactic
shape it had just fixed. The round-2 gate walks `ast.Assign` only, matches the callee name `get_db`
only, scans `dashboard/app.py` only, and its own docstring states it "deliberately does not flag
every connection binding" while explicitly carving `connect_db` out of scope. That carve-out is the
mechanism that produced this round's gap: `dashboard/app.py:2231` binds
`with connect_db(...) as conn:` — an `ast.With`, a different callee — and is structurally invisible
to the gate meant to prevent exactly it.

The one-line fix at line 2231 is not the point of this plan. The gate is.

The code fix is trivial and this plan makes it, along with every other instance of the class that
is already written down in this phase's own review (03.1-REVIEW.md WR-02) and in the orchestrator's
verified codebase inventory. Leaving an already-identified defect for a later round IS the loop.
The substance of the plan is a replacement gate built so that the only way to add a leaking
connection anywhere under `dashboard/` is to add an explicit, reasoned allowlist entry — and built
so that it has been watched to FAIL, because a gate that has never been observed to fail is not
evidence, it is decoration.

The complete class, verified by AST audit before planning:

- Sub-class A, lease-holding (`connect_db` → `ManagedConnection`, whose `close()` is the only thing
  that unlocks the shared flock at `dashboard/beacon/db.py:22-32`): exactly ONE unfixed instance,
  `dashboard/app.py:2231` in `worker_process_preview_requests`. The seventeen `queues.py` sites and
  `app.py`'s `_worker_write_transaction` are correct today but entirely ungated — the current gate
  never looks at `queues.py` at all, so an eighteenth site added without a `finally` would ship
  silently. That is next round's gap unless the gate widens by module as well as by shape.
- Sub-class B, plain-handle leak (`sqlite3.connect` used as a context manager, which commits and
  rolls back but does not close): four sites in `migrations.py` (609, 610, 612, 714) and four in
  `recovery.py` (136, 231, 267, 320). `migrations.py` already documents this exact stdlib behaviour
  and hardens two other functions against it with explicit `try/finally: conn.close()` — the file
  contradicts itself today.

Purpose: end the loop. Not by fixing more instances, but by making an unreasoned leaking binding
impossible to add anywhere in the package.

Output: nine converted sites, one class-exhaustive self-testing gate replacing the shape-specific
one, and a behavioural close proof that reaches the migration paths the existing spy never touches.
</objective>

2. `_derived_database_seams` parses `dashboard/beacon/db.py` and classifies every module-level
   function that produces a SQLite connection. A function is OPENING when it returns a connection
   whose close it does not itself own; it is CLOSING when its body closes the connection in a
   `finally` suite or delegates to a function already classified CLOSING. Applied to today's file
   this must yield `connect_db` as OPENING and `database_access`, `read_transaction` and
   `write_transaction` as CLOSING, with `exclusive_database_maintenance` recognised as a

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Worker poll loop → shared maintenance lease | The worker's preview callback opens a lease-bearing connection on every poll cycle with a claimed request and must release it at a single boundary. |
| Web/worker shared lease holding → migrator exclusive acquisition | Any lease held longer than necessary starves `exclusive_database_maintenance`, which is what the migrator needs. |
| Offline recovery process → the live database inode | The WAL checkpoint runs immediately before the inode is replaced; an open handle at that moment crosses a boundary the restore assumes is quiesced. |
| Future contributor → the structural gate | The gate is the only thing standing between a new connection site and a fourth gap-closure round. |
