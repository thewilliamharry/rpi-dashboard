<objective>
Three consecutive gap-closure rounds have chased one defect class: a SQLite connection whose
shared maintenance lease and file handle are not released on every exit path. Each round fixed the
instances it happened to enumerate, then wrote a regression gate recognising only the syntactic
shape it had just fixed. The round-2 gate walks `ast.Assign` only, matches the callee name `get_db`
only, scans `dashboard/app.py` only, and its own docstring states it "deliberately does not flag
every connection binding" while explicitly carving `connect_db` out of scope. That carve-out is the
mechanism that produced this round's gap: `dashboard/app.py:2231` binds
`with connect_db(...) as conn:` — an `ast.With`, a different callee — and is structurally invisible
to the gate meant to prevent exactly it.

The one-line fix at line 2231 is not the point of this plan. The gate is.

The code fix is trivial and this plan makes it, along with every other instance of the class that
is already written down in this phase's own review (03.1-REVIEW.md WR-02) and in the orchestrator's
verified codebase inventory. Leaving an already-identified defect for a later round IS the loop.
The substance of the plan is a detector built so that the only way to add a leaking connection
anywhere under `dashboard/` is to add an explicit, reasoned allowlist entry — and built so that it
has been watched to FIRE, because a gate that has never been observed to fail is not evidence, it
is decoration.

The complete class, verified by AST audit before planning and independently re-enumerated by the
plan checker:

- Sub-class A, lease-holding (`connect_db` produces a `ManagedConnection`, whose `close()` is the
  only thing that unlocks the shared flock at `dashboard/beacon/db.py:22-32`): exactly ONE unfixed
  instance, `dashboard/app.py:2231` in `worker_process_preview_requests`. The seventeen `queues.py`
  callers and `app.py`'s `_worker_write_transaction` are correct today but entirely ungated — the
  current gate never looks at `queues.py` at all, so an eighteenth caller added without a `finally`
  would ship silently. That is next round's gap unless the gate widens by module as well as by shape.
- Sub-class B, plain-handle leak (`sqlite3.connect` used as a context manager, which commits and
  rolls back but does not close): four sites in `migrations.py` (609, 610, 612, 714) and four in
  `recovery.py` (136, 231, 267, 320). `migrations.py` already documents this exact stdlib behaviour
  and hardens two other functions against it with explicit `try/finally: conn.close()` — the file
  contradicts itself today.

Nine sites. Not eleven: `db.py:78` inside `connect_db` and `app.py:247` inside
`_worker_write_transaction` are ownership-transfer and self-guarded respectively;
`migrations.py:637` and `:666` already carry their `finally`; `migrations.py:681` is an expression,
not a binding.

Purpose: end the loop. Not by fixing more instances, but by making an unreasoned leaking binding
impossible to add anywhere in the package.

Output: a detector proven against the unfixed tree, nine converted sites, and a class gate standing
over an empty class.
</objective>

Build the detection layer in `tests/test_module_boundaries.py`. Touch nothing under `dashboard/`.

1. Add module-level helper functions carrying the detector's logic, so it can be exercised against
   synthetic sources as well as against real files. Name them `_derived_database_seams`,
   `_package_connection_factories`, `_module_opening_seams` and `_unguarded_connection_bindings`, and
   give each a docstring stating what it derives and why derivation beats a literal. Keep them plain
   functions — no test-class methods, no fixtures on disk.

2. `_derived_database_seams` parses `dashboard/beacon/db.py` and classifies every module-level
   function that produces a SQLite connection. A function is OPENING when it returns a connection
   whose close it does not itself own; it is CLOSING when its body closes the connection in a
   `finally` suite or delegates to a function already classified CLOSING. Applied to today's file
   this must yield `connect_db` as OPENING and `database_access`, `read_transaction` and
   `write_transaction` as CLOSING, with `exclusive_database_maintenance` recognised as a
   lease-holding context manager that binds no connection. Record that expected classification as a
   module-level constant named `EXPECTED_DATABASE_SEAMS` and add
   `test_the_derived_seam_set_matches_the_database_module`, asserting the derivation equals the
   constant, with a failure message naming the seam that appeared, disappeared, or changed class.

3. `_package_connection_factories` is the package-wide phase, and it is what closes the cross-module
   hole. Walk every `.py` file under `dashboard/` recursively and collect every MODULE-LEVEL function
   that returns — directly or transitively through another collected factory — a call to an opening
   seam, keyed as `module_path::function_name`. Iterate to a fixed point so a factory returning
   another factory is caught. Against today's tree this set must contain at least
   `dashboard/beacon/queues.py::_connect`, `dashboard/app.py::get_db`,
   `dashboard/beacon/inventory.py::_readonly_connection` and `dashboard/beacon/db.py::connect_db`.
   Restrict collection to functions defined at module level: `dashboard/beacon/outbound.py` defines a
   `_connect` METHOD on a class returning a socket-level object, and a looser rule collects it.
   Add `test_the_package_wide_factory_set_contains_every_known_connection_factory`, asserting the
   four names above are present and that no `outbound.py` entry is.

4. `_module_opening_seams` takes one module's path and tree and returns the set of local names that,
   IN THAT MODULE, hand back a connection the caller must close. It is the union of four sources:
   the attribute call `sqlite3.connect`; every OPENING name from step 2 that the module imports;
   every factory from step 3 that the module imports, resolved through `ast.ImportFrom` and
   `ast.Import` INCLUDING `as` aliases, so the local name is what gets added rather than the
   defining name; and every factory from step 3 defined in the module itself. Without the third
   clause a future `dashboard/beacon/foo.py` doing a sibling import of a factory and binding it with
   no `finally` is invisible — a new call NAME in a covered module, which is precisely the mechanism
   that let `connect_db` slip past the round-2 gate. Resolve relative imports against the importing
   module's package so `from .queues import _connect` and `from ..app import get_db` both resolve.

5. `_unguarded_connection_bindings` walks a module tree and returns one finding per unguarded
   binding, each carrying the module path, the enclosing function name, the line number and the
   callee text. It must walk `ast.Assign` AND `ast.With` AND `ast.AsyncWith` — for the `with` forms
   it inspects every `withitem.context_expr`, which is the node type the round-2 gate never looked
   at. It must recognise callees that are `ast.Name` and callees that are `ast.Attribute`, since
   `sqlite3.connect` is the latter. A binding is ACCEPTED, producing no finding, in exactly two
   cases: the value expression is a call to a CLOSING seam or to `contextlib.closing` or to
   `exclusive_database_maintenance`; or the binding's own name is closed in a `finally` suite within
   the same enclosing function. Nothing else is accepted. A bare `return` of a call to an opening
   seam is not a binding and produces no finding — that is a factory, and factories are handled by
   step 7's RECORDED kind, not by this walk. Do not add a third acceptance rule to make a site pass.

6. Derive the module set rather than listing it. Add a helper that globs every `.py` file under
   `dashboard/` recursively, excluding nothing by name, and keeps those whose `_module_opening_seams`
   is non-empty. That is the gate's scope. Add `test_the_gate_covers_every_module_that_opens_a_connection`,
   asserting the derived scope contains at minimum `dashboard/app.py`, `dashboard/beacon/queues.py`,
   `dashboard/beacon/migrations.py`, `dashboard/beacon/db.py`, `dashboard/beacon/recovery.py` and
   `dashboard/beacon/inventory.py`, and that it does NOT contain `dashboard/beacon/outbound.py`.
   `dashboard/beacon/web.py` will also be in scope because it imports the seam; that is correct and
   is not a failure. State the derived scope in the failure message so a future module that starts
   opening connections announces itself.

7. Add the allowlist as TWO module-level constants with distinct, both-enforced staleness predicates.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Worker poll loop → shared maintenance lease | The worker's preview callback opens a lease-bearing connection on every poll cycle with a claimed request and must release it at a single boundary. |
| Web/worker shared lease holding → migrator exclusive acquisition | Any lease held longer than necessary starves `exclusive_database_maintenance`, which is what the migrator needs. |
| Offline recovery process → the live database inode | The WAL checkpoint runs immediately before the inode is replaced; an open handle at that moment crosses a boundary the restore assumes is quiesced. |
| Future contributor → the structural gate | The gate is the only thing standing between a new connection site and a fourth gap-closure round. |
| Module boundary → seam resolution | A factory imported from a sibling module under a new local name is a new call name inside a covered module — the exact shape that defeated the round-2 gate. |
