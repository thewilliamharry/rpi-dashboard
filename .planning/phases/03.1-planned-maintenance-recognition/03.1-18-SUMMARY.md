## Decisions Made
- **Derive, don't raise-or-cap.** Of G-03.1-71's `missing:` item's three offered shapes (derive the cap, raise it to genuinely cover the retention, or refuse/flag), derivation was chosen: a fixed-but-bigger number reproduces the exact same class of defect at a larger threshold (which is how this bound reached 64 with a comment claiming a year in the first place), and capping `EXPIRE_DAYS` in `config.py` would move the silent-truncation failure mode one layer down rather than eliminate it.
- **Ceiling raised, not removed.** `attributed_downtime_seconds` is callable with an arbitrary interval, so an anti-runaway ceiling stays mandatory; 4096 steps (8193 days) is chosen to be far beyond any `EXPIRE_DAYS` an operator would reasonably configure while remaining a genuine, cheap-to-reach anti-runaway bound rather than an unbounded loop.
- **Log, don't raise, on ceiling bind.** Both `attributed_downtime_seconds` callers (`get_current_diagnosis` serving `/api/advanced/current` on the live Pi, and `app.py`'s `/api/services` path) consume a plain integer; converting a long retention setting into a new exception type would be a worse regression than the under-count this plan fixes.
- **Noon-aligned test fixture.** Chose an interval that starts and ends at local noon (never covered by the midnight-start daily window used in the new tests) specifically so the pre-fix defect reproduces as an under-count (the undiscovered older segment's single `coverage()` check lands on an uncovered instant) rather than an accidental over-count from a lucky boundary alignment — verified this reasoning against the actual pre-fix behavior before writing the assertions, matching the plan's measured cross-check exactly (127d->127.0h, 128d->128.0h, 129d->129.0h, 130d->129.0h, 150d/400d->129.0h).
