## User Constraints (from CONTEXT.md)

### Locked Decisions

**Window Definition and Edit Surface**

- **D-01:** Maintenance windows are created, edited, disabled, and removed through the main dashboard's existing service metadata editor, extending the `PUT /api/service-meta/<int:port>` route (`dashboard/app.py:2510`). The `/advanced` workspace stays strictly GET-only with no mutation endpoint, exactly as PROJECT.md's Key Decision records and `03-SECURITY.md` verified across 46 blocking threats. No new mutation boundary is introduced. — Reversibility: costly.
- **D-02:** Local-time windows are evaluated as wall-clock literals. On a spring-forward date a window whose start time does not exist is skipped; on a fall-back date a window whose start time occurs twice is honored both times. This matches the behavior of the cron entry or systemd timer on the Pi that typically causes the restart. — Reversibility: costly.
- **D-03:** A window is a start time, a duration, and a set of active weekdays. A start time plus a duration crosses midnight naturally (23:50 + 30m), so no separate midnight rule is needed. No cron-style expression field. — Reversibility: one-way (shape becomes migration 9's stored schema).
- **D-04:** Every window carries its own explicit overrun grace period. The field is required and always visible in the editor, prefilled with a sensible default the operator can change. Grace is never derived from window duration. — Reversibility: costly.
- **D-05:** A service may have several windows, each with its own time, weekday set, and grace. "Is this service in maintenance now?" resolves to "does any enabled window cover now?". Where windows overlap, the longest grace applies. — Reversibility: one-way (list-per-service schema).

**Active Maintenance and Overrun Presentation**

- **D-06:** A service that is offline while covered by an active confirmed window displays a distinct, visually calm `In maintenance` state on both the dashboard card and the advanced services table — not the treatment a real failure receives. The stored fact stays `offline`; the displayed state is derived and discloses its derivation on inspection. The service is never removed from the failure surface entirely.
- **D-07:** Active confirmed maintenance is kept out of the advanced workspace's global active-exceptions list (`compose_active_exceptions`, `dashboard/beacon/diagnosis.py:451`) and is presented in the Services section detail instead (Phase 3's D-12 precedent). — Reversibility: reversible.
- **D-08:** The single overrun outage event required by MNT-04 carries the true down-since timestamp as its outage start (available from `services.state_since`) plus an explicit separate record of when it was raised at grace expiry. Both are durable and neither is inferred. — Reversibility: one-way.
- **D-09:** Availability continues to count planned downtime in full and the headline figure is never adjusted. Expanded detail attributes the portion of the loss caused by confirmed maintenance. No second "excluding maintenance" figure is presented at equal weight anywhere. — Reversibility: reversible.

**Suppression Mechanism**

- **D-10:** Expected down/recovered event entries are written and tagged, then filtered at read — never withheld from the database. The main dashboard events feed hides tagged entries by default behind a visible reveal control that states how many entries are hidden. — Reversibility: one-way.

**Suggestion Lifecycle**

- **D-11:** A suggested window surfaces only inside that service's metadata editor, alongside the fields it would populate. It is not shown on the service card and not listed in `/advanced`. It remains inactive and changes no event or alert behavior until the operator confirms or edits it.
- **D-12:** An unconfirmed suggestion persists indefinitely rather than expiring, and is recomputed against the service's recent outage evidence rather than frozen at first detection.

## Summary

This phase adds no new third-party dependency to the request/response path — it is almost entirely new domain logic layered onto an already-verified two-process (Flask web / APScheduler worker) architecture sharing one SQLite database. The only new package need is Python's `tzdata` (IANA time-zone data, PyPI, maintained by the CPython org — [VERIFIED: dashboard/pyproject.toml has no tzdata dependency today; SUS-flagged by the automated legitimacy check for "unknown downloads," not for provenance — see Package Legitimacy Audit]), because the container's Debian-slim base has no evidence of bundling `/usr/share/zoneinfo` and Python's stdlib `zoneinfo` module needs *some* IANA source to resolve named zones such as `America/New_York`.

The four requirements decompose into four largely independent read/write seams that all key off one new table, `maintenance_windows` (list-per-service, per D-05), plus two additive columns on `events` and one on `services`:

1. **CRUD (MNT-01):** extends the existing `PUT /api/service-meta/<port>` web-owned write path (D-01) — no new mutation boundary, no worker involvement.
2. **Detection (MNT-02):** a worker-side read-only analysis over recent `events` rows, surfaced through the *same* `GET /api/service-meta/<port>` payload the editor already fetches.
3. **Suppression (MNT-03):** a tag computed and written **inside** the existing `worker_handle_state_transition`/`_legacy_handle_state_transition` funnel, at the same moment the `state_change` event is inserted — never a second code path, never a withheld row.
4. **Overrun (MNT-04):** a periodic re-check that piggybacks on the *existing* down-service probe cadence (J4, `only_down=True`, every 60s) rather than requiring a new APScheduler job — because a service that stays down produces no new transition to hook, only the passage of time.

The single hardest correctness problem in this phase is **not** availability math or suppression plumbing — both are additive, non-breaking extensions of code already read and quoted below. It is **DST-safe local-wall-clock window matching** (D-02) combined with **idempotent overrun raising across schema-evolving operator edits** (open question 7a in the phase brief). Both are solved below with one clock-agnostic, race-free design: freeze the covering window's `grace_until` timestamp onto the *event row itself* the moment a down-transition is suppressed, rather than re-deriving it later from live (and editable) window configuration.

**Primary recommendation:** Add migration 9 with one list-shaped `maintenance_windows` table (never one-row-per-port), two nullable `events` columns (`suppressed_reason`, `maintenance_grace_until`), one nullable `events` column for the overrun event (`down_since_ts`), and one nullable `services` bookkeeping column (`overrun_raised_ts`); evaluate coverage with `zoneinfo` + PEP 495 `fold` inside a small pure function unit-testable independent of Flask/APScheduler; tag suppression inside the existing transition funnel; raise overrun inside the existing down-only uptime-check loop; and read availability attribution as a second, additive query over `service_checks` — never touching `_uptime_summary`'s existing time-weighted arithmetic.

### Pattern 1: Coverage evaluation as a pure, DST-aware function

**What:** A single function that, given a service's enabled windows, the current instant, and a timezone, answers "is this service covered right now, and until when (including grace)?" — with no SQLite or Flask dependency, matching the existing `beacon/monitoring.py` "operations interface" style (`[VERIFIED: dashboard/beacon/monitoring.py:1-9]` — "This module only receives callables for persistence, network transport, and clocks, which keeps it importable by jobs and unit tests without creating Flask, schedulers, or browser processes.").

**When to use:** Called from two places only — the transition-tagging seam (write-time) and the display-composition seam (`compose_service_diagnosis`, read-time). Both call sites pass the same function; there is exactly one definition of "covered."

**Example:**
```python
# dashboard/beacon/maintenance.py (new module)
from dataclasses import dataclass
from datetime import datetime, timedelta
from zoneinfo import ZoneInfo


@dataclass(frozen=True)
class Window:
    id: int
    start_minute: int          # minutes since local midnight, 0-1439
    duration_minutes: int
    weekdays: frozenset[int]   # ISO weekday ints, Mon=1 .. Sun=7
    grace_minutes: int
    enabled: bool


def _local_occurrence_epochs(window, now_epoch, tz):
    """Yield every valid UTC epoch at which `window` could have started,
    within [now - duration - grace - 1 day, now], honoring D-02's wall-clock
    literal rule: a nonexistent spring-forward instant is skipped; an
    ambiguous fall-back instant is yielded twice (fold=0 and fold=1)."""
    now_local = datetime.fromtimestamp(now_epoch, tz=tz)
    lookback_days = 2  # generous enough to cover any duration+grace this UI allows
    for day_offset in range(lookback_days + 1):
        candidate_date = (now_local - timedelta(days=day_offset)).date()
        if candidate_date.isoweekday() not in window.weekdays:
            continue
        naive = datetime(
            candidate_date.year, candidate_date.month, candidate_date.day,
            window.start_minute // 60, window.start_minute % 60,
        )
        for fold in (0, 1):
            candidate = naive.replace(tzinfo=tz, fold=fold)
            candidate_epoch = candidate.timestamp()
            # Round-trip through UTC and back: if the wall-clock time does not
            # exist (spring-forward gap), the round trip will not reproduce the
            # same naive wall time -- this is the standard zoneinfo idiom for
            # gap detection [CITED: PEP 495 / docs.python.org zoneinfo].
            roundtrip = datetime.fromtimestamp(candidate_epoch, tz=tz)
            if (roundtrip.hour, roundtrip.minute) != (naive.hour, naive.minute):
                if fold == 0:
                    continue  # nonexistent instant: skip per D-02
                continue
            yield int(candidate_epoch)
            if fold == 1 and _is_ambiguous(naive, tz):
                continue  # already yielded fold=0 case above in same loop
            break  # non-ambiguous: fold=0 and fold=1 give the same instant


def coverage(windows, now_epoch, tz_name):
    """Return (covered: bool, grace_until_epoch: int | None).

    D-05: "does any enabled window cover now?" with "the longest grace
    applies" where windows overlap. Coverage includes the grace period --
    a window is "covering" from its start through end+grace, matching the
    UI-SPEC tooltip: "until {window end + grace, local time}".
    """
    tz = ZoneInfo(tz_name)
    covering_grace_ends = []
    for window in windows:
        if not window.enabled:
            continue
        for start_epoch in _local_occurrence_epochs(window, now_epoch, tz):
            raw_end = start_epoch + window.duration_minutes * 60
            grace_end = raw_end + window.grace_minutes * 60
            if start_epoch <= now_epoch < grace_end:
                covering_grace_ends.append(grace_end)
    if not covering_grace_ends:
        return False, None
    return True, max(covering_grace_ends)
```

### Pattern 2: Suppression tag written inside the existing transition funnel

**What:** `worker_handle_state_transition` (`dashboard/app.py:1692`) and `_legacy_handle_state_transition` (`dashboard/app.py:849`) are the single funnel through which every `state_change` event and its optional alert are produced [VERIFIED: `dashboard/app.py:849-873`, `dashboard/app.py:1692-1701` — both call `_worker_record_event`/`_record_event` with `event_type='state_change'` then `worker_send_transition_alert`/`_send_transition_alert`]. Extend both, not a new parallel path.

**When to use:** At the exact moment a transition is detected (inside the existing `for transition in transitions: _handle_state_transition(**transition)` loop in `_legacy_do_uptime_check`, `dashboard/app.py:1478-1479`).

**Example:**
```python
# dashboard/app.py — worker_handle_state_transition, extended
def worker_handle_state_transition(authority, **kwargs):
    now = int(authority.now())
    with _worker_write_transaction(authority) as conn:
        windows = beacon_repositories.get_maintenance_windows(conn, kwargs['port'])
        suppressed_reason = None
        grace_until = None
        if not kwargs['online']:
            # Going down: suppress only if the down instant itself is covered.
            covered, grace_until = beacon_maintenance.coverage(windows, now, SETTINGS.timezone)
            if covered:
                suppressed_reason = 'maintenance'
        else:
            # Recovering: suppress only if this port's *current* down period
            # opened as a suppressed transition (frozen decision, D-08-style
            # non-inference -- see Open Question Q4/7a resolution below).
            opening = beacon_repositories.get_open_down_transition(conn, kwargs['port'])
            if opening and opening['suppressed_reason'] == 'maintenance':
                suppressed_reason = 'maintenance'
        beacon_repositories.insert_state_change_event(
            conn, ts=now, suppressed_reason=suppressed_reason,
            maintenance_grace_until=grace_until, **kwargs,
        )
        if suppressed_reason is not None:
            beacon_queues.renew_worker_authority(authority, now=now)  # unchanged pattern
            return False  # no alert attempted; nothing to record as sent/failed
    return worker_send_transition_alert(authority, now=now, **kwargs)
```

### Pattern 3: Overrun idempotency folded into the existing down-only probe loop

**What:** `_legacy_do_uptime_check(only_down=True)` (J4, every 60s) already iterates every currently-offline service under `_mutation_write_transaction` [VERIFIED: `dashboard/app.py:1358-1491`, `WHERE s.last_seen >= ? AND s.is_online = 0` when `only_down`]. Add the overrun check to the branch where `previous_online == online_int == 0` (still down, no new transition this poll).

**When to use:** Same transaction as the existing per-service `UPDATE services` write, so the idempotency read-then-set (`overrun_raised_ts IS NULL` → set it) is race-free by construction — J3 and J4 already share `_uptime_lock` [VERIFIED: `dashboard/app.py:1359`, `_uptime_lock.acquire(blocking=False)`], so only one of them is ever inside this loop at a time.

**Example:**
```python
# inside _legacy_do_uptime_check's per-row loop, after the existing UPDATE:
if previous_online == 0 and online_int == 0:  # still down, no transition this poll
    opening = beacon_repositories.get_open_down_transition(conn, port)
    if (
        opening and opening['suppressed_reason'] == 'maintenance'
        and opening['maintenance_grace_until'] is not None
        and now >= opening['maintenance_grace_until']
        and not beacon_repositories.overrun_already_raised(conn, port)
    ):
        beacon_repositories.insert_event(
            conn, ts=now, event_type='maintenance_overrun', port=port,
            online=0, previous_online=0,
            down_since_ts=row['state_since'],
            details=f"{row['display_name'] or row['title']} still down past maintenance",
        )
        beacon_repositories.mark_overrun_raised(conn, port, now)
        # Per MNT-04: this IS a real alert -- not suppressed -- so it still
        # goes through the normal alert path, cooldown-gated like any other.
```

### Anti-Patterns to Avoid

- **Re-deriving "was this covered by maintenance" from live window configuration at read time (for suppression or overrun purposes):** the operator can edit or disable a window at any moment (D-01's editor has no lock on in-flight state); re-deriving coverage later would let a *later* edit retroactively change what an *already-written* event row means, or cause the overrun evaluator to disagree with the decision the suppression path already made. Freeze `maintenance_grace_until` onto the event row at the moment of suppression instead (see open question 7a's resolution below).
- **Nesting `_worker_write_transaction` calls:** it opens `BEGIN IMMEDIATE` on a fresh connection every call [VERIFIED: `dashboard/app.py:238-250`]; the coverage read and the tagged event INSERT must share **one** transaction, not two nested ones.
- **Adding a new `event_type` for suppressed down/recovered events:** D-10 requires the *same* `state_change` semantics, filtered at read — a new event type would need its own frontend branch and would violate "written and tagged" (tagging implies the row keeps its existing shape plus a marker, not a divergent shape).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| DST offset tables / manual UTC-offset-by-date lookup | A custom "is DST in effect on this date" table | Python stdlib `zoneinfo.ZoneInfo` + PEP 495 `fold` | IANA transition rules change (governments move DST dates with little notice); `zoneinfo` reads the current, updatable IANA database. Hand-rolling this is the single highest-risk hand-roll in this phase. |
| Cron-expression parsing | A `croniter`-style parser | N/A — D-03 explicitly forbids a cron-style field; the schema is start+duration+weekday-set | Locked decision; do not introduce a parsing library for a field type the phase does not have. |
| Recurring-event RRULE logic | `python-dateutil`'s `rrule` | The small `_local_occurrence_epochs` function above | D-03's shape (fixed weekday set, single daily start+duration) is far narrower than RFC 5545 RRULE; pulling in a general recurrence library for "does this weekday, this time, exist today" is disproportionate and adds a dependency with no other use in this codebase. |

**Key insight:** Everything genuinely hard in this phase (DST correctness) has exactly one correct, narrow stdlib tool (`zoneinfo`); everything that *looks* hard (recurring schedules, cron) is explicitly narrowed by D-03 to something a ~40-line pure function covers completely and testably.

## Common Pitfalls

### Pitfall 1: Weekday numbering mismatch between browser and worker
**What goes wrong:** JavaScript's `Date.getDay()` returns Sunday=0..Saturday=6; Python's `date.weekday()` returns Monday=0..Sunday=6; Python's `date.isoweekday()` returns Monday=1..Sunday=7. The UI-SPEC's weekday chips are ordered `Mo Tu We Th Fr Sa Su` (Monday-first) — silently picking a different numbering on either side of the wire produces windows that fire on the wrong day.
**Why it happens:** Three different "day of week" integer conventions exist in the stacks this phase touches, and none of them match by accident.
**How to avoid:** Standardize on ISO weekday integers (Mon=1..Sun=7) end to end — store as a comma-separated `TEXT` column (matching the existing `service_meta.tags` CSV convention [VERIFIED: `dashboard/beacon/migrations.py:83`, `tags TEXT DEFAULT ''`]), and have the frontend map its `Mo..Su` chip order explicitly to `1..7`, never relying on `Date.getDay()`.
**Warning signs:** A window that appears to fire "one day early" or "one day late" in manual testing; a fall-back/spring-forward test that passes on Monday but fails on Sunday.

### Pitfall 2: Missing IANA tzdata in the container
**What goes wrong:** `zoneinfo.ZoneInfo("America/New_York")` raises `ZoneInfoNotFoundError` at first use inside the worker container.
**Why it happens:** `python:3.12-slim-bookworm` does not ship `/usr/share/zoneinfo` by default, and nothing in `dashboard/Dockerfile` installs the `tzdata` apt package [VERIFIED: full Dockerfile read this session, no `apt-get`/`tzdata` line present].
**How to avoid:** Add the `tzdata` PyPI package to `dashboard/pyproject.toml` dependencies (see Standard Stack); it is pure Python data, requires no apt/system changes, and is picked up automatically by `zoneinfo` as a fallback source.
**Warning signs:** Works fine in local dev (most developer machines have system tzdata) but fails only inside the built container — this is exactly the kind of gap CI/CD or a Pi-class acceptance run (OPS-07) is meant to catch, so a phase-local test that actually imports `zoneinfo` inside the test process (not mocked) is the cheap early catch.

### Pitfall 3: Assuming 60-second down-transition detection precision
**What goes wrong:** `dashboard/beacon/diagnosis.py:201`'s comment-adjacent cadence value (`cadence = 60 if availability == 'offline' else 300`) can be misread as "a down transition is detected within 60 seconds." It is not.
**Why it happens:** J4 (`only_down=True`, every 60s) only re-probes services **already** marked `is_online=0` [VERIFIED: `dashboard/app.py:1378`, `where = "WHERE s.last_seen >= ? AND s.is_online = 0" if only_down else ...`]. A service that was online and just went down is *not* visited by J4 until J3's full 5-minute sweep (`only_down=False`, every 300s) catches the flip. Only the *recovery* transition (offline→online) benefits from J4's 60s cadence, because by then the service is already marked offline and J4 is polling it.
**How to avoid:** Ground the MNT-02 detector's start-time tolerance in the *asymmetric* worst case: down-transition detection lag up to ~300s, recovery-transition detection lag up to ~60s. See `## Open Questions` Q1 for the derived tolerance numbers.
**Warning signs:** A detector tuned to a tight (~60-90s) tolerance will systematically under-cluster genuinely-recurring outages, because two occurrences of the *same* true restart time can be observed up to ~300s apart from each other.

### Pitfall 4: Reusing `alert_status` or `details` for the suppression tag
**What goes wrong:** `events.details` is rendered verbatim as the visible sub-line for `state_change` rows today [VERIFIED: `dashboard/app.js:314`, `event.event_type === 'monitoring_gap' ? monitoringGapDuration(event) : event.details || event.error_class || ''` — `details` is displayed, not just stored]; `events.alert_status` already carries a distinct vocabulary (`http_2xx`, `policy_*`, `delivery_error`) tied to webhook delivery outcomes [VERIFIED: `dashboard/app.py:773-846`]. Repurposing either column for the maintenance tag would silently corrupt the existing displayed message or collide with the alert-outcome vocabulary.
**How to avoid:** Add a dedicated nullable column, `events.suppressed_reason TEXT`, via `_add_column` in migration 9 (the established idempotent-add pattern, e.g. `_migration_2_service_diagnostics`'s additions to `services`).
**Warning signs:** Any code path that both writes and reads `alert_status`/`details` for two different purposes on the same row is doing this.

### Pitfall 5: Assuming `/advanced` already has an availability percentage to attach attribution to
**What goes wrong:** Planning MNT-03/D-09's "Maintenance attribution" row as if it modifies an existing `/advanced` uptime figure.
**Why it happens:** The main dashboard's `/api/services` route computes `uptime_pct`/`uptime_buckets` via `_uptime_summary` [VERIFIED: `dashboard/app.py:2431`], but `/advanced`'s `compose_service_diagnosis` (`dashboard/beacon/diagnosis.py:192-227`) does **not** — it has no `uptime_pct` field at all, and neither `dashboard/advanced.js` nor `dashboard/advanced.html` reference an uptime percentage anywhere [VERIFIED: grep of both files for `uptime`/`availability` returned only the unrelated `serviceAvailability()` status-word helper].
**How to avoid:** Treat the `/advanced` Maintenance-attribution row as a **net-new** additive read (a second query over `service_checks`, run alongside — not inside — `_uptime_summary`'s existing algorithm), not a modification of anything currently rendered there.

### Pitfall 6: Double-`BEGIN` from calling `_worker_write_transaction` inside another one
**What goes wrong:** `_worker_write_transaction` opens `conn = connect_db(...)` then `conn.execute('BEGIN IMMEDIATE')` on a **new** connection every call [VERIFIED: `dashboard/app.py:238-250`]. It does not compose with itself.
**How to avoid:** The coverage read (`get_maintenance_windows`) and the tagged event write must happen on the **same** `conn` inside **one** `with _worker_write_transaction(authority) as conn:` block, as shown in Pattern 2 above — never as a separate helper that opens its own transaction and is then called from inside another.

### Pitfall 7: Reusing `Migration(9, ...)`'s `schema_changing=True` default incorrectly for a data-only fix-up
**What goes wrong:** All eight existing migrations set `schema_changing=True`, which triggers `create_verified_backup` before applying [VERIFIED: `dashboard/beacon/migrations.py:507-516`, `run_migrations`'s `if migration.schema_changing and not new_database:`]. Migration 9 (adding tables/columns) correctly wants `True`. A *later*, purely data-fixup migration in this phase's follow-on work should not blindly copy `True` if it touches no schema — but this phase's migration 9 genuinely does change schema, so `True` is correct here; flagging only so the planner does not need to re-derive this from first principles.
**How to avoid:** Keep `schema_changing=True` for migration 9 (it adds a table and four columns) — this is not a pitfall to fix, it is confirmation of the correct value.

### Pitfall 8: Running the overrun check for services that just transitioned this same poll
**What goes wrong:** If the overrun check runs unconditionally for every offline service in J4's loop, it will re-evaluate a service that **just** went down in this very poll (a fresh, unsuppressed real outage) against stale `overrun_raised_ts`/`maintenance_grace_until` state left over from a *previous* down period, potentially raising a spurious duplicate `maintenance_overrun` event.
**How to avoid:** Guard the overrun check on `previous_online == online_int == 0` (i.e., "still down, no transition this poll") as shown in Pattern 3; a fresh down transition is handled entirely by the transition funnel (Pattern 2), never by the overrun path.

### Pitfall 9: Forgetting to reset `services.overrun_raised_ts` on state change
**What goes wrong:** If the bookkeeping column is never cleared, a service's *second* down period (after a full recovery and a later new outage) is silently treated as "already raised" and the MNT-04 event never fires for the new occurrence.
**How to avoid:** Clear `overrun_raised_ts` to `NULL` in the same `UPDATE services SET ... state_since=CASE WHEN is_online != X THEN ? ELSE state_since END` statement that already resets `state_since` on a genuine transition [VERIFIED: `dashboard/app.py:1416-1431`] — add `overrun_raised_ts=CASE WHEN is_online != ? THEN NULL ELSE overrun_raised_ts END` alongside it.

### 4. Suggestion detector (clustering sketch)
```python
# dashboard/beacon/maintenance.py — pure, framework-free, unit-testable with UtcClock
START_TOLERANCE_SECONDS = 900   # 15 minutes -- see Open Question Q1 for derivation
DURATION_TOLERANCE_SECONDS = 600  # 10 minutes -- see Open Question Q1 for derivation
MIN_OCCURRENCES = 3
LOOKBACK_DAYS = 21  # see Open Question Q2

def detect_suggestion(down_recovered_pairs, tz_name, *, now_epoch):
    """down_recovered_pairs: [(down_ts, recovered_ts), ...] for one port, most
    recent LOOKBACK_DAYS only. Returns a suggestion dict or None."""
    tz = ZoneInfo(tz_name)
    observations = []
    for down_ts, recovered_ts in down_recovered_pairs:
        local_down = datetime.fromtimestamp(down_ts, tz=tz)
        start_minute = local_down.hour * 60 + local_down.minute
        observations.append({
            'date': local_down.date(), 'start_minute': start_minute,
            'duration_seconds': recovered_ts - down_ts,
        })
    # Greedy single-link clustering on start_minute, then filter by duration
    # tolerance and >= 3 distinct calendar dates.
    observations.sort(key=lambda o: o['start_minute'])
    best_cluster = None
    for anchor in observations:
        cluster = [
            o for o in observations
            if abs((o['start_minute'] - anchor['start_minute']) * 60) <= START_TOLERANCE_SECONDS
            and abs(o['duration_seconds'] - anchor['duration_seconds']) <= DURATION_TOLERANCE_SECONDS
        ]
        distinct_dates = {o['date'] for o in cluster}
        if len(distinct_dates) >= MIN_OCCURRENCES and (
            best_cluster is None or len(distinct_dates) > len(best_cluster)
        ):
            best_cluster = cluster
    if best_cluster is None:
        return None
    return {
        'observed_start_minute': int(median(o['start_minute'] for o in best_cluster)),
        'observed_duration_minutes': int(median(o['duration_seconds'] for o in best_cluster) // 60),
        'observed_weekdays': tuple(range(1, 8)),  # "daily" per MNT-02 -- see Q3
        'occurrence_count': len({o['date'] for o in best_cluster}),
    }
```

## Open Questions

1. **What are the correct MNT-02 similarity tolerances?**
   - What we know: down-transition detection lag is bounded by J3's 300s sweep cadence (a newly-down service is invisible to J4 until J3 catches it — [VERIFIED: `dashboard/app.py:1378`]); recovery-transition detection lag is bounded by J4's 60s cadence once a service is already marked offline. Comparing two independently-sampled down-observations can differ by up to ~300s purely from polling jitter; comparing two observed *durations* can differ by up to ~360s (300s down-side + 60s recovery-side) purely from measurement noise, even for an identical true restart.
   - What's unclear: whether the operator wants a tighter or looser tolerance than the "generous margin over measurement noise" reasoning above produces (15 min start / 10 min duration, per Assumption A1).
   - Recommendation: ship A1's values as named constants (`MAINTENANCE_START_TOLERANCE_SECONDS`, `MAINTENANCE_DURATION_TOLERANCE_SECONDS`) so they are one-line-changeable without a migration, and treat them as provisional pending operator sign-off during `/gsd-discuss-phase` follow-up or plan review.

2. **What lookback window should the suggestion detector use?**
   - What we know: D-12 requires "recent outage evidence," recomputed every editor-open, never frozen. Phase 2 retains full-fidelity events for 90 days (D-03 there).
   - What's unclear: how "recent" should be interpreted numerically.
   - Recommendation: 21 days (3 weeks) as a starting point (Assumption A2) — long enough to plausibly accumulate 3 occurrences of a genuinely-daily pattern without waiting a full month, short enough to satisfy D-12's "actually been doing lately" framing. Trivially adjustable; not schema-bearing.

3. **Should a suppressed transition count as detector evidence (CONTEXT.md's open question 7b)?**
   - What we know: D-12 requires the suggestion to recompute against "recent outage evidence" indefinitely, including noticing if "the pattern stops recurring." A suggestion, once confirmed, becomes a real `maintenance_windows` row — separate from the suggestion-detection table entirely.
   - What's unclear: whether excluding suppressed transitions from evidence would make the detector unable to notice drift (e.g., a confirmed 2:00am window whose real restart time gradually shifts to 2:20am) or a second, unrelated recurring pattern on the same service.
   - Recommendation: **include** suppressed transitions as detector evidence (answering 7b: yes), but suppress the *suggestion output* itself when the detected cluster substantially overlaps an already-enabled window for that port (avoiding a redundant "confirm what you already confirmed" prompt). This keeps the detector able to notice drift and second patterns while not pestering the operator about a pattern they already own.

4. **Should the overrun check be folded into J4, or given its own `WorkerCallback`? And does a suppressed transition's `suppressed_reason` at recovery time freeze the down-event's decision (CONTEXT.md's open question 7a)?**
   - What we know: `WORKER_CALLBACK_INVENTORY` (`dashboard/beacon/worker_main.py:79-94`) is an explicit, declarative registry that supports adding a new job cleanly; J4 already visits every offline service every 60s under the correct authority/transaction machinery.
   - What's unclear: whether the planner/reviewer prioritizes job-health observability isolation (favoring a new job) or minimal surface area (favoring folding into J4).
   - Recommendation: fold into J4 (Assumption A5) as the simpler default; for 7a, freeze `maintenance_grace_until` onto the down-transition's own event row at suppression time (Pattern 2/Assumption A4) rather than re-deriving live window state later — this directly and durably answers "what happens when the operator edits/disables a window mid-outage": **nothing changes for the current down period**, because the boundary was already committed. A *future* down period picks up the edited window on its own next suppression decision.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Unbounded `maintenance_windows` rows per port (resource exhaustion via the existing single mutation route) | Denial of Service | D-05 deliberately allows "arbitrarily many windows"; recommend a generous but finite server-side cap (e.g., 50 windows/service) purely as a resource-exhaustion backstop, consistent with existing bounded-list precedents elsewhere in the codebase (`gaps_limit`, `stream_limit`, `pending_limit` in `read_pipeline_evidence`, all capped at 128 [VERIFIED: `dashboard/beacon/repositories.py:110-114`]). |
| Malformed/adversarial `weekdays`/timezone strings causing an unhandled exception in the worker's transition funnel | Denial of Service (of the monitoring loop itself, which is safety-critical) | Validate `weekdays` as a set of ISO integers 1-7 at write time (Code Example #2); the `coverage()` function must never raise on read-time malformed data already in SQLite — treat unparseable window rows as "not covering" (fail closed to "not suppressed / not in maintenance," which is the safe direction: worst case is a false real-outage alert, never a hidden real outage) rather than letting an exception propagate into `worker_handle_state_transition` and potentially abort the transition-write transaction (which Phase 1's worker-ownership fencing already treats as a hard failure). |
| Suppressed events becoming a hidden audit-evasion channel (an operator or attacker with write access defining an always-on window to suppress all alerts) | Repudiation | Out of scope for this phase's threat model — PROJECT.md's trusted-LAN, single-operator boundary already accepts this class of risk for the *existing* `PUT /api/service-meta` route (an operator with write access can already set `critical=false` to silence alerts); maintenance windows do not introduce a materially new privilege. D-10's write-and-tag (never withhold) design is itself the mitigation that keeps this auditable — every suppressed event remains in `events`, retrievable, unlike a true silent-drop design would be. |
