# Phase 03.1: Code Review Report

**Reviewed:** 2026-08-23T17:40:41Z
**Depth:** standard
**Files Reviewed:** 9
**Status:** issues_found

## Summary

This gap-closure work (plans 11-13 for G-03.1-2) added a one-shot `beacon.migrate`
compose step, a pending-work fast path with bounded contention backoff and a new
`MigrationContended` condition, and converted `dashboard/app.py`'s web connection
sites to context-managed shared-lease ownership. The migration/backoff machinery
in `dashboard/beacon/migrations.py` is well tested and correct in its primary
paths (lock ordering, contention survival, real-error fidelity, idempotent
re-entry). However, the "convert every connection site" effort in `app.py`
missed one call site that reintroduces exactly the class of bug this phase
exists to close: a raw `connect_db()` connection used as a `with` block, which
never closes and therefore never releases its shared maintenance lease. This
site runs in the worker's normal poll loop, not in a one-off code path, so it
leaks on every call for the life of the worker process. This is a BLOCKER.

Two lower-severity issues were also found in `migrations.py`: the contention
budget is not a strict wall-clock ceiling (it can overrun by up to one
`lock_timeout_seconds`), and several connections inside the migration/backup
path rely on the stdlib `sqlite3.Connection` context manager to close them,
which — as this same file explicitly documents elsewhere — it does not do.

## Critical Issues

### CR-01: `worker_process_preview_requests` leaks its shared maintenance lease on every call

**File:** `dashboard/app.py:2231`
**Issue:**

```python
def worker_process_preview_requests(authority):
    ...
    with connect_db(authority.db_path) as conn:
        row = conn.execute(
            "SELECT COALESCE(url, '') AS url FROM service_meta WHERE port=?", (claim.port,)
        ).fetchone()
    url = _safe_service_url(row['url'] if row else '', claim.port)
    ...
```

`connect_db()` returns a `ManagedConnection` (a `sqlite3.Connection` subclass)
whose `close()` is the only thing that releases the shared `flock` maintenance
lease (see `dashboard/beacon/db.py:18-32`). `sqlite3.Connection`'s context
manager protocol only commits/rolls back the current transaction on `__exit__`
— it does **not** close the connection (this is documented stdlib behaviour,
and this very file relies on that fact elsewhere: see the comments in
`dashboard/beacon/migrations.py` at `_recorded_version` and
`_is_empty_database`, which explicitly open a raw connection with `try/finally:
conn.close()` "because the standard library's connection context manager
commits/rolls back but does NOT close"). So `with connect_db(...) as conn:`
here binds a connection whose shared lease is never explicitly released.

This is precisely the class of defect G-03.1-2 (and this whole phase) exists
to close: a held shared maintenance lease starves `exclusive_database_maintenance`,
which is what the migrator needs to run. Unlike a one-off script, this
function is registered as the worker's `process_preview_requests` callback
(`dashboard/worker.py:35`) and is invoked on every poll cycle of the worker's
job loop — so every single poll leaks one more shared lease + open file
descriptor for the remaining lifetime of the worker process, eventually
starving any concurrent/future migration attempt and exhausting file
descriptors.

Every other connection site in `app.py` was correctly converted for this
phase: `database_access()` always closes in a `finally` (`dashboard/beacon/db.py:92-99`),
and `_worker_write_transaction` explicitly binds via `connect_db` and closes
in its own `finally` (`dashboard/app.py:244-257`). This is the one site that
was missed.

This gap is **not** caught by the existing regression suite. The AST-based
gate in `tests/test_module_boundaries.py::test_no_web_handler_binds_a_connection_outside_a_context_manager`
only flags a bare `ast.Assign` whose value is a call to `get_db` — its own
docstring states "it deliberately does not flag every connection binding" and
explicitly carves out `connect_db`-based bindings as out of scope for that
gate. It does not walk `ast.With` nodes at all, so `with connect_db(...) as
conn:` (a different shape, and in a worker function rather than a "web
handler") is invisible to it. `tests/test_api_and_auth.py`'s lease-release
tests (`test_a_failing_request_releases_its_shared_maintenance_lease`,
`test_a_handler_that_raises_for_any_reason_releases_its_lease`) only spy on
`appmod.database_access`, which this call site never uses, so they cannot see
it either.

**Fix:** Use the same managed seam as every other site (`database_access`),
which closes unconditionally in `finally`:

```python
with database_access(authority.db_path) as conn:
    row = conn.execute(
        "SELECT COALESCE(url, '') AS url FROM service_meta WHERE port=?", (claim.port,)
    ).fetchone()
```

(`database_access` accepts either a `Settings` object or a path string, so
`authority.db_path` works unchanged.) Consider also extending the AST gate in
`test_module_boundaries.py` (or adding a companion test alongside the
`test_api_and_auth.py` lease-release tests) to cover worker call sites and the
`with connect_db(...) as conn:` shape, not just bare `get_db()` assignments,
so a regression like this is caught automatically next time.

## Warnings

### WR-01: Migration contention budget is not a strict wall-clock ceiling

**File:** `dashboard/beacon/migrations.py:777-807`
**Issue:** `run_migrations`'s contention retry loop calls
`exclusive_database_maintenance(database, lock_timeout_seconds)` on every
attempt with the full, unreduced `lock_timeout_seconds` (default 30s), and
only checks `contention_deadline` *after* `MaintenanceBusy` is raised:

```python
contention_deadline = contention_started + contention_budget_seconds
while True:
    with ExitStack() as stack:
        try:
            stack.enter_context(
                exclusive_database_maintenance(database, lock_timeout_seconds)
            )
        except MaintenanceBusy:
            elapsed = time.monotonic() - contention_started
            if time.monotonic() >= contention_deadline:
                raise MigrationContended(...)
            attempt += 1
            time.sleep(min(0.1 * (2 ** (attempt - 1)), 2.0))
            continue
        return _apply_pending_migrations(database, marker_path, clock)
```

An attempt that starts just before `contention_deadline` can still block
inside `_acquire_lock` for up to another full `lock_timeout_seconds` before
`MaintenanceBusy` is even raised. With the shipped defaults
(`CONTENTION_BUDGET_SECONDS = 240`, `lock_timeout_seconds` default 30), total
wall-clock time before `MigrationContended` is raised can reach ~270s, not
240s. This contradicts the budget's own documented rationale a few lines above
(`CONTENTION_BUDGET_SECONDS` is sized to "span four worst-case ordinary
connections (4 * 60s = 240s) and twenty-four healthcheck cycles (24 * 10s =
240s)" — a comment that only holds if the budget is a hard ceiling).

**Fix:** Cap each attempt's timeout to the remaining budget:

```python
remaining = max(0.0, contention_deadline - time.monotonic())
try:
    stack.enter_context(
        exclusive_database_maintenance(database, min(lock_timeout_seconds, remaining))
    )
except MaintenanceBusy:
    if time.monotonic() >= contention_deadline:
        raise MigrationContended(...)
    ...
```

### WR-02: Several migration/backup connections rely on `sqlite3`'s context manager to close them, which it does not do

**File:** `dashboard/beacon/migrations.py:609-612`, `dashboard/beacon/migrations.py:714`
**Issue:** `create_verified_backup` and `_apply_pending_migrations` both open
connections with the plain stdlib pattern:

```python
with sqlite3.connect(database, timeout=30) as source:
    with sqlite3.connect(partial_path) as destination:
        source.backup(destination)
with sqlite3.connect('file:{}?mode=ro'.format(partial_path), uri=True) as check:
    integrity = check.execute('PRAGMA integrity_check').fetchone()[0]
```
```python
with sqlite3.connect(database, timeout=30) as conn:
    conn.execute('PRAGMA foreign_keys=ON')
    conn.execute('BEGIN IMMEDIATE')
    migration.apply(conn)
    ...
```

As this same file documents explicitly at `_recorded_version` (line ~633) and
`_is_empty_database` (line ~659) — both of which were hardened with an
explicit `try/finally: conn.close()` specifically because "the standard
library's connection context manager commits/rolls back but does NOT close,
which would leak a handle" — the `with sqlite3.connect(...) as conn:` shape
used here does not close the connection either. Because these run under the
exclusive maintenance flock in the one-shot migrator process, this is lower
risk than CR-01 (no cross-process lease starvation, and the process exits
shortly after), but it is inconsistent with the file's own established,
documented pattern, and leaves closing to CPython refcounting/GC rather than
an explicit boundary. On a failure path where the raised exception's traceback
keeps the enclosing frame alive, the underlying file handle can stay open
longer than the code appears to intend. It is also untested: the only test
that spies on `sqlite3.connect` close behaviour
(`test_the_pending_work_check_closes_every_connection_it_opens`) exercises
only the already-migrated fast path and never reaches `_apply_pending_migrations`
or `create_verified_backup`.

**Fix:** Use the same explicit pattern as `_recorded_version`/`_is_empty_database`
(`conn = sqlite3.connect(...); try: ... finally: conn.close()`), or wrap with
`contextlib.closing()`, for both sites.
