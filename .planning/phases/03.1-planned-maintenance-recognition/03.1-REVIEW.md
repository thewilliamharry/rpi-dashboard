## Warnings

### WR-03: `settings.maintenance_default_grace_minutes` is parsed and validated but never consumed anywhere

**File:** `dashboard/beacon/config.py:61`, `dashboard/beacon/config.py:262-264`, `dashboard/app.js:411`
**Issue:**

`Settings.maintenance_default_grace_minutes` is declared, parsed from the
`MAINTENANCE_DEFAULT_GRACE_MINUTES` environment variable, validated (falls
back to `15` on a non-numeric value), and even has a dedicated unit test
(`tests/test_maintenance_windows.py::SettingsBoundsTests`) — but grep across
the entire application confirms it is never read outside `config.py` and that
one test:

```
$ grep -rn "maintenance_default_grace_minutes" dashboard/ tests/
dashboard/beacon/config.py:61:    maintenance_default_grace_minutes: int = 15
dashboard/beacon/config.py:262:        maintenance_default_grace_minutes=_positive_int(
dashboard/beacon/config.py:263:            source, 'MAINTENANCE_DEFAULT_GRACE_MINUTES', 15,
tests/test_maintenance_windows.py:667:        self.assertEqual(settings.maintenance_default_grace_minutes, 15)
tests/test_maintenance_windows.py:675:        self.assertEqual(settings.maintenance_default_grace_minutes, 15)
```

Meanwhile `dashboard/app.js:411` independently hardcodes its own copy:

```js
const MAINTENANCE_DEFAULT_GRACE_MINUTES = 15;
```

which is what actually pre-fills a new window row's grace field (line 497),
and the confirm/adjust-suggestion actions (lines 632, 645). `/api/config`
(`dashboard/app.py:2435-2442`) does not expose the setting, and
`beacon_web.metadata_response`/`_service_meta_row` do not either. So an
operator who sets `MAINTENANCE_DEFAULT_GRACE_MINUTES=30` in
`docker-compose.yml` (the sibling knob `MAINTENANCE_WINDOWS_PER_PORT_MAX` *is*
correctly wired through to `_validate_maintenance_windows` at
`dashboard/app.py:2765`) will see **no change whatsoever** in the UI's grace
prefill — it stays at `15` regardless, because the client-side literal is the
only value ever actually used. `tests/test_ui_states.py::test_adding_a_row_prefills_the_default_grace_and_focuses_the_start_field`
asserts the literal `'15'` directly, with no dependency on the Settings field,
which is why this drift is not caught by the existing suite.

This is a "does nothing" configuration knob: it looks like a real, documented
per-deployment tunable, but changing it has zero observable effect anywhere in
the running system.

**Fix:** Either wire the value through — expose it via `/api/config` (or fold
it into `metadata_response`'s payload) and have `app.js` read it instead of
hardcoding `MAINTENANCE_DEFAULT_GRACE_MINUTES = 15` — or remove the unused
`Settings` field and its env var entirely so the configuration surface does not
advertise a knob that has no effect.

### WR-04: MNT-02 suggestion clustering does not handle midnight wraparound, so a genuine nightly pattern around midnight will never be detected

**File:** `dashboard/beacon/maintenance.py:255-260`
**Issue:**

`detect_suggestion` clusters observations by raw local start-of-day minute
distance:

```python
for anchor in observations:
    cluster = [
        o for o in observations
        if abs(o['start_minute'] - anchor['start_minute']) * 60 <= start_tolerance_seconds
        and abs(o['duration_seconds'] - anchor['duration_seconds']) <= duration_tolerance_seconds
    ]
```

`start_minute` is minutes-since-local-midnight (`0..1439`, set in
`_observation_from_pair`). This arithmetic has no wraparound handling: an
observation at `23:55` (`start_minute = 1435`) and one at `00:05`
(`start_minute = 5`) are only 10 real minutes apart, but
`abs(1435 - 5) = 1430` minutes (85,800 seconds) — vastly outside the default
900-second (`maintenance_start_tolerance_seconds`) tolerance — so they will
never cluster together, even though a genuine daily restart pattern that
straddles midnight is one of the most common real-world maintenance patterns
(e.g., a nightly cron restart scheduled at `23:58` that sometimes lands a
couple of minutes into the next day due to polling jitter). Three such
occurrences on different dates would silently never produce a suggestion.

This is a real functional gap distinct from `coverage()`'s window-covers-now
check, which is genuinely midnight-safe (it derives full UTC epochs from
date + start_minute + duration and is covered by
`tests/test_maintenance_windows.py::test_a_window_crossing_midnight_covers_after_midnight`).
`detect_suggestion` has no analogous test: every existing suggestion test
(`test_three_similar_daily_outages_produce_a_suggestion`,
`test_start_times_outside_the_tolerance_do_not_cluster`, etc.) uses start
times around `02:00`, so this edge case is untested and unnoticed.

**Fix:** Use a wraparound-aware distance when comparing start minutes, e.g.:

```python
def _minute_distance(a, b):
    diff = abs(a - b) % 1440
    return min(diff, 1440 - diff)
```

and use `_minute_distance(o['start_minute'], anchor['start_minute']) * 60 <=
start_tolerance_seconds` in the cluster filter. Add a test mirroring
`test_three_similar_daily_outages_produce_a_suggestion` but with start times
that straddle midnight (e.g., `23:55`, `00:00`, `00:05`).

### WR-05: `_ATTRIBUTION_MAX_ANCHOR_STEPS` covers roughly 129 days, not "well over a year" as documented, and silently truncates boundary discovery for long-retention deployments

**File:** `dashboard/beacon/maintenance.py:312-345`
**Issue:**

The bound's own comment claims:

```python
# ... (each step covers MAINTENANCE_OCCURRENCE_LOOKBACK_DAYS days, so 64 steps
# covers well over a year).
_ATTRIBUTION_MAX_ANCHOR_STEPS = 64
```

Tracing `_covering_boundaries`'s loop: the first `_local_occurrence_epochs`
call (at `anchor = interval_end`) examines 3 calendar dates (`day_offset` in
`range(MAINTENANCE_OCCURRENCE_LOOKBACK_DAYS + 1)` = `range(3)`). Each
subsequent step moves `anchor` back by `step_seconds = 2 * 86400` and
re-examines another 3-day window that overlaps the previous one by exactly one
day, so each step after the first adds only 2 *new* calendar days of coverage.
Total days covered after `N` steps is `3 + (N - 1) * 2 = 2N + 1`. At the cap
`N = 64`, that is `2*64 + 1 = 129` days — about 4.3 months, not "well over a
year" (365+ days).

`attributed_downtime_seconds` (the caller, via `_covering_boundaries`) is
invoked with `period_seconds = settings.expire_days * 86400` from
`get_current_diagnosis` (`dashboard/beacon/diagnosis.py:628-629`), and
`settings.expire_days` (`EXPIRE_DAYS`) has no enforced upper bound in
`dashboard/beacon/config.py::_positive_int` — any positive integer is
accepted. An operator who configures a multi-month-or-longer retention (a
plausible choice for `EXPIRE_DAYS`, since it also controls how long offline
services and thumbnails are retained) and has a service continuously offline
under a recurring maintenance window for longer than ~129 days will silently
get an incomplete boundary set: `_covering_boundaries` stops discovering
occurrence start/grace-end boundaries beyond the step cap, so
`attributed_downtime_seconds`'s segment-splitting collapses the older portion
of the interval into one large unsplit segment whose covered/uncovered
classification is decided by a single `coverage()` call at that segment's
start instant — even though the window's real periodic occurrences would
toggle covered/uncovered many times across that segment. The result is a
silently inaccurate (not obviously wrong, no error raised)
`maintenance_attribution`/`maintenance_attributed_seconds` figure for the
older part of a very long offline interval. No test exercises an interval
approaching or exceeding this ~129-day bound (`grep` for
`_ATTRIBUTION_MAX_ANCHOR_STEPS`/`ANCHOR_STEPS` in `tests/test_maintenance_windows.py`
returns nothing).

This does not affect default deployments (`EXPIRE_DAYS` defaults to 7, and
`api_services`'s own attribution call is separately bounded to
`CHECK_RETENTION_SECONDS` = 8 days), so it is not a Critical-severity risk, but
the comment's stated guarantee is false and the mechanism silently
under-splits (and thus can mis-attribute) once a deployment's configured
retention exceeds roughly four months.

**Fix:** Either correct the comment to state the true bound (~129 days) and
document that `EXPIRE_DAYS` must stay under that bound for attribution to stay
exact, or raise `_ATTRIBUTION_MAX_ANCHOR_STEPS` to a value that actually
covers a year-plus at 2 new days per step (`~183` steps for 366 days), or add
an explicit cap/validation on `EXPIRE_DAYS` in `config.py` consistent with
whatever bound `_ATTRIBUTION_MAX_ANCHOR_STEPS` is set to. Add a regression
test with a long-spanning offline interval (e.g., 150+ days) and a
still-enabled recurring window near the far end of that interval, asserting
that far-end occurrence is still attributed.
