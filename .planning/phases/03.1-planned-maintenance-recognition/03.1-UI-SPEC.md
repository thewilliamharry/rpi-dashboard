# Phase 03.1 — UI Design Contract

> Visual and interaction contract for operator-managed maintenance windows, suggestion review, the
> derived `In maintenance` state, overrun-outage disclosure, availability attribution, and
> suppressed-event review. Extends the existing main-dashboard service editor (`dashboard/index.html`,
> `dashboard/app.js`, `dashboard/style.css`) and the read-only `/advanced` workspace
> (`dashboard/advanced.html`, `dashboard/advanced.js`, `dashboard/advanced.css`). This contract
> reuses the existing token system, modal system, and status vocabulary rather than introducing a
> parallel one; it does not reopen any decision already locked in `03.1-CONTEXT.md`.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — dependency-free vanilla HTML, CSS, and JavaScript (unchanged) |
| Preset | not applicable |
| Component library | none |
| Icon library | none; concise text labels, native `<time>`/`title` disclosure, and existing status-pip convention |
| Font | existing system sans in light mode (`--font-sans`); existing system monospace in dark mode (`--font-mono`) |

No frontend build step, third-party component package, icon package, or registry is introduced.
Every new element in this phase is built from `dashboard/style.css`'s existing custom properties
and the existing `.meta-*` (service editor modal), `.svc-*` (dashboard card), `.evt-*` (events feed),
and `.service-*`/`.evidence-*` (`/advanced` table and detail) class vocabularies. New class names
extend these families (e.g. `.meta-window-row`, `.svc-maintenance`) rather than starting a new one.

## Spacing Scale

Declared values (multiples of 4), for every NEW element this phase introduces:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Weekday-chip internal padding, badge/pill padding, gap between a status pip and its label |
| sm | 8px | Gap between a window row's fields, gap between weekday chips, evidence-row internal gaps |
| md | 16px | Gap between the window list and the `+ Add window` control, gap between the suggestion card and the confirmed-window list |
| lg | 24px | Not used within the modal (too wide for its 560px column); reserved for `/advanced` detail spacing, matching the existing Phase 3 scale |
| xl | 32px | Not used by this phase's additions |
| 2xl | 48px | Not used by this phase's additions |
| 3xl | 64px | Not used by this phase's additions |

**Exceptions:**
- The existing service-metadata modal's internal field rhythm is `12px` (`.meta-form { gap: 12px }`, `.meta-field { gap: 5px }`), not a multiple of 4. This is a pre-existing, unchanged pattern. All NEW maintenance-window and suggestion markup reuses that exact `12px`/`5px` rhythm for visual consistency with the surrounding form, rather than introducing a competing 4pt rhythm inside the same modal.
- Every interactive control this phase adds (`+ Add window`, `Remove`/`Confirm remove`, weekday chips, `Confirm`/`Adjust` on the suggestion card, the events reveal control) keeps a minimum 44px by 44px hit target at narrow (`< 720px`) viewport widths, matching the existing site-wide narrow-action rule (`.btn-scan`, `.svc-edit`, `.meta-btn` all already do this at `< 720px`).

## Layout and Responsive Contract

### Focal points

Declared explicitly so hierarchy is not left to be inferred from treatment alone:

- **Service editor, maintenance section** — the confirmed-window list is the focal point. The
  suggestion card, when present, takes deliberate *secondary* weight (dashed outline, muted text)
  despite sitting above it: it is a proposal, not the operator's own configuration. `+ Add window`
  is tertiary (ghost treatment) so `Save` remains the section's only primary commit action.
- **Dashboard service card** — the status pip and word are the focal point of the `In maintenance`
  treatment. Everything else on the card is unchanged from the healthy card, so the status change
  is the only thing that moves.
- **`/advanced` services row** — the `Status` column value carries the focal weight; the new
  evidence rows are secondary detail, appended after the existing diagnostic rows and revealed only
  on expansion.
- **Events panel** — when suppressed entries exist, the reveal control is the focal element of the
  panel head, because its count is the only signal that the feed is not showing everything.
- **Overrun outage entry** — takes the strongest weight available in the feed. It is the one place
  in this phase where maintenance context must not reduce visual severity at all.

### Service metadata editor (main dashboard modal)

- The existing `.meta-modal-window` (`width: min(560px, 100%)`) gains a bounded height once
  maintenance content is added: `max-height: min(86vh, 720px)`, with `.meta-form` scrolling
  internally (`overflow-y: auto`). The modal header (`.meta-modal-head`) stays pinned above the
  scrolling form; `.meta-actions` (Cancel/Save) remains the last element inside the scrollable
  form, exactly as today — it is not pinned separately, matching existing behavior.
- A new, always-visible (non-collapsed) section titled `Maintenance windows` is placed after the
  existing `Tags` field and before the existing `Advanced` `<details>` section. It is not
  collapsed by default — maintenance is core functionality in this phase, not a rarely-used
  advanced toggle.
- Inside that section, top to bottom: the suggestion card (only when a suggestion exists), the
  confirmed-window list (or its empty state), then the `+ Add window` control.
- Each window row lays out its five controls (Start, Duration, Weekdays, Grace, Enabled) in a
  responsive grid: two columns down to `~420px` inner width (matches the modal's own narrow
  breakpoint), collapsing to one column below that. `Remove`/`Confirm remove` sits at the end of
  the row on its own line at the narrowest width.
- The window list becomes internally scrollable past 4 visible rows (`max-height: ~280px;
  overflow-y: auto`), consistent with the existing `.evidence-list` scroll pattern used on
  `/advanced`. This never blocks the list from growing to arbitrarily many windows (D-05).
- Weekday chips (`Mo Tu We Th Fr Sa Su`) wrap onto a second line rather than shrinking below a
  legible/tappable size at narrow widths.

### Dashboard service card

- The `In maintenance` treatment does not add a new grid position; it replaces only the status
  pip/text and its disclosure tooltip within the existing `.svc-status-row`. Card dimensions,
  thumbnail, and layout are unchanged from the healthy/online card.
- The status word `MAINTENANCE` (11 characters) fits the existing `.svc-status-row` flex layout
  at all supported widths without wrapping onto a second line; `.svc-status-row` gains
  `flex-wrap: wrap` as a defensive rule so an unusually narrow viewport wraps the status word
  below the pip rather than clipping it (this rule is additive and does not change today's
  `ONLINE`/`OFFLINE` rendering, which already fits).

### `/advanced` services table and Overview

- No new column is added to the fixed six-column services table
  (`Name + port | Status | Latency / failure class | State duration | Criticality | Freshness`).
  `maintenance` is a new possible VALUE of the existing `Status` column, not a new column —
  preserving Phase 3's fixed-column contract.
- The Services row's expanded detail (`.service-detail-evidence`) gains up to three new evidence
  rows (Maintenance, Down since / Raised at when an overrun is active, Maintenance attribution),
  appended after the existing `Collection-gap evidence` row, using the identical
  `.evidence-row` two-column grid and `overflow-wrap: anywhere` already in place — no new layout
  primitive.
- Per D-07, confirmed active maintenance is never added to the Overview `Active exceptions` list
  or its count; it exists only inside the Services section and its row detail.

### Events panel (main dashboard)

- The reveal control sits as a new first row of `.events-panel` (or immediately above it) when
  and only when at least one suppressed entry exists for the currently loaded event window; it
  occupies its own full-width row, not squeezed into the existing `.sh` section-head row.
- Revealed suppressed rows render inline in chronological order with the rest of the feed (not a
  separate sub-list), each carrying the small `Expected` pill described in the Interaction
  Contract, so a suppressed night reads as a taller feed with visibly-tagged entries rather than
  a separate, easy-to-miss panel.

## Interaction Contract

### Maintenance window editor

- **Fields per window:** Start (`<input type="time">`, local wall-clock literal per D-02), Duration
  in minutes (`<input type="number" min="1">`), Weekdays (seven toggle chips, `Mo`–`Su`, each with
  a full-day `aria-label` and `aria-pressed`), Grace period in minutes (`<input type="number"
  min="0">`, prefilled with a default of **15 minutes**, always visible and always required per
  D-04 — never hidden behind a details/summary), and Enabled (checkbox, default checked for a
  newly added window).
- Selected weekday chips use the accent (cyan) treatment already established for the existing
  `.meta-checkbox input { accent-color: var(--accent) }` pattern — a filled/accent border — so
  selection state visually matches how every other "on" control already reads in this modal.
- **Add:** `+ Add window` (ghost-button treatment, matching `.meta-btn-ghost` — not the primary
  accent button, since Save remains the single primary commit action) appends a new row with the
  default grace prefilled and all other fields empty/unselected; the new row receives initial
  focus on its Start field.
- **Remove:** each row's `Remove` control is a two-step inline confirm — the first click relabels
  the same button to `Confirm remove` for one further interaction; clicking anywhere else, or
  clicking `Confirm remove` a second time inadvertently after the window elapses, is not a
  concern since the button always requires an explicit second click. Nothing is deleted from
  storage until the operator subsequently clicks the modal's existing `Save`. No native
  `window.confirm()` dialog is used (matches the dependency-free, testable, accessible pattern
  already used everywhere else in this codebase).
- **Disable:** unchecking `Enabled` keeps the row and its fields visible (dimmed to the muted
  text color, not hidden), so a disabled window remains inspectable and easy to re-enable.
- **Overlap:** the editor does NOT detect or flag overlapping windows client-side. Per D-05,
  overlap resolution (longest grace wins) is a server-side evaluation rule with no operator
  decision attached to it in this phase; no overlap warning is in scope.
- **Validation:** all validation errors reuse the existing single shared `#meta-error` region
  (no new inline-per-field error UI is introduced), each prefixed by which window failed. Exact
  copy is in the Copywriting Contract. Save remains disabled/blocked while any window fails
  validation, matching the existing modal's save-blocking behavior on other field errors.

### Suggestion card

- Rendered only when the server returns an active suggestion for this service (D-11); otherwise
  no suggestion UI is rendered at all — this is an absence, not an empty-state message.
- Visually distinct from every confirmed window: a dashed `1px var(--border)` outline (not a
  solid border, not a color), `var(--muted)` text throughout, and the label `Suggested window`
  reusing the existing `.meta-label` treatment. It never uses the Maintenance (`--accent3`) or
  Warning (`--accent2`) colors — those are reserved for the confirmed-window derived states.
- Body copy states the observed evidence in plain language (see Copywriting Contract) — start
  time, duration, and weekdays the detector observed, never a raw internal score or threshold
  value.
- Two actions only, per D-11 ("confirm and edit paths"): `Confirm` (primary, `.meta-btn-primary`
  treatment — the one exception where this section uses the accent commit-button color, since it
  is this section's own primary action) copies the suggested values into a new row appended to
  the confirmed-window list, still unsaved until `Save`; `Adjust` opens that same new row already
  populated, with focus moved to its Start field so the operator edits before it is added. No
  `Dismiss`/`Not now` control is offered — per D-12 the suggestion recomputes against recent
  evidence every time the editor opens, so closing the modal without acting is itself "not now,"
  and a permanent-dismiss affordance would contradict D-12's persistent-recompute design.

### Dashboard card `In maintenance` state

- The card's structural class is `svc-card svc-maintenance` (a new class), never `svc-card
  offline`, whenever the derived condition (`offline AND covered by an active enabled window`) is
  true. This is the mechanism that keeps the calm treatment: none of the existing
  `.svc-card.offline` rules (card opacity 0.5/saturate 0.2 in dark, opacity 0.4 in light,
  thumbnail grayscale/opacity, offline-badge) apply, because those selectors target `.offline`
  specifically and `.svc-maintenance` does not carry that class. The underlying `is_online` value
  stays `false` for every non-visual purpose (aria labeling, sorting, data).
- Status pip and text: pip and text both use the Maintenance color (`--accent3`); text reads
  `MAINTENANCE` (see Copywriting Contract for exact casing/wording). The pip does not pulse or
  glow (that treatment is reserved for `ONLINE`'s pip in dark mode) — it stays static, reinforcing
  "calm, not alarming."
- The existing `svc-since` line is unchanged in content (`down since {relative time}`) — the true
  fact is preserved, never replaced or hidden — but the row additionally carries a `title`
  attribute on the status span disclosing the derivation on inspection, following the exact
  pattern already used for the TLS-unverified badge (`tls.title = '...'`): `"Offline and covered
  by a confirmed maintenance window until {window end + grace, local time}. Downtime is still
  counted in the 7-day availability figure."`
- **Automatic reversion:** the moment the current time passes the window's end time plus its
  grace period while the service is still offline, the derived condition becomes false on the
  very next poll and the card reverts to the ordinary `svc-card offline` treatment (red,
  faded, `OFFLINE`) with no special handling required — this is a natural consequence of
  re-evaluating the same derivation, not a separate state machine. This is what keeps an overrun
  from silently staying "calm."

### `/advanced` services table and detail

- `serviceAvailability()`'s vocabulary gains one new value, `maintenance`, rendered exactly like
  its siblings: `● maintenance` in the Status column, using the Maintenance color instead of
  green/red/muted.
- The expanded row detail gains, appended after the existing evidence rows:
  - `Maintenance` — when currently in maintenance: the covering window's schedule and grace, and
    when it ends; when not: `No active maintenance window`. Always rendered, never a blank cell
    (matches Phase 3's no-blank-cell discipline).
  - `Down since / Raised at` — rendered ONLY while an overrun outage is open for this service:
    two separate lines, `Down since {exact timestamp}` and `Raised at {exact timestamp}`, never
    merged into one string (D-08 requires both independently legible).
  - `Maintenance attribution` — always rendered (see Availability below).
- Because `/advanced` is strictly read-only (D-01), none of this new evidence is interactive; the
  Services detail simply states, in plain text, where windows are managed: `"Maintenance windows
  are managed from the main dashboard's service editor."` — no link that implies an action is
  performed from `/advanced`.

### Availability attribution

- The existing headline uptime figure (`svc-uptime-pct` on the dashboard card; the equivalent
  time-weighted figure surfaced via `/advanced`) is never recalculated or replaced. Per D-09, only
  one number is ever shown at that weight.
- The `Maintenance attribution` evidence row (in the `/advanced` Services detail) states the
  portion of the SAME period's downtime that occurred during confirmed maintenance, in plain
  language (see Copywriting Contract). When that portion is zero, the row still renders,
  explicitly stating there was none — never omitted.
- No second, adjusted, "excluding maintenance" percentage is rendered anywhere in this phase, at
  any weight, on any surface.

### Events feed suppression and reveal

- Suppressed (tagged) entries are always retained and always counted; they are filtered at
  render time only. The reveal control is not rendered at all when the current feed contains zero
  suppressed entries (an absence, not an empty-state message, matching the suggestion-card
  pattern above).
- When at least one suppressed entry exists, the control defaults to collapsed and states the
  hidden count in its own label (D-10's hard requirement) — see Copywriting Contract for exact
  singular/plural copy. Activating it toggles to the revealed state and its own label flips to a
  `Hide` action; state is not persisted across a page reload (matches existing dashboard behavior
  of not persisting any events-panel UI state).
- Each revealed suppressed row keeps its existing `.evt-row` structure and event-specific color
  (e.g. a suppressed recovery keeps the green `evt-up` treatment) but gains one new inline pill,
  `Expected`, in the Maintenance color (`--accent3`), positioned after `.evt-title`, so a
  suppressed entry is never visually indistinguishable from a normal one even once revealed.
- The overrun-outage event (MNT-04) is a normal, fully visible feed entry at all times — it is
  never suppressed and never carries the `Expected` pill. It uses the exact same red `evt-down`
  treatment as any other genuine outage, unmuted, because it must read as a truthful, undiminished
  fault (see Copywriting Contract for its distinct title copy, which still communicates that it
  began during a maintenance window without softening its severity).

## UI Considerations

Resolved via the UI-consideration probe after checker approval. Element kinds were narrowed from
the classifier's maximal proposal (every kind on every element) to the kinds each surface actually
has — no surface in this phase is `media` or `nav`, and the dashboard status state, the overrun
presentation, and the availability attribution row are read-only text with no inputs and no item
collection. Narrowing was confirmed with the operator, not applied silently.

**40 considerations resolved: 40 explicit, 0 backstop, 0 unresolved.**

### Maintenance window editor — form, list-collection, interactive-control

|----------|--------|------------|

### Events feed suppression reveal — list-collection, interactive-control

| Category | Status | Resolution |
|----------|--------|------------|
