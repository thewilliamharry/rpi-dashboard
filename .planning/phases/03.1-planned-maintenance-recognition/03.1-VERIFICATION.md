### Gaps Summary

**The phase's core maintenance-recognition mechanism (MNT-01 through MNT-04) is intact and
unaffected by this round's changes** — confirmed by re-running the maintenance/uptime regression
subset (120 passed, matching the prior round exactly) and by the orchestrator-supplied full-suite
result (528 passed / 456 subtests, exit 0).

**G-03.1-2 is three-quarters closed, not fully closed.** Plans 03.1-11 and 03.1-12 close the
startup-ordering and contention-backoff defects thoroughly and are backed by 16 new, individually
re-run, passing regressions that reproduce the Pi's exact failure shapes (a lock-timeout death, a
displaced real error, an unnecessary reboot-path escalation, a version read racing a live writer).
Plan 03.1-13 correctly converts 24 of 25 enumerated `dashboard/app.py` connection sites to the
`database_access` context manager, confirmed by an independent count (`grep -n "conn.close()"`
finds exactly one remaining occurrence, at the deliberately out-of-scope
`_worker_write_transaction`).

But one site sharing the identical defect shape was never enumerated and was never converted:
`worker_process_preview_requests` at `dashboard/app.py:2231`. It opens its connection via
`with connect_db(authority.db_path) as conn:` — a different shape from the 24 enumerated
`with _db_lock: conn = get_db()` sites, and one the plan's own read list and structural gate did
not anticipate. Because `sqlite3.Connection`'s stdlib context-manager protocol commits or rolls
back on `__exit__` but never calls `close()`, and because `ManagedConnection.close()` — the only
method that unlocks the shared `flock` (`dashboard/beacon/db.py:24-32`) — is therefore never
invoked at the `with` block's boundary, this site holds its shared maintenance lease for the
entire remainder of the function's execution (through the browser-based preview capture,
`_refresh_service_preview`) rather than releasing it at the point the read completes. I confirmed
this empirically: after exiting an equivalent `with connect_db(...) as conn:` block, `conn` is
still open and usable, and its `_maintenance_handle` is still attached.

One nuance worth recording precisely, because it changes the practical severity without changing
the verdict: I also confirmed that once every reference to `conn` (and its attached lock-file
handle) is dropped — e.g. the enclosing function returns normally with no exception in flight —
CPython's ordinary refcounting garbage-collects the connection and lock-file objects immediately,
and closing the underlying lock file descriptor releases the OS-level `flock` automatically
(POSIX `flock` releases on file-descriptor close, independent of whether Python's own `close()`
method ran). So this is not necessarily an unbounded, ever-accumulating leak on the ordinary
success path the way "one more handle per poll, forever" would read in isolation — but it is not
the structural, close()-guaranteed, single-boundary release the plan's must-have claims either: the
lease is held far longer than intended (through the whole remaining function body, not released at
the read), and any path that keeps a reference alive longer — a retained exception traceback, a
logged/stored error object, a future edit to this function that stores `conn` somewhere, or simply
a slow `_refresh_service_preview` call stacking up with concurrent polls — extends or compounds the
window during which this specific worker-callback holds the lease. Because this function runs
inside the actual worker process (`dashboard/worker.py:35`) on every poll cycle that has a claimed
preview request, it is exactly the mechanism (an ordinary connection holding a shared lease longer
than necessary) that starved the migrator on the Pi, reintroduced at one call site the gap-closure
work was specifically trying to eliminate everywhere.

The new structural gate (`test_no_web_handler_binds_a_connection_outside_a_context_manager`) does
not catch this: by design (per its own docstring and confirmed by reading its AST walk) it only
flags a bare `ast.Assign` whose value is a call to `get_db`; it does not walk `ast.With` nodes and
does not consider `connect_db` at all. The new lease-release regressions in
`tests/test_api_and_auth.py` spy on `appmod.database_access`, which this site never calls, so they
cannot see it either. This matches 03.1-REVIEW.md's CR-01 finding exactly, and I independently
reproduced it at the source and runtime level rather than taking the review at face value.

**This gap is pre-existing, not introduced by this round.** `git show b16672b:dashboard/app.py`
(the commit at the base of this gap-closure round, before plans 11-13) shows the identical
`with connect_db(authority.db_path) as conn:` line at the same position, unchanged. Plans 11-13 did
not create this defect; they closed the surrounding defects thoroughly enough that this one now
stands out as the sole remaining piece of G-03.1-2's third defect, and the plan's own must-have
language ("Every connection the web process opens is owned by a context manager... the web and
legacy-worker surface") claims coverage this site falsifies.

**Recommended fix (small, scoped, low risk):** convert line 2231 to
`with database_access(authority.db_path) as conn:` (the seam already accepts a path string, and
`authority.db_path` is exactly that), matching every other converted site, and extend either the
AST gate or the `test_api_and_auth.py` lease-release regressions to also cover the
`with connect_db(...) as conn:` shape and worker-callback call sites, so this defect class cannot
silently reopen at a future site the same way it did here.
