# Phase 03.1: Planned Maintenance Recognition Verification Report

**Phase Goal:** The operator can confirm or define expected recurring service restarts so Beacon
suppresses routine transition noise without hiding failed probes, reducing uptime impact, or
overlooking an overrun.

**Verified:** 2026-08-22
**Status:** complete
**Method:** Direct code inspection of the merged `main` branch (not SUMMARY.md claims), full test
suite execution (`uv run --project dashboard python -m pytest -q`: 506 passed, 454 subtests passed,
0 failed, matching the claimed execution state), and a scoped re-run of
`tests/test_maintenance_windows.py` + `tests/test_uptime_integration.py::UptimeIntegrationTests`
(120 passed) with test bodies read for substance, not just pass/fail counts.

## Goal Achievement — Roadmap Success Criteria

### 1. Operator can add, edit, disable, and remove a recurring per-service local-time window with an explicit grace period

**Status: ✓ VERIFIED**

- `PUT /api/service-meta/<int:port>` (`dashboard/app.py:2763`) accepts an optional
  `maintenance_windows` array. No new mutation route was added — the CRUD surface is exactly the
  pre-existing operator-write endpoint (D-01).
- `_validate_maintenance_windows` (`dashboard/app.py:555`) enforces server-side bounds on every
  field — `start_minute` (0-1439), `duration_minutes` (1..10080), `weekdays` (1..7, non-empty,
  deduplicated), and **`grace_minutes`, which is required** (`type(grace_minutes) is not int or
  grace_minutes < 0` rejects a missing/negative grace with `Window {n}: Grace period is required
  and must be 0 minutes or more.`) — before any DB connection opens.
- `upsert_maintenance_windows` (`dashboard/beacon/repositories.py:789`) implements replace
  semantics: `DELETE FROM maintenance_windows WHERE port=?` then re-insert, sharing the caller's
  connection/transaction/lock with `upsert_service_metadata` and one final `conn.commit()`
  (`dashboard/app.py:2867-2872`) — concurrent readers see either the full old or full new set, never
  a partial one.
- Several windows per service are supported: `maintenance_windows` is a list keyed by `port`, no
  uniqueness constraint collapses two windows on the same port (migration 9,
  `dashboard/beacon/migrations.py:507`).
- Empty-array vs. omitted-key semantics are exactly as specified: `'maintenance_windows' in payload`
  gates whether `upsert_maintenance_windows` runs at all (`dashboard/app.py:2800-2806, 2867-2870`) —
  an omitted key never touches the table; an empty array deletes every row for that port via the
  same replace path.
- Confirmed by tests: `WindowCrudApiTests`, `WindowValidationTests`, `WindowConcurrencyTests`,
  `test_repeating_an_identical_put_is_idempotent` (`tests/test_maintenance_windows.py:857`), all
  passing.
- Migration 9 (`Migration(9, 'planned_maintenance', True, _migration_9_planned_maintenance)`) is
  additive-only (`CREATE TABLE IF NOT EXISTS`, `_add_column`), runs `schema_changing=True` (behind
  the verified-backup path), and `test_migration_nine_is_idempotent` passes.

### 2. After three similar daily restart outages, Beacon offers an INACTIVE suggested window requiring confirmation or adjustment before it changes event or alert behavior

**Status: ✓ VERIFIED**

- `detect_suggestion` (`dashboard/beacon/maintenance.py:218`) clusters down/recovered pairs by
  distinct calendar date and requires `MAINTENANCE_MIN_OCCURRENCES = 3` (line 28) before returning
  anything.
- The suggestion is never written to storage: it is computed at read time inside
  `metadata_response` (`dashboard/beacon/web.py:46-75`), attached to the `GET
  /api/service-meta/<port>` payload only, and `suggestion_overlaps_enabled_window` withholds it when
  an enabled window already covers it.
- Confirmed genuinely inert in the browser: `confirmMaintenanceSuggestion` and
  `adjustMaintenanceSuggestion` (`dashboard/app.js:626-651`) both call `addMaintenanceWindowRow`
  (an in-DOM row append) and set `$('meta-suggestion').hidden = true` — **neither makes a network
  request**. Nothing reaches the server until the operator clicks the modal's pre-existing Save
  (`submitMetaEditor`, the same `PUT` path verified above).
- No permanent dismiss control exists (`grep -n "Dismiss|Not now" dashboard/app.js
  dashboard/index.html` → no matches), matching D-11/D-12's "recomputation replaces dismissal"
  design.
- Confirmed by tests: `DetectorTests`, `SuggestionOverlapTests`, `SuggestionLifecycleTests`,
  `SuggestionEvidenceTests`, all passing, including
  `test_a_pattern_already_covered_by_an_enabled_window_is_withheld` and
  `test_a_second_unrelated_pattern_is_still_offered`.

### 3. Confirmed maintenance suppresses ONLY expected down/recovered event entries and transition alerts; every probe remains stored and planned downtime still lowers availability

**Status: ✓ VERIFIED** — this is the phase's central honesty claim, checked against all four sub-clauses in the brief.

**(a) Suppressed events are still INSERTed carrying a tag, never withheld at write time.**
`_maintenance_suppression_decision` (`dashboard/app.py:928-950`) and `worker_handle_state_transition`
(`dashboard/app.py:1886-1913`) always call `_insert_event(... event_type='state_change',
suppressed_reason=suppressed_reason, ...)` inside the write transaction — the insert happens
unconditionally; only the *subsequent alert dispatch* is skipped when `suppressed_reason is not
None`. Proven end-to-end (not mocked at the DB boundary) by
`test_a_covered_down_transition_is_written_tagged_and_unalerted`
(`tests/test_maintenance_windows.py:1160`): asserts exactly one `state_change` row exists with
`suppressed_reason == 'maintenance'` and zero `alert_sent`/`alert_failed` rows, while
`worker_send_transition_alert` is mocked only to assert it was never called (the DB write itself is
real). The matching recovery inherits its tag from the down period's own opening row rather than
re-deriving live coverage — verified by
`test_a_recovery_whose_down_period_was_not_suppressed_is_not_tagged` (line 1221), which installs a
window *after* the down transition and confirms the recovery is still unsuppressed (D-08
non-inference).

**(b) No failed probe is discarded.** The down-only poll loop always executes `INSERT OR REPLACE
INTO service_checks` (`dashboard/app.py:1604-1608`) regardless of maintenance/overrun status — the
suppression/overrun logic (lines 1570-1603) is additive code inside the same transaction, never a
branch that skips the checks insert. Confirmed by
`test_every_failed_probe_is_still_stored` (`tests/test_maintenance_windows.py:2141`), which asserts
the exact count of pre-seeded checks survives a poll cycle.

**(c) `_uptime_summary`/`calc_uptime_pct`/`build_uptime_buckets` and the uptime path in
`dashboard/beacon/monitoring.py` are unmodified; the headline figure is never adjusted.**
`git log --oneline -- dashboard/beacon/monitoring.py` shows the file's only commit is
`ab0f5b5 feat(01-03)` from Phase 1 — **zero commits from this phase touch it**. Cross-referencing
every phase-03.1 commit's changed-file list (`git log --name-only` filtered to `(feat|test|fix)(03.1`
commits) confirms `dashboard/beacon/monitoring.py` never appears. `_uptime_summary` in `app.py`
(line 1785) is an unchanged thin delegator to `beacon_monitoring.uptime_summary`. Attribution
(`attributed_downtime_seconds`, `dashboard/beacon/maintenance.py:348`) is called as a **second,
additive** read at `dashboard/app.py:2678` — outside, never inside, the uptime computation — and
`test_availability_is_unchanged_by_an_overrun` (`tests/test_maintenance_windows.py:1627`) plus
`UptimeIntegrationTests` (both passing) regression-pin this.

**(d) No "excluding maintenance" percentage exists anywhere.** `grep -rniE
"excluding.?maintenance|adjusted.?(uptime|availability)|maintenance.?adjusted"` across
`dashboard/` and `tests/` returns zero matches. `test_the_payload_contains_no_second_availability_percentage`
(`tests/test_maintenance_windows.py:2130`) and the UI-SPEC-derived prohibition (D-09: "no second
competing percentage is ever rendered at any weight on any surface") are both honored — `api_services`
publishes exactly one `uptime_pct` plus a separately-labelled `maintenance_attributed_seconds`, never
a second percentage.

### 4. A service still down after window + grace produces ONE truthful outage event and alert, while the dashboard distinguishes active maintenance from an unresolved failure

**Status: ✓ VERIFIED**

- **Overrun idempotency (exactly once per down period).** `overrun_already_raised`/
  `mark_overrun_raised` (`dashboard/beacon/repositories.py:852-876`) guard the raise inside the same
  write transaction that updates `services`; the bookkeeping column
  `overrun_raised_ts` is cleared by the very `UPDATE services ... overrun_raised_ts=CASE WHEN
  is_online != 1 THEN NULL ELSE overrun_raised_ts END` that already resets `state_since` on a
  genuine transition (`dashboard/app.py:1548-1568`). Proven by
  `test_repeated_polls_raise_exactly_one_overrun` (4 polls at/after the boundary → exactly 1 row) and
  `test_a_second_down_period_raises_its_own_overrun` (a second, later down period on the same port
  raises its own independent overrun — 2 rows total), both passing.
- **Boundary-second precision.** `test_no_overrun_is_raised_one_second_before_the_boundary` confirms
  the half-open `[start, end+grace)` boundary is exact.
- **Never derived from live window edits mid-outage.** `test_editing_the_window_mid_outage_does_not_move_the_boundary`
  edits the covering window's grace to 500 minutes mid-outage and confirms the overrun still fires at
  the original frozen boundary (`opening['maintenance_grace_until']`, read once at suppression time,
  never re-derived).
- **True down-since + explicit raised-at, both durable.** The overrun event carries `down_since_ts`
  (from `services.state_since`, the true fact) and its own `ts` (the raise instant) as separate
  columns (`dashboard/app.py:1582-1591`); `dashboard/app.js:308-312` renders them as two permanently
  separate `<span>` lines, never merged into one truncatable string (D-08), confirmed by
  `test_the_overrun_event_carries_both_timestamps_separately`.
- **Never suppressed or softened.** `isOverrunEvent`/`isSuppressedEvent`
  (`dashboard/app.js:326-334`) explicitly exclude the overrun event type from the suppressed
  partition "unconditionally, regardless of any other field it carries" — confirmed by
  `test_the_overrun_event_is_never_tagged_as_suppressed`. The alert dispatch
  (`_dispatch_overrun_alert`, `dashboard/app.py:1753`) reuses the real alert sender, outside the
  write transaction, gated only by the existing cooldown/critical-only filters — no parallel/softer
  mechanism.
- **Dashboard distinguishes active maintenance from unresolved failure.** `buildServiceCard`
  (`dashboard/app.js:214`) assigns `card.className = maintenance ? 'svc-card svc-maintenance' :
  'svc-card' + (online ? '' : ' offline')` — a maintenance card **never** receives the `offline`
  class, so none of `.svc-card.offline`'s rules (`opacity: 0.5`, `filter: saturate(0.2)` in dark
  theme, `opacity: 0.4` in light — `dashboard/style.css:402,421,585,586`) apply; it keeps the
  default calm card treatment by construction. The status word/pip use `.svc-maintenance-status`
  with `var(--accent3)` (an existing purple token, distinct from the green/red online/offline
  colours, never a new CSS custom property), and a `title` attribute discloses "Offline and covered
  by a confirmed maintenance window until {end}. Downtime is still counted in the 7-day availability
  figure." — the true `down since` line is unchanged. `is_online` in the underlying data stays `0`
  for maintenance-derived services for every non-visual purpose (sorting, accessible labelling)
  since the display-only reclassification happens in `serviceCardAvailability`, a rendering helper,
  never on the stored/served `is_online` field itself.
