<objective>
Add the one net-new server capability this phase needs: a parameterised, bounded, validated
`GET /api/events/history` that returns incidents as grouped down-to-recovered episodes plus the
flat transitions that compose them, filtered by service, criticality, event type, and time.

Purpose: the existing `api_events` route takes only `limit` and `since` — it cannot express a
range-and-filter contract, and it does no grouping. D-12 requires grouping to be a *view* over
durable rows computed where the server already classifies (the `beacon/diagnosis.py` split), and
D-14 requires an overrun episode to carry both durable timestamps rather than one.
Output: `dashboard/beacon/incidents.py`; the `GET /api/events/history` route; a new
`tests/test_incidents_api.py`.
</objective>

<assumption_delta_decision>
The `assumption-delta scan` fired `kind: chosen` on this phase ("Operator can **choose** shared
ranges … or a validated **custom** range"). A value that was previously derived and constant is
now operator-chosen and parameterised, so the identity question is: what noun is primary now?

- **Primary noun:** the **investigation range** — a validated half-open `{start_ts, end_ts}`
  interval represented by `beacon_telemetry.HistoricalRange`. "Now" is no longer the implicit
  anchor of a historical read; it is one particular range among many.
- **Decision: `promote`.** The new incidents read takes `HistoricalRange` as its primary
  identity, exactly as `/api/telemetry/history` already does. It does **not** add a
  range contract *alongside* the existing `api_events` `limit`/`since` pair, and `api_events`
  is left untouched for its existing main-dashboard consumer. Adding alongside would leave two
  competing notions of "which events" in one file, and the newer one would be the only one that
  can express what this phase's UI needs — the exact asymmetry the promote rule exists to stop.
- **Invariant test (accepted, implemented in Task 3):** every incidents read round-trips through
  `HistoricalRange`, proven by asserting the new route rejects an inverted span and a
  91-day span with the *same* error strings `/api/telemetry/history` returns. That test goes red
  the instant a future change reintroduces bespoke bounds logic on this route.
</assumption_delta_decision>

`read_events_in_range(conn, *, start_ts, end_ts, port=None, event_type=None, criticality=None,
maintenance='include', limit=INCIDENT_ROW_BUDGET)`:
- Builds a `WHERE e.ts >= ? AND e.ts < ?` half-open predicate — a row at exactly `start_ts` is
  in, a row at exactly `end_ts` is out, matching `HistoricalRange`'s half-open definition.
- Appends predicates only for filters that are present, and only after each value has been
  checked against its allowlist (`event_type in EVENT_TYPES`, `criticality in
  CRITICALITY_VALUES`, `maintenance in MAINTENANCE_MODES`, `port` an int in 1..65535). Every
  value reaches SQLite as a bound `?` parameter; no filter value is ever concatenated into the
  statement text. An out-of-allowlist value raises `ValueError` with a message naming the
  parameter — reject, never coerce.
- `criticality='critical'` maps to `COALESCE(m.critical, 0) = 1`; `standard` to `= 0`.
- `maintenance='exclude'` maps to `e.suppressed_reason IS NULL`; `only` to
  `e.suppressed_reason IS NOT NULL`; `include` adds no predicate.
- Orders `e.ts ASC, e.id ASC` for grouping, and selects `LIMIT ? ` with `limit + 1` so the
  caller can detect truncation without a second COUNT query. Returns
  `(rows, truncated)` where `truncated` is True when `limit + 1` rows came back, and `rows` is
  trimmed back to `limit`.

`read_open_episode_anchors(conn, *, start_ts, ports)`:
- For each port in `ports`, returns at most one row: the most recent `state_change` with
  `online = 0` strictly before `start_ts`. This is what makes an outage that *began* before the
  selected range group correctly instead of appearing as a recovery with no cause. It reads
  durable rows only and invents nothing. Uses `idx_events_port_ts`.

`group_episodes(rows)`:
- Consumes `state_change` rows for one port ordered `ts ASC` and returns episode dicts:
  `port`, `service_name`, `critical`, `down_ts` (`down_since_ts` when present, else the row's
  `ts` — the true down-since 03.1 D-08 stored), `raised_ts` (the row's own `ts`),
  `recovered_ts`, `open`, `duration_seconds`, `failure_class` (the `error_class` of the opening
  row), `suppressed_reason`, `maintenance_grace_until`, `transitions` (the raw rows composing
  the episode), and the keys `split_overrun_span` returns.
- A row with `online = 0` opens an episode; a row with `online = 1` closes the currently open
  one. A closing row with nothing open emits no episode. A still-open episode is returned with
  `recovered_ts = None`, `duration_seconds = None`, `open = True` — never closed against
  `end_ts` or the current time. Rows whose `event_type` is not `state_change` never participate
  in grouping.

`split_overrun_span(down_ts, recovered_ts, grace_until)`:
- Returns `{overrun, grace_seconds, fault_seconds}`. With no `grace_until`, the whole span is
  fault and `overrun` is False. With a `grace_until`, `grace_seconds` is the portion of the span
  at or before it and `fault_seconds` the portion after; `overrun` is True only when
  `fault_seconds` is greater than zero. When `recovered_ts` is None, `fault_seconds` is None and
  `grace_seconds` is None — an unresolved overrun is not measured against a clock the operator
  did not observe (Research Pitfall 4).

`classify_flapping(episodes)`:
- Assigns a shared integer `flapping_group_id` to every run of `FLAPPING_EPISODE_THRESHOLD` or
  more episodes for the same port whose `down_ts` values all fall inside a
  `FLAPPING_SPAN_SECONDS` window, and `None` to every other episode. Returns the list of
  `{id, port, count, span_seconds}` groups. This is a classification over the returned rows
  only — it creates no durable record, merges no rows, and filters nothing.

`compose_incidents_response(rows, anchors, *, start_ts, end_ts, filters, truncated)`:
- Partitions rows by port, prepends each port's anchor row when present, groups, applies the
  overrun split and the flapping classification, and returns the response dict:
  `{requested: {start_ts, end_ts}, filters, episodes, events, flapping_groups, row_budget,
  truncated, matched_count}`. `episodes` is ordered `open` first, then `down_ts` descending,
  then opening event `id` descending — a total order, so equal timestamps never reorder between
  identical requests. `events` is the flat filtered transition list ordered `ts DESC, id DESC`
  (Research open question 1: both projections come from the one query result set).

Write the unit half of `tests/test_incidents_api.py` first, driving each behaviour above
against in-memory row dicts, then implement until green.
