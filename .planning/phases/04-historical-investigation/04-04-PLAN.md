the selected range, and a simple trend that is a least-squares slope over observed points only —
withheld when there is not enough evidence, qualified when there is barely enough, and never

preset the preceding 90 days are entirely outside retention, so the longest range could never
compute one. D-09 fixed "latest" to the latest observation *within the range* so all five values
describe the same window.
Output: `leastSquaresSlope`, the three trend confidence tiers, the per-chart comparison row, and
the DST tick annotation on the shared time axis.
</objective>

`TREND_MIN_POINTS = 3` and `TREND_CONFIDENT_POINTS = 10` are the two thresholds; between them is
the low-confidence band. `TREND_HOURLY_MAX_SPAN_SECONDS = 86400` is the boundary between the
per-hour and per-day expression.

`leastSquaresSlope(points)` takes the fetched host points, keeps only those whose `avg_value` is
a finite number (the observed-points-only rule inherits Phase 2's no-interpolation guarantee
without new disclosure machinery), and returns the closed-form least-squares gradient of
`avg_value` against `ts`, in value-units per second. Use the existing `finiteMeasurement`
helper's discipline for deciding what counts as a value — a boolean, an array, an object or a
blank string is an absence, not a measurement of zero. Fewer than two usable points returns
`null`.

`trendDisplay(metric, points, spanSeconds)` turns that into the exact contracted copy:
- Fewer than `TREND_MIN_POINTS` usable points → `Not enough data for a trend`.
- Otherwise convert the per-second slope to per-hour when `spanSeconds <=
  TREND_HOURLY_MAX_SPAN_SECONDS`, per-day otherwise, and format its magnitude with a fixed
  one-decimal formatter.
- If the formatted magnitude is zero, return `{Label} steady` — no sign, no arrow. This is the
  flat band: a misleadingly precise signed zero is worse than saying steady. The predicted-change
  quantity used to reach this branch is an internal comparison only and is never rendered.
- Otherwise return `{Label} {sign}{value}{unit}/{hour|day} {arrow}`, with the arrow chosen from
  the slope's sign, matching the documented `disk +0.4%/day ↑` shape.
- With `TREND_MIN_POINTS` to `TREND_CONFIDENT_POINTS - 1` usable points, append the qualifier
  ` (low confidence — {N} points)` naming the actual usable-point count.

Nothing in the returned string may express a projection: no target date, no remaining time, no
"will reach". The slope describes the window that was observed and stops there.

Write the tests first: drive each `<behavior>` case from a fixture points array through a
Playwright page evaluation of the exposed function (or, if the IIFE keeps it private, through
the rendered comparison row's text for a fixture engineered to produce that exact tier), then
implement until green.

`rangeAggregate(points)` reduces the fetched points to the five values, all describing the same
selected-range window:
- `minimum` — the smallest non-null `min_value` across the points.
- `maximum` — the largest non-null `max_value`.
- `average` — the `sample_count`-weighted mean of `avg_value`, matching how the server itself
  composes an average across mixed-resolution buckets; an unweighted mean of bucket averages
  would silently over-weight sparse buckets.
- `latest` — the `latest_value` of the last point that has one, together with that point's `ts`.
  This is the latest *observed* point inside the range, never "now" (D-09).
- `observedPoints` — the usable-point count Task 1's tier logic consumes.
When the range contains no usable point, every one of the four values is the absence string
`Unknown` — never `0`, which would be a measurement Beacon did not make.

`formatComparisonValue(value, unit)` applies the fixed one-decimal formatter and appends the
metric's unit. The formatter is the single rounding site: no displayed rounded value is read back
and used in a further computation, so rounding cannot compound.

`renderComparisonRow(metric, points, spanSeconds)` writes five labelled values into
`comparison-{metric}`: `Latest`, `Minimum`, `Maximum`, `Average`, and the trend. The latest value
always renders its exact timestamp beside it, formatted through `formatLocalTimestamp`, in the
shape `Latest: {value} (as of {exact local timestamp})` — the range bounds are the disambiguator
that stops a past-ending range from reading as a current reading.

Style `.hist-comparison` as a wrapping row at the existing 14px body size with the numeric
portions in `--font-mono`, reusing the `.evidence-row` visual language rather than starting a new

`dstAnnotations(tickTimestamps)` walks the generated tick positions and compares each adjacent
pair of *local* labels produced by `formatLocalTimestamp`:
- **Fall-back (ambiguous hour):** two adjacent ticks whose full local labels are identical while
  their epoch values differ. Both ticks are annotated.
- **Spring-forward (absent hour):** two adjacent ticks whose local labels skip an hour that the
  fixed epoch interval between them should have produced. The tick after the skip is annotated.
The comparison is made against the labels `Intl.DateTimeFormat` produces for the Pi's configured
zone — never against manual UTC-offset arithmetic or a hand-rolled transition table, which is
exactly the class of bug offset maths gets wrong.

`renderSharedTimeAxis` renders an annotated tick with the class `hist-dst-tick` and the visible
text `⚠ DST transition`, plus a `<title>` naming which kind of transition it is, so the operator
sees a labelled anomaly rather than a compressed hour or two identical-looking labels with no
explanation. The axis is never re-spaced to hide the discontinuity.

When `state.timezone` is `UTC` — including the fail-closed case where the configured zone name
could not be resolved — no annotation can ever fire, and the axis renders normally.

Style `.hist-dst-tick` from the existing token set; the annotation is text and glyph, never
colour alone.
