`deriveBandSegments(points, episodes)` turns each bucket into one or more sub-segments whose
widths are proportional to that bucket's real durations: `online_seconds`, `offline_seconds`,
`unknown_seconds` and `gap_seconds`. A bucket carrying both online and offline seconds is split
proportionally, and its tooltip discloses the exact second counts together with a note that the
ordering *within* the bucket is below the displayed resolution — the durations are observed, the
sequence at sub-bucket scale is not, and the tooltip says so rather than implying it. A bucket
with zero online and zero offline seconds renders as `unknown` across its full width — "we did
not observe" is never rendered as "nothing happened". An `offline` sub-segment that falls inside
a maintenance-suppressed episode span (or inside the grace-covered portion of an overrun episode,
per plan 04-02's split) renders in the `maintenance` state instead.

`mergeBandSegments(segments)` merges only **adjacent segments carrying the same state**, into one
segment with one duration label. Adjacent segments with **different** states are never merged,
even when both would render below `MIN_BAND_SEGMENT_PX` — each keeps its own minimum-width slot,
so a state transition can never be compressed out of existence. A single uninterrupted state
therefore spans the full band width with exactly one duration label.

Each rendered segment carries a `title` with its exact start and end timestamps (through
`formatLocalTimestamp`) and its duration, and discloses the same on hover or keyboard focus.

Present the one number an operator opens this view for, without letting it disagree with anything
else on the page.

`timeWeightedAvailability(points)` sums `online_seconds` and `offline_seconds` across the range's
buckets and returns `{availability, observedSeconds, unknownSeconds, gapSeconds}` where
`availability` is `online / (online + offline)`. Unknown and gap seconds are **excluded from both
the numerator and the denominator** and reported separately — folding them into either would
turn "we did not observe" into either an outage or an uptime. Because the figure is a sum over
buckets it is invariant to processing order.

When `online + offline` is zero, `availability` is `null` and the readout renders `Unknown` —
never `0%` and never `100%`, both of which would be assertions Beacon cannot make about a window
it did not observe.

`renderAvailability(result)` writes the headline percentage into `service-availability` at the
28px mono treatment, with the range bounds rendered beside it so the figure is unambiguously
about the selected window. Beneath it, `service-availability-detail` is an expandable region
carrying the observed, unknown and gap second counts and the maintenance-attributed seconds.
Per 03.1 D-09 the headline is **never adjusted** for planned downtime and no
excluding-maintenance figure appears at equal weight — the attribution lives in the expanded
detail only. The headline duration must describe the same span the Incidents rows attribute to
this service, so an incident row and this figure can never disagree about how long the service
was down.

`aggregateFailureClasses(points)` sums each bucket's `failure_class_counts` map across the range,
reusing the existing failure-class vocabulary verbatim and inventing no display name for a class
the server did not emit. `renderFailureClassChips(counts)` renders one
`{class}: {count}` chip per class into `failure-class-chips`, beside the band and never inside
the latency chart, sorted by **descending count and then ascending class name**, so equal counts
produce a stable order between identical requests. The list is preceded by an explicit count
using singular and plural copy: `1 failure class` or `{N} failure classes`, and renders
`0 failure classes` rather than being omitted when there are none. At narrow widths the chip list
wraps to a second line rather than truncating any class name.

Tests: a fixture with 900 online and 100 offline seconds renders 90.0 percent; the same fixture

the headline and shows the attribution only in the expanded detail; a fixture with two classes of
equal count renders them in ascending class-name order; a fixture with no failures renders
`0 failure classes`.
