## Planner assumptions surfaced (not silently taken)

1. **`read_open_episode_anchors`'s existing semantics are tightened as part of the CR-01 fix, not
   as separate scope.** Widening the anchor candidate set to "every port with a currently-open
   state_change as of `start_ts`" is only correct if the anchor query answers "is this port
   currently down?" rather than "when did this port last go down?". Under the current
   most-recent-`online = 0` semantics, a service that went down at T1 and recovered at T2 with both
   before `start_ts` would be handed an anchor and fabricated as an open episode — a *new*
   dishonesty introduced by the fix. The tightening is therefore required by
   `04-VERIFICATION.md` missing item 1, not an extra.
2. **`DIA-04`'s promotion is deliberately not in scope.** The verifier recommends promoting DIA-04
   to Complete, but DIA-04 is connected to no gap. It is left for re-verification rather than
   promoted by a gap-closure plan, which is exactly the premature-promotion mistake commit 96bd3ca
   made with DIA-08.
3. **`COVERAGE.md` is not regenerated.** The phase's API-coverage declaration ("no external API
   integration") still holds for gap closure; this plan installs zero packages and adds no
   external call.

<assumption_delta_decision>
- **Primary noun:** the **incident episode**. Before this plan, an episode's identity was
  implicitly "a grouping of whatever rows this request's filters returned". After it, an episode's
  identity is "a grouping of the durable state_change record for an in-scope service over the
  requested range", with the operator's `event_type`/`maintenance` selections applied *to* episodes
  rather than *underneath* them.
- **Decision: `promote`.** The durable-record grouping becomes the one definition of an episode.
  The filtered-row-set grouping is not kept alongside it — keeping both would leave two competing
  notions of "an incident" in one response, and only one of them can represent a state machine.
- **Invariant test (accepted, implemented in Task 2):**
  `test_episode_scope_discloses_grouping_source_and_applied_narrowing` pins
  `episode_scope.grouped_from` to `EPISODE_GROUPING_SOURCE` on every request shape, so any future
  change that reintroduces grouping from the filtered row set goes red immediately.
- Advisory only; nothing in this plan blocks on it.
</assumption_delta_decision>
