## Explicit assumptions recorded by this plan

`05-CONTEXT.md` records only D-01/D-02/D-03. Where it is silent the planner's choice is recorded
here, visibly, so a later verifier evaluates the phase against decisions actually made.

- **A-01 — `degraded` == the `aging` tier.** Adopted from `05-UI-SPEC.md`'s resolution of D-01,
  confirmed against live source: `freshness_state()` (`dashboard/beacon/diagnosis.py:101-118`)
  already partitions evidence four ways, `aging` already reaches the advanced payload
  (`diagnosis.py:442`), and it has no dedicated presentation. Confirmed, not silently accepted.
- **A-02 — the backend change is real but narrow.** `/api/scan-status` (`dashboard/app.py:3034`)
  computes `worker_stale` from a single ad hoc cutoff (`heartbeat_age_seconds >
  WORKER_READY_SECONDS`) and has no tier vocabulary at all. This plan does **not** add a second
  cutoff: it extracts the cadence/classification the advanced payload already uses
  (`callback_schedule_evidence(J1)` → `freshness_state`, `diagnosis.py:353,442`) into a named
  helper and calls it from both places.
- **A-03 — assumption-delta decision: `promote`, not add-alongside.** One boolean
  (`worker_stale`) becomes two facts. The generalized noun is the **three-tier worker freshness
  state**, so `/api/scan-status` publishes the full `worker_freshness` object as the primary
  representation and `worker_degraded` as a derived convenience boolean. `worker_stale` /
  `worker_ready` / `recovery_required` are unchanged derived views kept for their existing
  consumers. What would force further promotion: a third consumer needing a fourth boolean.
- **A-04 — non-contradiction guard on the main dashboard.** `worker_stale` (threshold
  `WORKER_READY_SECONDS`, default 20) and `aging` (threshold `4 × cadence`, fixed at 20) coincide
  at the defaults. Only one of the two thresholds is configurable: the J1 heartbeat cadence is the
  literal `('seconds', 5)` in `WORKER_CALLBACK_INVENTORY` (`dashboard/beacon/worker_main.py:83`),
  and `callback_schedule_evidence` substitutes a settings value for the cadence of `J2` only
  (`dashboard/beacon/diagnosis.py:322-323`), so `4 × cadence` is fixed at 20 seconds and no
  configuration moves it. The overlap window is therefore **one-sided**: lowering
  `WORKER_READY_SECONDS` below 20 makes one heartbeat both `aging` and `worker_stale`, while
  raising it above 20 only widens the degraded window and creates no contradiction. Because that
  one-sided overlap is reachable by configuration, `/api/scan-status` publishes `worker_degraded`
  as *aging **and not** worker_stale*. Rationale: a page asserting
  both "monitoring paused" and "monitoring continues, this is not a failure" about the same
  heartbeat is worse than a narrower degraded window. The advanced payload needs no such guard —
  `stale`/`aging` are exclusive tiers of one call.
- **A-05 — banner form.** The UI-SPEC's box-vs-inline rule governs **per-subject** state
  renderings (a boxed `.advanced-error` vs an inline degraded badge). The global banner cluster is
  a pre-existing shared form (`.safety-warning`, four members) disambiguated by copy. To keep the
  two `--accent2` banners distinguishable without hue, `.degraded-warning` carries **no border at
  all**, where `.recovery-warning` keeps its `border-bottom` (`style.css:68`).
- **A-06 — banner placement.** `#degraded-warning` is appended as the **fourth and last** child of
  `#safety-warning-cluster` in both documents, leaving the existing three banners at their current
  positions and order.
- **A-07 — Phase 6 boundary, restated.** This definition covers freshness/evidence staleness only.
  Phase 6's OPS-02 concerns capture-pipeline health and will compose from different evidence; it
  may reuse this contract's glyph, colour and copy shape but not this boolean.
