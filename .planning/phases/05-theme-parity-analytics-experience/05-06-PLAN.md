<objective>
Reconcile the one genuine cross-surface inconsistency, then close OPS-06 with the breadth the
requirement asks for.

`dashboard/style.css` narrows at 720px; `dashboard/advanced.css` narrows at 719px. No artifact
anywhere records a reason for the difference, and a viewport exactly 720px wide therefore gets the
narrow layout on one surface and the wide layout on the other. This plan reconciles them to one
value and pins the agreement at source level so they cannot drift apart again.

Then it establishes `tests/test_theme_parity_ui.py` — the phase's dedicated cross-surface
dual-theme contract module — and uses it to assert the boundary from both sides on both documents,
and to pin the four layouts the responsive contract calls at-risk.

Purpose: UX-05 asks that the dashboard and the advanced workspace remain usable at supported narrow
and desktop widths. `05-RESEARCH.md` found every at-risk layout already mitigated but none of them
asserted at a narrow viewport in both themes — the risk is regression, and regression risk is
closed by coverage.
Output: the reconciled breakpoint and `tests/test_theme_parity_ui.py` with its harness and three
tests.
</objective>

## Explicit assumptions recorded by this plan

- **A-30 — the 719/720 mismatch is unintentional and is reconciled upward to 720.** `05-RESEARCH.md`
  assumption A3 flags it as a likely off-by-one with no documentation supporting intentionality;
  the UI-SPEC resolves it to one shared value. This plan moves the advanced workspace's narrow
  boundary to match the main dashboard's rather than the reverse, because the main dashboard's
  value is the older and more widely-tested of the two and moving it would touch a larger surface.
  The 959px nav-rail boundary is unrelated and is not changed.
- **A-31 — OPS-06 is satisfied without pixel snapshots, and this plan states the argument rather
  than assuming it.** `05-RESEARCH.md` Pitfall 4 and the UI-SPEC both rule them out. The reasons,
  restated so a later reader can weigh them: this project has no baseline-review workflow, its CI
  and its target hardware are Raspberry Pi-class where font and GPU rendering differ from a
  developer machine, two themes would double every artifact, and a contract assertion can express
  a role, an accessible name or a text claim that a pixel diff cannot. The planner agrees with the
  recommendation and does not switch silently.
- **A-32 — this phase's cross-surface coverage gets its own test module.** `tests/test_ui_states.py`
  and `tests/test_advanced_ui.py` are each scoped to one document. The assertions here are
  deliberately cross-surface — the same viewport width applied to both documents in both themes —
  so they get a module named for that concern rather than being split across two single-document
  modules where the shared boundary would be invisible.
- **A-33 — the boundary is asserted from both sides.** Asserting only that the narrow layout
  appears at the boundary would pass against a stylesheet that narrows at every width. Each
  boundary assertion is paired with an assertion one pixel wider that the wide layout appears.
