<objective>
Make Beacon's deferred SQLite concurrency decision explicit and proven: put every connection in WAL
mode, keep the rollout correct whether the operator's live database is already in WAL or still on the
default rollback journal, and cover concurrent web/worker access and restart recovery with automated
tests. Leave `_db_lock` exactly as it is, and write down why (D-01).

Purpose: `journal_mode` is set nowhere in this codebase — a repo-wide grep confirms it appears only
where it is *read* (`inventory.py:134`, `telemetry.py`). `PROJECT.md` records the WAL question as
deferred to this phase. Today the only concurrency guarantees are the `flock` sibling lease,
`PRAGMA busy_timeout=30000`, and a process-global `threading.Lock()` serializing all eight gunicorn
threads (`app.py:115`).

Output: WAL enabled with a verified read-back, the inspection and backup paths hardened for WAL
sidecars, the `restart_recovery` and concurrent-writer tests `06-VALIDATION.md` names for OPS-04, and
`06-DEBT.md` recording the `_db_lock` follow-up.

This plan stays `autonomous: true`. Both starting modes — default rollback journal and already-WAL —
are covered by automated tests against synthetic fixtures, so the rollout logic is proven without a
Pi. Reading the *production* starting mode is evidence, not a gate: when a Pi is reachable the reading
is captured and attached; when it is not, the reading is recorded as `unverified` and carried as an
open verification item in `06-DEBT.md` rather than silently assumed. `06-RESEARCH.md` Open Question 1
asked for the evidence trail, not for a halt.
</objective>

**`dashboard/beacon/db.py`**:
- Add module constant `JOURNAL_MODE = 'WAL'` with a comment recording the decision: WAL lets readers
  proceed without blocking on a writer, which is what OPS-01's "analytics queries active" clause and
  the `AR-03-01` accepted-risk note both need; the mode is persisted in the database header, so
  issuing the PRAGMA on every connection is idempotent; and the `flock` sibling lease is orthogonal
  and stays exactly as it is because it protects the *maintenance exclusion*, not ordinary read/write
  concurrency.
- In `connect_db`, add `conn.execute('PRAGMA journal_mode=' + JOURNAL_MODE)` immediately after the
  existing `busy_timeout` and `foreign_keys` PRAGMAs, inside the same `try` block so the existing
  `except Exception` branch still releases the flock handle. `JOURNAL_MODE` is a module constant, not
  caller input, so this is not a parameterization site.
- Add `configured_journal_mode(conn)` returning `str(conn.execute('PRAGMA journal_mode').fetchone()[0]).lower()`.
  This exists so callers and tests read the mode that is actually in force rather than trusting the
  request — SQLite silently declines the switch if another connection holds a lock.
- Do not touch `_db_lock` in `dashboard/app.py` in this task or this plan (D-01, RESEARCH Pitfall 4).
  WAL governs reader/writer blocking across connections; `_db_lock` serializes eight threads inside
  one process. They solve different problems and are changed separately, in that order.

**`dashboard/beacon/inventory.py`** — `_readonly_connection` opens with `mode=ro`. A `mode=ro`
connection to a WAL-mode database cannot initialize the `-shm` shared-memory file it needs, so schema
inspection of a WAL database fails — and `_apply_pending_migrations` calls `collect_inventory` on
every non-empty database below the target version, which would lock every deployment out of upgrading.
Fix it: attempt the existing `mode=ro` URI connection first; on `sqlite3.Error`, fall back to a normal
`sqlite3.connect(resolved)` and immediately execute `PRAGMA query_only=ON`, which forbids writes at
the SQL level while permitting the `-shm` mapping. Wrap any failure of the fallback in `InventoryError`
exactly as today. Leave `collect_inventory`'s size/mtime non-modification assertion untouched — it is
the real guarantee that inspection does not mutate the file, and it now also covers the fallback path.

**`dashboard/beacon/migrations.py`** — `create_verified_backup` copies the source with the online
backup API and then reopens the partial file with `mode=ro` for `PRAGMA integrity_check`. Once the
source is in WAL, that copy inherits WAL in its header and the `mode=ro` integrity check hits the same
problem. Fix it at the source of the artifact: on the destination connection, after `source.backup(destination)`
and before closing it, execute `PRAGMA journal_mode=DELETE`. A retained backup is a static artifact
with no concurrency requirement, so rollback-journal mode is the right shape for it — and it means a
retained backup never carries `-wal`/`-shm` sidecars, which keeps the existing restore assertion in
`recovery.py` (no sidecars after restore) true by construction. Record that reasoning in a comment.
