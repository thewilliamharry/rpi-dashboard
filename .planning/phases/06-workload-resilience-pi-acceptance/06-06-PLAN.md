<objective>
Build the Raspberry Pi-class acceptance run as a checked-in, repeatable, automated harness whose
pass/fail oracle is evidence the product already produces and already trusts — then run it, on real
hardware if reachable and as a labelled smoke run if not.

actually holds up under load on the target hardware. `06-RESEARCH.md` § Environment Availability
records that a physical Pi may not be reachable from the execution environment, and that this must not
block *building* the harness — only its execution on real hardware is human-gated, consistent with how
`03-UAT.md` and `03.1-UAT.md` handled real-Pi tests for this project.

and the operator instructions for running it.

  <action>
Create `tests/pi_load_acceptance.py` as a standalone, checked-in, repeatable script — not a pytest
module. The file name deliberately does not match pytest's `test_*.py` collection pattern, so it will
not be collected by the suite; that is intended, and `06-VALIDATION.md` invokes it directly.

Build it entirely from already-pinned dependencies — `requests`, `threading`, `psutil`, `argparse`,
`json`, `statistics`, `time`, plus the Beacon modules named below. Add no new package
(`06-RESEARCH.md` § Don't Hand-Roll rejects locust/k6 for exactly this reason).

**CLI:** `--duration` (seconds, default 600), `--base-url` (default `http://127.0.0.1`), `--db`
(default `/data/dashboard.db`), `--concurrency` (default 8, matching gunicorn's thread count),
`--output` (JSON report path, default stdout), `--self-test` (a short bounded run against a locally
started app, for automated verification without a Pi).

**Load generation:** `--concurrency` worker threads issuing `requests` against the dashboard's own
routes for the run duration — `/api/services`, `/api/scan-status`, `/api/thumbnail-status`, a
`/api/thumbnail/<port>` for each port the services list reports, and the analytics routes under
`/api/history/` and `/api/advanced/`. Record every response's status and elapsed time. This is the
"discovery + preview churn + analytics queries" mix Pattern 5 specifies; the worker's own discovery,
preview, cleanup and sampling jobs supply the background half by simply running.

**Oracles — call the product's code, do not restate it:**
- Cadence: open the database with `dashboard.beacon.db.database_access`, read
  `dashboard.beacon.repositories.read_background_job_health`, and pass each job's `last_success_ts`
  through `dashboard.beacon.diagnosis.freshness_state` with that job's own cadence taken from
  `WORKER_CALLBACK_INVENTORY` (and `Settings.metric_sample_seconds` for J2). `assert_cadence` fails
  when any essential job (`J1`, `J2`, `J3`, `J4`) classifies as `stale`, or when any job's
  `background_job_health` state is `failed`. Do not write a second staleness rule anywhere in this
  file — `06-RESEARCH.md` § Don't Hand-Roll and the Anti-Patterns list both call inventing parallel
  thresholds out by name, and PROH-OPS-07-01 forbids it.
- Resources: `parse_compose_memory_limits` reads `docker-compose.yml` and converts the declared
  `mem_limit` strings (`1g`, `256m`) to bytes. Sample the worker and web processes with
  `psutil.Process(...).memory_info().rss` and `cpu_percent`, matching processes by command line
  (`worker.py` for the worker, `gunicorn` for the web tier), and fail if any sampled RSS exceeds that
  process's parsed limit. Record peak and mean CPU percent in the report as observed evidence.
- Response times: `assert_response_times` computes p50/p95/max per route and fails when p95 exceeds a
  declared budget. Declare the budgets as a module-level dict with a comment explaining each choice
  in terms Beacon already uses — the dashboard polls `/api/scan-status` and `/api/services` on an
  interactive cadence, so those get the tightest budget; `/api/thumbnail/<port>` serves up to
  `THUMB_MAX_BYTES` and gets a looser one; the analytics routes under `/api/history/` and
  `/api/advanced/` are operator-initiated and get the loosest. Choose defensible values and state the
  reasoning; do not derive them from a run you already made (PROH-OPS-07-01).

**Report:** an `AcceptanceReport` serialized as JSON containing the run parameters, the host
(`platform.machine()` and `platform.node()`), a `run_kind` of `acceptance` or `smoke`, per-route
latency percentiles, the sampled resource series, the full `background_job_health` projection, the
`freshness_state` classification per job, and one boolean per assertion plus an overall verdict.
`run_kind` is `acceptance` only when the run was invoked without `--self-test`; a `--self-test` run is
always `smoke`, so a convenience run can never be mistaken for hardware evidence (PROH-OPS-07-02).

**Honest failure:** exit non-zero whenever the target was unreachable, the database could not be
opened, any required oracle could not be sampled, or any assertion failed — with the reason named in
the report. Never exit 0 with missing evidence.

**`tests/test_workload_resilience.py`** — add `test_pi_load_acceptance_oracles_are_the_products_own`
importing the harness module and asserting: `parse_compose_memory_limits` returns 1073741824 for the
worker and 268435456 for the web tier from the real `docker-compose.yml`; `assert_cadence` fails for a
synthetic job-health row aged past four times its cadence and passes at exactly that boundary; and
`assert_resource_budget` fails for an RSS above the parsed limit. This is the automated coverage that
keeps the harness honest without needing hardware.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| harness → running Beacon instance | The harness drives real HTTP load against a live deployment and reads its live database |
| harness report → phase verification | A JSON verdict becomes the evidence a requirement is judged against |
| host resources → container limits | Memory and CPU consumption crosses the declared compose budgets |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-26 | Repudiation | a smoke run passed off as hardware acceptance evidence | high | mitigate | `run_kind` is derived from the invocation, not from a flag the runner sets; `--self-test` always yields `smoke`; the report carries `platform.machine()` and `platform.node()` (PROH-OPS-07-02). |
| T-06-27 | Tampering | thresholds tuned to make a run pass | high | mitigate | The cadence oracle delegates to `freshness_state` and cannot be adjusted without changing product code that other suites assert against; route budgets are declared with written reasoning and covered by `test_pi_load_acceptance_oracles_are_the_products_own` (PROH-OPS-07-01). |
| T-06-28 | Denial of Service | the harness itself overloading the Pi | medium | mitigate | `--concurrency` defaults to 8, matching gunicorn's own thread count, so the harness cannot exceed what the deployment already admits; `--duration` is bounded and required; the harness issues no writes. |
| T-06-29 | Information Disclosure | the report embedding operator data | low | mitigate | The report carries route names, latency statistics, resource samples and `background_job_health` rows — job ids, timestamps and error classes only. | T-06-30 | Spoofing | a run against the wrong target reported as the deployment | medium | mitigate | The report records the resolved `--base-url` and `--db` alongside the host, so the artifact names what it measured; an unreachable target exits non-zero rather than reporting a pass. |
| T-06-SC | Tampering | npm/pip/cargo installs | high | mitigate | No new packages this phase (`06-RESEARCH.md` § Package Legitimacy Audit); the harness is built from `requests`, `psutil`, `threading` and the stdlib, all already pinned. No install task exists, so no legitimacy checkpoint applies. |
