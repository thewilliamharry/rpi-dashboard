<objective>
Make the acceptance harness's resource oracle measure Beacon. Today it measures whatever program on
the host happens to have a matching string in its command line, and on the user's Pi that was a
completely different application.

Purpose: the 600s acceptance run reported `assertions.resources.passed: true` with
`peak_rss_bytes: 45924352`. That number is byte-for-byte the RSS of PID 675687 — the gunicorn master
of `/opt/offline-portal`, another application sharing the Pi. The real Beacon web worker (PID 907613)
was at 45.6% CPU and 88944 KB at the same instant. The reported pass was never earned. This is the
exact unearned-evidence class `PROH-OPS-07-02` exists to prevent, and it is systemic for this
product: Beacon is a dashboard *for other services on the same LAN host*, so a bare `gunicorn`
substring match is close to guaranteed to mis-target.

Until this lands, no report the harness produces is trustworthy, which is why every other plan in
this gap-closure round that depends on a believable acceptance report is sequenced behind it.

Output: a harness whose per-role targets are derived from the Beacon containers, whose sampled set
covers the process that actually serves requests, whose report states which processes it measured,
and which fails honestly and loudly when it cannot resolve them.
</objective>

  <action>
Replace host-wide command-line matching with container-derived resolution for acceptance runs.

**Add a validated, injectable docker seam.** Add `subprocess` to the import block. Write
`_container_root_pid(name, *, runner=subprocess.run)` that:
- Rejects any `name` not matching `^[A-Za-z0-9][A-Za-z0-9_.-]*$` before doing anything else, raising
  a `ValueError`. Docker's own name grammar is exactly this, so a rejection here is a caller error,
  not a lost capability — and it removes argument-injection as a concern outright (T-06-31).
- Invokes `['docker', 'inspect', '--format', '{{.State.Pid}}', name]` as an argv list through
  `runner`, with `capture_output=True`, `text=True`, and a bounded `timeout`. Never build a shell
  string; never pass `shell=True`.
- Issues one invocation per container name, so a missing container is attributable to that name
  rather than to an ambiguous position in a multi-name result.
- Treats a non-zero return code, a `FileNotFoundError` (no docker binary), a `subprocess`
  `TimeoutExpired`, unparseable output, and a reported PID of `0` (docker's value for a
  not-running container) as failures, each surfacing a short reason string. A stopped container
  reporting `0` must not be mistaken for a valid target.

The `runner` parameter is the test seam: it lets the regression coverage in Task 3 drive every one
of these branches without docker, a container, or root.

**Expand the root PID to the serving process set.** Write
`resolve_container_process_tree(name, *, runner=subprocess.run)` returning
`(processes, reason)` — a non-empty list of `psutil.Process` handles on success with `reason` unset,
or an empty list with a reason on failure. On success it returns `psutil.Process(root_pid)` together
with `children(recursive=True)`. The recursion is load-bearing and not defensive tidiness: the Pi
evidence shows the web container's root process is the gunicorn master (PID 907527, idle) while the
process actually serving requests is its forked child (PID 907613, 45.6% CPU). Sampling only the root
would reproduce the very defect this task closes, in a subtler form. Tolerate a process that exits
between enumeration and sampling by skipping it, not by failing the run.

**Re-derive the child set on every sampling tick, not once at run start.** Gunicorn kills and respawns
workers — on timeout, on `max_requests`, on a crash — and a 600-second run is long enough for that to
happen. If the set were enumerated once, a respawn would leave the web role sampling only the surviving
master: an alive process, so Task 2's empty-sample guard would not fire, producing a report of near-zero
CPU for a tier under load. That is this plan's own defect returning in a subtler form, so the fix has to
be structural rather than a caveat. Hold the container root PID for the run and re-walk
`children(recursive=True)` each tick; at the current sample interval that walk is negligible next to the
sampling it feeds. If the root PID itself disappears, that is a genuine failure for the role — record it
with a reason rather than continuing against an empty set (PROH-OPS-07-06).

**Rewrite `_resource_targets`.** Keep its signature and keep the `self_test` branch returning the
current process for both roles — but return the mapping in the new shape, so every downstream
consumer handles roles uniformly and the smoke branch cannot diverge into its own code path. For
`self_test=False`, resolve `worker` from the `beacon-worker` container and `web` from `beacon-web`,
returning per role either the resolved process list or an unresolved marker carrying its reason.
There must be no path from `self_test=False` to the current-process fallback and no path from either
branch to a host-wide process scan. Rewrite the function's docstring: its current text asserts that
command-line matching is "never by assumption", which the hardware run disproved, so leaving it
would leave a false claim standing next to its own correction.

Delete `_find_process_by_cmdline`. It has exactly one caller, which this task removes, and leaving a
host-wide substring matcher in the file invites its reuse — the failure mode being closed here is
that this matcher looked correct at every review until real hardware ran it.

**Expose container names as documented CLI knobs.** Add `--web-container` (default `beacon-web`) and
`--worker-container` (default `beacon-worker`) arguments. The defaults are the `container_name` values
pinned in `docker-compose.yml`, so the harness and the deployment cannot drift apart silently; the
override exists for an operator running a modified compose file. Follow the D-02 convention this
phase established for every knob it introduced: a specified value, a way to change it, and recorded
rationale — put that rationale in the argument help text and the module docstring rather than leaving
the numbers unexplained.

**Sum across each role's process set when sampling.** Change `_sample_resources` to accept the
role-to-process-list mapping, priming `cpu_percent` on every process, and recording each sample as the
sum of `memory_info().rss` and the sum of `cpu_percent()` across that role's live processes. Summing
RSS over-counts pages shared copy-on-write between a gunicorn master and its child, so the reading is
an upper bound rather than an exact figure. State that in a comment with its justification: for an
acceptance oracle asserting *against a ceiling*, an upper bound can produce a false failure but never
a false pass, and biasing toward false failure is the correct direction for evidence this phase has
already been burned by trusting.

**Record provenance in the report.** Add a `resource_targets` entry to the `assertions.resources`
block giving, per role, the container name it resolved, the resolution method, the container root PID,
the union of every PID sampled at any point during the run, and a boolean recording whether that set
changed mid-run. The union and the flag are what make a respawn visible: without them a run that
sampled two different worker processes is indistinguishable in the report from one continuous
measurement, and an operator investigating an odd CPU curve has no way to tell which they are holding. The 600s run's resource pass was unfalsifiable from the report alone — the numbers looked
plausible and nothing recorded whose numbers they were. A reader must be able to audit the resource
evidence instead of trusting it.

**Extend `PiLoadAcceptanceHarnessTests`** with coverage of the seam driven through a stub `runner`:

empty list and a non-empty reason; and an invalid container name raises before the runner is called
at all. Assert the last of these by having the stub record its invocations and checking none were
made.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| harness → docker daemon | The harness shells out to `docker inspect`; the container name is operator-supplied via CLI |
| harness → host process table | The harness reads PIDs and resource counters for processes it did not start |
| harness → acceptance report | The report is downstream evidence for a requirement sign-off; whatever it asserts is trusted by readers who did not watch the run |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-06-31 | Tampering | `_container_root_pid` subprocess invocation | medium | mitigate | Container name validated against `^[A-Za-z0-9][A-Za-z0-9_.-]*$` before any call; docker invoked as an argv list with a bounded timeout and never `shell=True`, so no string is ever interpreted by a shell |
| T-06-32 | Repudiation | acceptance report resource assertions | high | mitigate | Per-role `resource_targets` provenance records the container and PID set that produced each figure, making a resource pass falsifiable from the report alone rather than only from the run |
| T-06-33 | Spoofing | role-to-process resolution | high | mitigate | Targets derive from the Beacon containers' own root PIDs and descendants; the host-wide command-line matcher that allowed an unrelated application to impersonate the web tier is deleted, and Task 3's co-tenant regression fails if it returns |
| T-06-53 | Spoofing | sampled process set going stale mid-run | high | mitigate | A gunicorn worker respawn would leave a one-shot enumeration sampling only the surviving idle master — alive, so the empty-sample guard stays silent — reproducing the unearned-evidence defect; the set is re-derived every tick, the sampled-PID union and a changed flag are recorded, and Task 3's respawn regression asserts on sampled values rather than bookkeeping (PROH-OPS-07-06) |
