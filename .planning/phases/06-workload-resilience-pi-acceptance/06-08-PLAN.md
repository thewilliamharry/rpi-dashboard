<objective>
Remove the ~2.5 seconds of pure Python arithmetic that one `/api/services` request spends recomputing
hourly uptime buckets, without changing a single value the route returns.

Purpose: measured on the Pi at `--concurrency 1`, with all queueing removed, `/api/services` costs
p50 2504.6ms / p95 2523.3ms / max 2529.8ms. Every other route is 3-98ms. A ~1% spread across p50,
p95 and max is the signature of fixed-size CPU work, and the source is a nested loop in
`dashboard/app.py` that walks every interval once per bucket: 168 buckets x ~2,000-10,000 intervals x
8 services is on the order of 2.7 million inner iterations per request. The real `beacon-web` worker
was independently measured at 45.6% CPU during the load run, corroborating it.

Both alternative explanations were eliminated by direct measurement on hardware and must not be
re-planned: managed connection open+close is 0.8ms, and reading the largest 978 KiB thumbnail blob is
1.8ms. The `thumbnails` overflow-page hypothesis recorded in this gap's `missing:` list was measured
false — 8 rows, the exact production query returning in 1ms — and no index change is warranted.

This is not a Phase 06 regression: `git diff 8c2fc48..HEAD -- dashboard/app.py` touches no uptime,
bucket or interval code, and the loop last changed in `51a4393`. It is a latent defect that OPS-07's
harness surfaced on its first genuine hardware run — which is what the harness was built to do.

Output: an equivalent computation with linear cost, an N+1 removed, and permanent tests that pin both
the exact output and the improved scaling.
</objective>

  <action>
Rewrite only the bucket accumulation in `_legacy_uptime_summary`. Leave the interval construction, the
percentage computation and the clamp untouched — they are already linear and already correct.

**Keep the bucket boundaries bit-identical.** Continue to derive them exactly as the current code
does: `bucket_seconds = UPTIME_WINDOW_SECONDS / UPTIME_BUCKETS` as float division, each boundary as
`start + int(idx * bucket_seconds)`, and the final bucket's end overridden to `int(now)`. Recomputing
these any other way — integer division, cumulative addition, `round` instead of `int` — would shift
boundaries by a second in places and silently change published bucket values. Precompute the boundary
pairs once into a list, then sweep.

**Sweep instead of rescanning.** Walk buckets in ascending order with an index into `intervals` that
only moves forward. Because `intervals` is sorted, contiguous and non-overlapping, an interval whose
end is at or before the current bucket's start can never overlap this bucket or any later one, so the
index may advance past it permanently. For each bucket, accumulate from that index forward while the
interval's start is before the bucket's end, using the identical overlap expression
`max(0, min(end, bucket_end) - max(begin, bucket_start))`. Do not advance the permanent index past an
interval that extends beyond the current bucket — it still contributes to later buckets.

Total work becomes proportional to the number of intervals plus the number of buckets, instead of
their product.

**Why this is exactly equal, not approximately.** Every overlap term is an integer, integer addition
is associative, and each bucket accumulates exactly the same non-zero terms in the same order —
intervals the sweep skips are precisely those whose overlap expression evaluates to zero. The
per-bucket sums are therefore identical integers, so `round(bucket_online / bucket_observed, 3)`
receives identical operands and the `-1` sentinel triggers on identical conditions. Record this
argument as a comment on the sweep, because the reason a reader can trust the rewrite is the
invariant, not the diff.
