`WR-01` (`dashboard/beacon/inventory.py:41-56`): the WAL read-only-inspection fallback opens a
*writable* connection and forbids writes at the SQL level with `PRAGMA query_only=ON`. Establishing
that connection against a WAL database still requires write access to the source directory to map the
`-shm` sidecar, so inspecting a locked-down archival copy raises `InventoryError`. That is exactly the
copy-then-restrict workflow this phase's own README documents. Accepted as `AR-06-02` in
`06-SECURITY.md` with `mode=ro&immutable=1` recorded as the suggested remedy.

`WR-02` (`dashboard/app.py:3054-3062`): `thumb_state` checks the degraded preview status before
checking whether a thumbnail exists, so a service can be reported `degraded` while a perfectly valid
thumbnail is being served. Scoped to an API field with no current frontend consumers — which is why it
is worth fixing now, while nothing depends on the wrong behavior.

Output: both warnings closed, each with a test, and `AR-06-02`'s residual gap resolved rather than
carried into the next milestone.

  <action>
Add a third attempt to `_readonly_connection`, **after** the existing two, using a
`mode=ro&immutable=1` URI. `immutable=1` tells SQLite the file cannot change, so it reads the main
database file directly and never attempts to map the `-shm` sidecar — which is precisely why it works
on read-only media where both current attempts fail.

**The ordering is the entire safety argument, so do not shorten it.** The sequence must remain: the
plain `mode=ro` URI first, then the writable `PRAGMA query_only=ON` fallback, and only then the
immutable URI. Placing the immutable attempt earlier would change which connection the live, writable
`/data` upgrade path receives, and that path is currently covered end-to-end by a non-empty-sidecar WAL
fixture test. `immutable=1` makes SQLite ignore the `-wal` file entirely, so a database with committed
but not-yet-checkpointed transactions would be inspected as though those transactions did not exist —
a stale schema version reported to the code that decides which migrations to run. As the final attempt
it is only ever reached where nothing can be writing anyway, because both attempts that require write
access already failed; earlier in the sequence it would be a correctness hazard on the deployment path
(PROH-OPS-04-03, T-06-43).

Preserve the existing exception handling exactly: every attempt's `sqlite3.Error` and `OSError` are
caught, and a total failure still raises `InventoryError('unable to inspect SQLite database')` with the
originating exception chained. The failure stays loud; only the set of cases that reach it shrinks.

**Record the strategy in the report.** Report which attempt produced the connection, alongside the
existing `journal_mode` reading. Without it, a reading taken under the immutability assumption is
indistinguishable from a normal one, and the whole reason to constrain the ordering above is that the
two are not equivalent. An operator holding a report has to be able to tell which they are looking at.

**Tests in `tests/test_migrations.py`:** a WAL-mode fixture in a directory made non-writable inspects
successfully and reports the immutable strategy — skip the test cleanly if the environment cannot
create a non-writable directory, for example when running as root, rather than letting it pass
vacuously; a WAL-mode fixture in a writable directory still inspects successfully and reports the
non-immutable strategy, which is the assertion that pins the ordering; a non-WAL fixture still
inspects through the first attempt; and a genuinely unopenable path still raises `InventoryError`.
  </action>
