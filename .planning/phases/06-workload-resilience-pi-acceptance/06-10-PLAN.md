<objective>
Re-run the acceptance test on real hardware against a harness that measures Beacon and a route that no
longer costs 2.5 seconds — then decide, on that evidence, whether the deferred lock narrowing is still
correctly deferred.

Purpose: this is where the phase closes or does not. The previous run failed with every exercised
route over budget, and produced a resource "pass" that had asserted against another program entirely.
`06-07` fixed the oracle and `06-08` fixed the cost; neither claim is worth anything until hardware
says so.

The third defect is deliberately not pre-fixed. `_db_lock` serializes all eight gunicorn threads to an
effective concurrency of one, which is what turned a single 2.5-second route into `/api/scan-status`
reporting p50 7695ms for 3.4ms of its own work. But the lock is the amplifier, not the defect. With the
amplified input removed, the amplification may no longer matter — and narrowing the lock is a genuinely
risky change across 30 call sites that reopens a closed security threat and lifts a fence the user set
deliberately in `D-01`. Guessing in either direction is worse than measuring, so this plan measures
first and puts the decision in the user's hands.

Output: a trustworthy acceptance report, a recorded decision on the lock, and debt entries that match
what hardware actually established.
</objective>

  </decision>
  <context>
`--workers 1 --threads 8` in `dashboard/Dockerfile` gives eight HTTP threads, but every database-touching
route holds one process-wide lock across 30 call sites, so effective concurrency is one. In the failing
600s run that turned a single 2.5-second route into a whole-deployment stall: `/api/scan-status`, whose
own work is 3.4ms, reported p50 7695ms. `D-01` fenced this deliberately; `T-06-24` is closed on the
evidence that no call site changed. There is now hardware evidence that the deferral has a cost.

**What the arithmetic predicts — a prediction to check against Task 1's numbers, not an assumption.**
The failing run served ~2718 requests over 600s across 13 rotating route labels, so `/api/services` took
roughly 209 of them at ~2.5s each: about 523 seconds of serialized service time inside a 600-second
window. That single route accounts for roughly 87% of everything the lock was serializing. Remove it
and mean serialized service time falls from ~221ms to a few tens of milliseconds, taking the deployment
from saturated to lightly loaded at the same request rate — at which point queueing largely disappears
and p95s should approach the concurrency-1 control values, which were 3-68ms against budgets of
500-2000ms.

If Task 1 bears that out, the lock is not currently costing anything observable, and narrowing it would
mean touching 30 call sites and reopening a closed security threat to fix a problem the evidence says
is no longer there. **Deferring again is the expected outcome and is a legitimate result, not a
failure to act.**

If Task 1 does not bear it out — routes still over budget with `/api/services` now fast — then the
lock is the remaining binding constraint, the deferral has become the defect, and narrowing is
evidence-backed rather than speculative.
  </context>
