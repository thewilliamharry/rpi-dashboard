<objective>
Expand the tracer's wait/hold measurement into the two further decompositions
`06-VERIFICATION.md` Truth 5 asks for: what `_db_lock`'s critical section is actually made of
(missing item 4), and how much of each request's latency is the GIL rather than the lock
(missing item 3).

Both are answered by measurement, not by inference from another mechanism's absence. That is the
explicit correction `D-DEBT-06-09` records: `D-DEBT-06-01`'s second reopening test used an
unlocked, GIL-bound 82ms route as the discriminator for a lock, and could not fire while any GIL
cost existed. This plan measures the GIL contribution and the lock contribution independently, on
the same requests, so neither is read off the other.

**This plan still measures and does not fix.** `_db_lock`'s scope is unchanged; `06-15` Task 3's
28-call-site pin stays green. `06-CONTEXT.md` D-01 and `PROH-OPS-04-02` hold.

Purpose: `06-PROFILE.md` puts `/api/services`' SQL share at 17.958% — on an Apple Silicon laptop,
under `cProfile`, at concurrency 1. That number sizes the candidate round-5 fix (releasing the lock
after the reads). It has never been confirmed on Pi hardware under load, and `PROH-OPS-07-09`
forbids treating the laptop figure as Pi evidence. This plan builds the instrument that can confirm
or contradict it in situ.

Output: a snapshot that answers all four of Truth 5's measurement questions, proven end-to-end
under an eight-thread rehearsal against the real app.

`D-DEBT-06-10`'s requirement, applied to this plan.

**Clauses that genuinely mandate a mechanism, with reasons and falsifiers:**

1. **"Time SQL inside `ManagedConnection` and a `TimingCursor`, not by wrapping call sites."**
   *Why:* `api_services`' critical section is 155 lines with many query sites, and
   `06-PROFILE.md`'s own buckets already split `sql_execute` from `sql_fetch` — instrumenting the
   connection seam reproduces that split at one place instead of dozens, and touches no route body.
   *What would make it wrong:* CPython's `Connection.execute` is expected to route through
   `self.cursor()`; if on some build it does not, `fetchall` time would go unmeasured and land in
   the Python bucket, understating SQL and overstating the candidate fix's payoff — the exact
   direction of error that would mislead round 5. Task 1's guard is therefore an **outcome**
   assertion that a real `conn.execute(...).fetchall()` records non-zero fetch nanoseconds, not an
   inspection that the override exists.

2. **"Derive off-CPU time as wall minus `time.thread_time_ns()`."**
   *Why:* the outcome — an independent GIL measurement — needs some clock, and this is the only
   per-thread CPU clock in the stdlib. A GIL-contention profiler would be a new dependency, which
   `T-06-SC` forbids adding without a legitimacy audit. *What would make it wrong:* off-CPU time
   also contains genuine I/O wait, so a single measurement over-attributes to the GIL. This is
   handled as an outcome, not hand-waved: the concurrency-1 pass establishes each route's I/O
   baseline, and only the concurrency-8 **excess** over that baseline is read as contention. The
   report must state this, and `06-18`'s report task asserts it is stated.

3. **"Do not add a module-level `def` to `dashboard/beacon/db.py`."**
   *Why:* `tests/test_module_boundaries.py:377` classifies every module-level `FunctionDef` in that
   file against a closed four-name set at line 403. A new module-level function fails
   `test_the_derived_seam_set_matches_the_database_module` for a reason unrelated to database
   ownership. *What would make it wrong:* nothing about the constraint is a correctness property;
   it is a known interaction with an existing gate, recorded so the executor is not surprised. If
   the gate is later generalised, the constraint lapses.

**Clauses deliberately phrased as outcomes where a mechanism was tempting.** The first draft of
Task 1 said "record `sql_execute_ns` and `sql_fetch_ns`". That is shape — a wrapper that records
zeros satisfies it. It now states the outcome: for a critical section containing a query with a
known, artificially inflated cost, the reported SQL share must land within a stated band of the
known share. That assertion fails if the numbers are wrong, not merely absent.

**Every new test is mutation-verified**, with observed failure values recorded in the SUMMARY. Each
task names its mutation.

**What this review changed.** (a) Task 1's guard moved from "records the fields" to "reports the
known share within a band", because the former is satisfiable by a broken instrument. (b) Task 2
originally asserted `off_cpu_ns > 0` for a sleeping route — trivially true and uninformative; it
now asserts the sleeping route's off-CPU is within a tolerance of the known sleep AND that a
CPU-bound route's off-CPU is a small fraction of its wall, which together are falsifiable in both
directions. (c) A clamping counter was added: the first draft clamped `non_lock_off_cpu_ns` at zero
silently, which would have hidden clock-skew defects exactly the way `06-13`'s guard hid a
truncation defect.
