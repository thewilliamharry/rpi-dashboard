<objective>
Teach the acceptance harness to collect the lock-profile snapshot pair around its own load window,
derive the four quantities `06-VERIFICATION.md` Truth 5 asks for, and reach an explicit
**CONFIRMED / REFUTED / INCONCLUSIVE** verdict against the falsifiable predictions the verification
report stated.

The verdict logic is the point of this plan. `D-DEBT-06-09` records that two consecutive rounds
proposed a mechanism and were partly wrong, and the orchestrator's scope for round 4 states the
requirement plainly: the round must be able to refute the attribution. A verdict function whose
REFUTED branch is unreachable — or reachable but never exercised — is a confirmation exercise
wearing a diagnostic's clothes. So the REFUTED branch is built first, from a synthetic snapshot
pair representing the world in which the attribution is wrong, and the test that drives it is
mutation-verified like every other guard this round adds.

**This plan changes no budget, no assertion, and no default.** `PROH-OPS-07-01` names
`ROUTE_BUDGETS_MS`, `assert_response_times`, `assert_resource_budget`, `assert_cadence` and the
`--concurrency`/`--duration` defaults; none is touched. `PROH-OPS-07-12` (minted in `06-15`) is
enforced by an explicit test: the lock-profile block contributes to no verdict.

Purpose: without this plan the instrument built in `06-15` and `06-16` can only be read by hand
over HTTP, at some moment unrelated to the load window, by an operator with no Pi-side tooling.
With it, one command produces one JSON file containing both the latencies and the measurement that
explains them.

Output: an acceptance report carrying a `lock_profile` block, a verdict function proven to fire in
both directions, and a completed laptop rehearsal of the exact path the Pi operator will run.
</objective>

<plan_review_against_d_debt_06_10>

`D-DEBT-06-10`'s requirement, applied to this plan.

**Clauses that genuinely mandate a mechanism, with reasons and falsifiers:**

1. **"Snapshot immediately before the first load thread starts and immediately after the last one
   joins."** *Why:* the outcome — "figures that describe the measured window" — is not achievable by
   any placement; a snapshot taken at CLI start would include the port-discovery request and the
   resource-target resolution, and one taken after the database oracle read would include it too.
   The boundary is load-bearing, so it is specified. *What would make it wrong:* if a future change
   moved real load outside those boundaries, the snapshot would under-cover the window. The guard is
   an outcome assertion — the reported `window_ns` must be within a small tolerance of the
   scenario's `duration_seconds` — which fails if the boundaries drift, without pinning the
   implementation's shape.

2. **"Derive percentiles from cumulative histogram bucket differences rather than storing samples."**
   *Why:* the outcome is windowed percentiles without a reset endpoint; two cumulative snapshots
   subtract cleanly, whereas a sample list cannot be differenced. `06-15` chose fixed edges for the
   same reason. *What would make it wrong:* a percentile read off a histogram is bounded by its
   bucket, not exact. This is handled as an outcome, not hidden: `percentile_from_histogram` returns
   the bucket's lower and upper edge, and every reported percentile carries its bound, so a reader
   never mistakes a bucketed estimate for an exact figure.

3. **"The verdict thresholds are declared as data in `LOCK_ATTRIBUTION_PREDICTIONS`, not inlined."**
   *Why:* `06-VERIFICATION.md` stated specific falsifiable predictions; a reader must be able to see
   exactly which numbers the verdict turned on, and `T-06-27`'s principle (thresholds must not be
   quietly tunable to reach a desired answer) applies to a diagnostic as much as to an oracle.
   *What would make it wrong:* nothing, provided the values are the verification report's own and
   the SUMMARY records any deviation. The guard is that the test asserts the constants match the
   report's stated predictions.

**The clause this plan most needed to get right, and how it is phrased.** The temptation was:
"the harness must confirm that `/api/scan-status`'s wait is lock wait." That is a mechanism clause
of the exact defective kind `D-DEBT-06-10` was filed over — it names the answer. It is instead
phrased as an outcome with three exhaustive branches: given the measured wait, hold and off-CPU
figures, the harness reports CONFIRMED, REFUTED or INCONCLUSIVE, and each branch is exercised by a
test built from a synthetic snapshot pair representing that world. The plan does not say which
branch the hardware run will take.

**Guards assert consequence, not shape.** The collection test does not assert that a `lock_profile`
key exists; it asserts that the derived utilisation of a synthetic snapshot pair with a known held
fraction equals that fraction, and that a run with a failing collection produces a byte-identical
verdict to one without collection. The verdict tests assert the verdict *value* under each world.

**Every new test is mutation-verified**, with observed failure values recorded in the SUMMARY.

**What this review changed.** (a) The verdict function originally returned a boolean
`attribution_confirmed`; a boolean cannot express "the measurement did not settle it", so a
run that failed to collect enough acquisitions would have read as a refutation. It now returns a
three-valued verdict with a named reason. (b) The collection failure path originally appended to
`failure_reasons`; that would have made a diagnostic instrument into an oracle, violating
`PROH-OPS-07-12` and `T-06-27`'s principle. It now records `collected: false` with a reason and
leaves the verdict untouched, and a test asserts the equivalence. (c) `percentile_from_histogram`
originally returned a single number; it now returns the bounding edges, because a bucketed estimate
presented as exact is precisely the kind of shape-over-substance the round is guarding against.
