Run the diagnostic on real Raspberry Pi hardware, record what it measured, and put the fix decision
to the user against that measurement rather than against a fourth inference.

This is the plan the whole round was built for, and it is deliberately the only one that touches
hardware. `06-15` built the instrument, `06-16` decomposed what it measures, `06-17` wired it into
the harness and rehearsed the operator's exact command path on a laptop. What remains is to run it
where the failure lives.

**The round must be able to come back with "the attribution was wrong."** `06-17` Task 2 built the
REFUTED branch first and proved it fires on a world constructed from the hardware run's own figures
with the lock component removed. If the hardware says REFUTED, this plan's artifact says REFUTED,
names what it found instead, and the decision checkpoint routes accordingly. `D-DEBT-06-09` records
that two consecutive rounds proposed a mechanism and were partly wrong; a third round that can only
confirm would be the same failure with better instrumentation.

**No fix is implemented here.** Narrowing `_db_lock`'s scope is the obvious candidate and it is a
one-way door: `06-CONTEXT.md` D-01 fences it, `PROH-OPS-04-02` forbids it this phase,
`PROH-OPS-04-05` names the audit any change to the concurrency model requires, and
`06-SECURITY.md`'s `T-06-24` closure evidence rests on the lock's current shape. Task 3 puts that
door to the user as a blocking decision with the measurements in hand. The planner's recommendation
is recorded in that checkpoint; the choice is not the planner's to make.

Purpose: `06-VERIFICATION.md` Truth 5's fifth `missing:` item states that a hardware acceptance
re-run happens only AFTER a fix chosen against these measurements — so it is almost certainly not
this round. This plan produces the evidence that fix decision is made from.

<plan_review_against_d_debt_06_10>

`D-DEBT-06-10`'s requirement, applied to this plan — and this is the plan where it bites hardest,
because a documentation plan can state a conclusion without measuring one.

**Clauses that genuinely mandate a mechanism, with reasons and falsifiers:**

1. **"Run a concurrency-1 control pass as well as the concurrency-8 pass."** *Why:* the outcome
   asked for — the GIL's contribution measured independently — is not extractable from a single
   run. `other_off_cpu_ns` contains genuine I/O wait, and only the excess over the same route's
   uncontended value is contention. One run yields one number and no way to split it. *What would
   make it wrong:* if the two passes ran against different builds, or against materially different
   stored data volumes, the excess would be an artifact. The acceptance criteria therefore require
   both passes to be taken against one build in one session, with the git SHA recorded from the Pi
   and the stored `service_checks` row count recorded at both ends.

2. **"Record `D-DEBT-06-01`'s second reopening test as non-diagnostic rather than running it."**
   *Why:* this is an instruction from the gap contract itself, and it is a mechanism clause
   (naming what not to do) because the failure mode is specific: the test uses an unlocked,
   GIL-bound 82ms route as the discriminator for a lock, so it cannot fire while any GIL cost
   exists. *What would make it wrong:* nothing, unless the hardware measurement shows
   `/api/advanced/current`'s off-CPU excess to be negligible — in which case the route would after
   all be a usable discriminator and the artifact must say so. That contingency is written into
   Task 2's acceptance criteria rather than assumed away.

**The clause this plan most needed to get right.** The temptation was: "record that the `_db_lock`
attribution is confirmed by the measurement." That names the answer before measuring — the exact
defect `D-DEBT-06-10` was filed over, in its purest form. Every clause below is instead phrased as
"record what the measurement says, whichever way it falls", and the acceptance criteria are
symmetric: the artifact is required to state the verdict and the figures behind it, and is required
to be equally complete under REFUTED as under CONFIRMED. Task 2's criteria include an explicit item
for the REFUTED path — what the artifact must contain if the attribution fails — so that path is
not an afterthought discovered at write-up time.

**Guards assert consequence, not shape.** The hardware checkpoint's acceptance criteria are not
"the operator ran the command" but specific field values in the returned JSON: `collected: true`,
a `window_ns` matching the scenario, a non-zero acquisition count on the lock-taking routes, a
`primed_pid_count` consistent with `06-11`'s CPU fix, and an instrumented control-pass
`/api/services` p50 within a stated band of round 3's uninstrumented 209.355ms — the in-situ
overhead check `T-06-81` promised.

**Every claim in the artifact is traceable to a field in an attached JSON report.** Task 2's
criteria require it, because a narrative that cannot be re-derived from the evidence is how
`06-ACCEPTANCE-ROUND3.md` came to state the GIL reading that `D-DEBT-06-09` later had to withdraw.

**What this review changed.** (a) The first draft had one hardware pass; the GIL separation is not
derivable from one, so the control pass became mandatory and its purpose is stated. (b) The first
draft's artifact section listed "the verdict" without saying what the artifact must contain if the
verdict is REFUTED; that asymmetry is removed. (c) The first draft's decision checkpoint offered
"narrow the lock now" and "defer to round 5"; a third option — "the measurement refuted the
attribution, so round 5 investigates what it found instead" — was missing and would have forced a
refuting measurement into a fix-shaped decision.

    An `ENABLE_LOCK_PROFILE`-gated instrument that measures, per route and per request, the time
    spent waiting for `_db_lock` versus holding it; decomposes each held critical section into
    connection setup, SQLite and pure Python; and decomposes each request's wall time into on-CPU,
    lock-wait and other-off-CPU. The acceptance harness collects a snapshot pair around exactly its
    own load window and embeds the derived figures — plus a CONFIRMED / REFUTED / INCONCLUSIVE
    verdict — in its JSON report. The whole path has been rehearsed end to end on a developer
    machine (`06-17` Task 3); nothing below is being attempted for the first time.

    The instrument is off by default, performs zero timing work when off, and its endpoint returns
    404 when off. `_db_lock`'s scope is unchanged: all 28 `with _db_lock` call sites are pinned by
    a test.

        cd ~/projects/rpi-dashboard
        git pull
        git log --oneline -1
        BEACON_LOCK_PROFILE=1 docker compose up -d --build

    run a 600-second pass against a deployment whose endpoint is 404.

    (If `sqlite3` is not installed on the host, the same two counts can be read with
    `docker exec beacon-web python -c` against `/data/dashboard.db`.)

    **4. The concurrency-1 control pass — the baseline the GIL separation depends on.**

        sudo dashboard/.venv/bin/python tests/pi_load_acceptance.py \
            --base-url http://127.0.0.1 \
            --db /var/lib/docker/volumes/rpi-dashboard_dashboard-data/_data/dashboard.db \
            --concurrency 1 --duration 120 --lock-profile \
            --output ~/beacon-lockdiag-c1.json

    Takes about two minutes. This mirrors round 3's control pass exactly (concurrency 1, 120s) so
    its latencies are directly comparable, and it supplies each route's uncontended off-CPU value —
    without it, contention cannot be separated from ordinary I/O wait.

    **5. The concurrency-8 / 600s pass — the failing scenario, measured.**

        sudo dashboard/.venv/bin/python tests/pi_load_acceptance.py \

            --output ~/beacon-lockdiag-c8.json

    (`PROH-OPS-07-10`). This run is expected to report `overall_passed: false` — that is not a
    problem to solve here; it is the condition being measured. Leave the Pi otherwise idle.

    **6. Re-record the stored-data shape** with the same query as step 3, so any growth during the
    twelve-minute window is known rather than assumed.

    **7. Restore the uninstrumented deployment.**

        docker compose up -d --build
        curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/api/diagnostics/lock-profile
