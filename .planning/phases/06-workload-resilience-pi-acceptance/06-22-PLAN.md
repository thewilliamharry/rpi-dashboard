<objective>
Close the half `_db_lock` cannot reach — and let the user open the one-way door, or decline it.

`06-LOCK-DIAGNOSTIC.md` §3 measured `/api/advanced/current` at p95 2217.6ms against a 2000ms budget
with **exactly 0.0ms lock wait across 880 requests**. Its cost is `cpu = 536,241.0ms` plus
`other_off_cpu = 550,980.5ms` — mean 609.4ms on-CPU and 626.1ms off-CPU per request — on a four-core
Pi running `--workers 1 --threads 8`. `D-DEBT-06-15` records plainly that narrowing `_db_lock`
cannot touch it. `06-21` has now re-measured it after the narrowing, and that measurement is what
this decision is made against.

**The machine is not CPU-saturated.** Round 4's total measured request CPU across every route is
roughly 942 seconds inside a 600-second window — about 1.57 of four cores, matching the web role's
165.504% `mean_cpu_percent`. Roughly 2.4 cores sit idle while a route misses its budget. That is the
signature of a single interpreter's bytecode being the binding constraint, and it is why more
processes would genuinely help — and equally why less work per request would.

**Which of those to do is a one-way door and is not the planner's call.** Raising `--workers` above
1 grants a second OS process unserialized concurrent write access to the same SQLite file with no
line of `_db_lock` changing. `PROH-OPS-04-05` fences it, `test_the_deployment_pins_its_gunicorn_concurrency_model`
pins it, and `06-SECURITY.md`'s `T-06-24` is closed on that boundary. Task 1 puts it to the user with
`06-21`'s figures in hand and a recorded planner recommendation. All four options are fully specified
so any of them can ship from this plan.

**Whatever ships, the payload does not move.** `PROH-OPS-07-14`, minted here: `/api/advanced/current`'s
response must be byte-identical for the same input, for the same reason `PROH-OPS-07-05` binds
`/api/services`. `D-DEBT-06-10`'s regression was a scope change that silently altered a number
operators trust.

<plan_review>

**Clauses in this plan that mandate a MECHANISM, why, and what makes each wrong:**

1. **The cost-reduction branch specifies the request-scoped occurrence memo, not "make the route
   faster".** *Why:* an unbounded instruction to reduce cost invites changes to
   `_offline_intervals_from_points`' interval-merging behaviour, which `06-13-SUMMARY.md` explicitly
   declined as risking the byte-identical output guarantee. Naming the mechanism bounds the blast
   radius to a memo over a function already proven pure at that key granularity. *What would make it
   wrong:* if `_local_occurrence_epochs` is not invariant at the `(window, date, timezone)` key in
   `diagnosis.py`'s call pattern the way it is in `/api/services`'. The payload-equivalence guard is
   the falsifier and it runs on both branches.

2. **The cost-reduction branch's guard is a call count, not a duration.** *Why:* `06-13`'s own guard
   asserted an achieved absolute cost reduction, and `D-DEBT-06-01` records as an honest limit that
   the growth-ratio classification it wanted was never reached. A call count is exact, is not
   load-sensitive, and does not decay as the machine or dataset changes — which is precisely
   `D-DEBT-06-14`'s lesson and `D-DEBT-06-13`'s (an assertion over a quantity too small to be stable
   under suite load is a gate that cries wolf). *What would make it wrong:* a memo that reduces call
   count while returning a wrong value. The payload-equivalence guard covers exactly that, and the
   two together are what a call count alone is not.

3. **The worker-count branch requires `mem_limit` re-derived from measured RSS.** *Why:*
   `PROH-OPS-04-05` states it, and `D-DEBT-06-07` records that a single worker measured 124.9MB peak
   RSS against a declared 256m. *What would make it wrong:* treating the declared limit as a
   protection. `D-DEBT-06-07` records this Pi's kernel does not enforce `mem_limit` at all — the
   arithmetic still matters because `assert_resource_budget` checks it, but there is no kernel
   backstop, and the branch must record that rather than implying one.

**Every threshold on every branch is relational, a count, or an equality — none is an absolute
millisecond value.** The call-count guard is exact. The payload guard is equality. The worker-count
branch's memory arithmetic is a measured-RSS derivation recorded in prose, not a test threshold.

**Guards assert consequences.** The payload guard asserts the bytes an operator's browser receives.
The call-count guard asserts how many times a walk actually ran, mutation-verified by removing the
`cache=` argument — the `acquisitions 1 != 2400` shape this phase established. Neither asserts that
a parameter exists or that a call returned `200`.

**Timing comparisons.** This plan gates on no timing comparison. If the implementer adds one for the
SUMMARY's benefit, it must compare minima over at least five alternating-order repetitions per arm
and must be labelled developer-machine evidence (`PROH-OPS-07-09`); it may not become an acceptance
criterion, because `D-DEBT-06-13` records this suite is already load-sensitive.

</plan_review>
