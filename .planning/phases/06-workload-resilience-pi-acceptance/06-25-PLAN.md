<objective>
Replace `/api/services`' per-port Python uptime sweep with one bulk all-ports SQL aggregation, and
prove the rendered strip did not move.

This is **option C**, chosen by the operator on `D-DEBT-06-21`'s corrected evidence. It is the
sixth round on OPS-07 and the first that attacks *how much work happens* rather than *where it
happens*.

**Why this target, with its arithmetic.** `06-ACCEPTANCE-C3-RUN2.md` measured `/api/services` at
p95 **679.3ms** against a 500ms budget — 36% over, on the second independent concurrency-3 run,
with run 1's worker-CPU confound resolved and shown not to be the explanation.
`06-PROFILE-2.md` re-attributed the route against the current build: `uptime_sweep` is
**43.727%** of profiled self time, the dominant bucket, and `maintenance_coverage` has already
collapsed to 5.479% because `06-13`'s memo banked it. Removing `uptime_sweep` projects to
somewhere between ~382ms and ~475ms. **Both ends are inside budget; neither may be planned against
as a point estimate** — the profiler states its own bias, and `uptime_sweep` at 1,131,112 calls is
the most Python-heavy bucket in the table, so cProfile inflates it by an amount the instrument
cannot quantify.

**This is not a reuse of `SERVICE_QUERY_SHAPES['raw']`.** `06-PREMISE-C.md` verified the premise
against source and found three mismatches, all of which this plan resolves explicitly rather than
inheriting: the existing shape binds `port=?` where this route needs one bulk read; it aligns
buckets to an absolute epoch multiple where this route anchors at `now - 7d`; and its closing
`WHERE` drops zero-observation buckets where this route renders a fixed 168-value array with a
`-1` sentinel. A new query is written for this route's exact contract.

**What is deliberately NOT in scope.** `maintenance_coverage` — `06-13` already banked it and
re-attacking it would re-fix a solved problem. `row_grouping` (16.083%) — its loop also builds
`points_by_port` for the offline-interval path, so it survives; only the `checks_by_port` half goes
away. `service_rollups` — refuted by `D-DEBT-06-21`, which measured **zero** rollup buckets inside
the uptime window by construction. `_db_lock`'s scope — round 5 narrowed it, measured worse, and was
reverted; nothing here moves across that boundary.

**What this plan does not claim.** It does not claim the route will pass. Whether the SQL path is
genuinely cheaper than the already-linear Python sweep it replaces is an open measurement, taken in
`06-26` on this host and in `06-27` on the Pi. The correctness proof lands here; the cost verdict
does not.

Purpose: close OPS-07's only remaining gap by reducing `/api/services`' per-request cost.
Output: a bulk SQL uptime reader, a route that uses it, a differential oracle, and an unmoved strip.
</objective>

<assumption_delta_decision>

**Signal:** `pluralization` — this plan introduces a second way to produce the 168-bucket
availability strip, where there has been exactly one since the route was written.

**The noun that is now primary:** *the port-scoped 7-day availability strip* — a pair of
(`uptime_pct`, 168 rendered values) derived for a **set** of ports over one window. It was
previously modelled as a per-port computation over a Python list of checks
(`_legacy_uptime_summary(checks, now)`); it is now modelled as a bulk, set-scoped read.

**Decision: `promote`.** The bulk SQL reader becomes the primary — the single production producer
of any strip an operator sees. `_legacy_uptime_summary` is **demoted**, not kept alongside as an
equal: it retains exactly two roles, (a) the differential oracle in
`tests/test_services_route_scaling.py`, and (b) its existing non-route callers
(`_legacy_build_uptime_buckets` / `_legacy_calc_uptime_pct`, reachable only through
`MonitoringOperations`). It is not deleted, because deleting the oracle would delete the only
independent evidence that the new producer is correct.

**Rationale:** add-alongside would leave two live producers of a rendered contract with three
documented semantic mismatches between the idioms they are built from — precisely the seam
`06-PREMISE-C.md` found and precisely the shape that drifts silently. Promotion with a demoted
oracle keeps one truth and one check on it.

**Companion invariant (REQUIRED here, not optional):** `UptimeStripSqlDifferentialTests` asserts
the two producers agree on randomized inputs. It goes red the instant a future change makes either
producer diverge, so a reintroduced singular assumption cannot land silently. This is the mechanism
`PROH-OPS-07-16` names.

</assumption_delta_decision>

  <action>
    Add `UPTIME_STRIP_QUERY` and `read_uptime_strips_by_port(conn, *, ports, now, window_seconds, bucket_count)`
    to `dashboard/beacon/repositories.py`, then call it from `api_services` in `dashboard/app.py` in
    place of the per-service `_uptime_summary(checks, now)` call.

    **Where the work is split, and why.** SQL returns integer second totals only. Python performs
    every division, every `round(..., 3)`, the percentage, and the 99.999 clamp. This is not
    stylistic: SQLite's `ROUND()` rounds half away from zero and CPython's `round()` rounds half to
    even, so moving the division into SQL would change rendered values while every shape-checking
    test stayed green. Reuse the existing arithmetic from `_legacy_uptime_summary` verbatim for the
    Python half — same expressions, same order of operations.

    **The reader's contract.** Takes an iterable of ports and an integer `now`; derives
    `start = int(now) - window_seconds` and `bucket_seconds = window_seconds // bucket_count`;
    asserts `window_seconds % bucket_count == 0` and raises `ValueError` if not, so a future constant
    change fails loudly instead of drifting the strip. Returns a mapping with an entry for **every
    requested port** — including ports with no rows, which map to `(None, [-1] * bucket_count)`.
    This deliberately differs from `read_service_offline_intervals_by_port`'s absent-means-empty
    convention: the strip is a fixed-shape rendered contract, and pushing sentinel construction into
    the route would put the contract in two places. Say so in the docstring.

    **The query's contract, resolving `06-PREMISE-C.md`'s three mismatches explicitly.**

    *Bulk, not per-port.* One statement for all ports, parameterized with
    `','.join('?' * len(ports))` exactly as the route's own `all_checks` read and
    `read_maintenance_windows_by_port` already do. Never string-interpolate a port value. Partition
    every window function and group every aggregate by `port` so N ports cost one statement, not N
    recursive CTEs under `_db_lock` — the shape round 5 measured worse.

    *Origin, not epoch alignment.* Generate buckets from `start` upward in `bucket_seconds`
    increments for exactly `bucket_count` rows. Do not use the `? - (? % ?)` epoch-modulo generator
    from `SERVICE_QUERY_SHAPES['raw']`; it produces different boundaries and a different last-bucket
    width, which is a change to a rendered contract (`PROH-OPS-07-15`). Derive both `start` and
    `bucket_seconds` from `UPTIME_WINDOW_SECONDS` and `UPTIME_BUCKETS` passed in by the caller;
    hardcode neither 604800 nor 3600 in the query or the reader.

    *Every bucket emitted, sentinels reconstructed.* The result must carry a row for every one of
    the `bucket_count` buckets for every requested port, whether or not any segment overlaps it.
    Build the strip as a left join from the generated bucket series onto the per-bucket sums, and do
    not filter the joined result on the sums being positive — `SERVICE_QUERY_SHAPES['raw']` does
    exactly that filtering and it is why that shape cannot serve this contract. A bucket whose
    online+offline seconds total zero becomes `-1` in Python.

    **The semantics that must match `_legacy_uptime_summary` exactly.** Read each off the source; the
    differential test in Task 2 is what proves you got them right.
    - In-window admission is `ts >= start AND ts <= now` — inclusive at both ends. The existing SQL
      shape uses an exclusive upper bound; that is a divergence.
    - The boundary sample is the latest row with `ts < start`, tie-broken by the higher `online`
      value, matching Python's `sorted((ts, state))` where the last of a tie group wins.
    - Segment ordering inside the window is by `(ts, online)`, not by `ts` alone, for the same
      tie-break reason. A `LEAD` window ordered on `ts` alone leaves duplicate-timestamp order
      unspecified and can carry the wrong state forward.
    - A segment starts at `MAX(ts, start)` and ends at `MIN(next_ts, now)`, with the final segment
      ending at `now`.
    - Per-bucket overlap is `MAX(0, MIN(segment_end, bucket_start + bucket_seconds, now) - MAX(segment_start, bucket_start, start))`,
      summed separately for online and offline segments. There is no unknown state: `observed` is
