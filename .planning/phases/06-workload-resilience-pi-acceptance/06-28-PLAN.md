currently closed partly on evidence that the revert removed. It cites
`LockScopePreservationTests::test_api_services_lock_scope_is_database_reads_only` — the narrowed-shape
pin — and `NarrowedShapeConcurrentAccessTests`. Those two are in different positions and the row
treats them alike, which is itself part of the problem:

  `tests/test_lock_profile.py` now carries the pre-narrowing containment pin restored verbatim from
  `1a4db68^`. The name survives only inside comments at `tests/test_lock_profile.py:643` and

Either way a high-severity threat is recorded closed on evidence that does not describe the tree.
That is a register describing a build that no longer exists, and it is exactly the defect class this
project keeps finding: a guard, or a claim, asserting something it cannot detect.

**And `T-06-101` (high) carries the identical defect.** `06-SECURITY.md:69` closes it on
`HeldRegionCompositionTests::test_services_held_region_is_sql_dominated_after_narrowing` — a measured
composition guard on the reverted narrowing — and on the same removed narrowed-shape pin. Task 1's
generic sweep would reach it, but a threat this specific is named rather than left to a sweep.

`api_services`' existing `with _db_lock` block, removed a Python computation from it, rewrote the
scope pin's `required_calls`, and realigned all 28 rows of `06-LOCK-AUDIT.md`. None of that widens a
concurrency boundary — but "none of that widens it" is a claim to be re-checked against HEAD, not
assumed. `PROH-OPS-04-05`'s prerequisite 4 exists for precisely this re-check.

**What this plan does not do.** It does not promote OPS-07 (`PROH-OPS-07-08`). It does not decide
option A. It does not change a worker count, a budget, or `_db_lock`'s scope. And it does not mark
`PROH-OPS-04-05` discharged: only the parts this round's changes touch are re-closed, and whatever
remains outstanding is named as outstanding.
