<objective>
One configuration value, end to end, on the route that actually costs something.

Phase 7 exists because the operator runs Beacon on a server that already has monitoring and alerting.
They want the services front page they like, and they want advanced diagnostics gone — hidden, and
not running any extras. The prior investigation established that there are no background extras to
stop: `get_current_diagnosis` is read-time only, and none of `J1`..`J9` in
`dashboard/beacon/worker_main.py` feeds it. So "off" is route gating plus removing the entry point.
No schema change. No worker change. No migration.

This plan is the tracer: it wires the toggle through **every layer the phase touches** — environment,
`Settings`, the application module, one route handler, the deployment file, the operator
documentation, and a real measurement — on the single most important route,
`/api/advanced/current`. Plan `07-02` expands the same shape to the remaining three routes and to the
front page's entry point; plan `07-03` closes the cost, reversibility and OPS-07 guardrail records.

`/api/advanced/current` is the right tracer target for two reasons. It is the only one of the four
routes that touches the database, so it is the only one where "performs none of the work" is a
measurable claim rather than a truism. And it is the route Phase 6 measured at 584s CPU and
1,090,992ms off-CPU across 750 requests in round 5b — the one whose absence would make a Pi
acceptance run dramatically easier, which is exactly why `07-03` mints a prohibition against ever
running acceptance with it off.

**Purpose:** establish the toggle, its default, and the measurement instrument, so every later claim
in this phase is measured rather than asserted.
**Output:** `Settings.enable_advanced_diagnostics`; a gated `api_advanced_current`; the deployment
and documentation entries; a pre-change response golden; and a connection/statement counting harness
the rest of the phase reuses.

This plan's decisions, referenced by later plans and consolidated by `07-03` into `07-DECISIONS.md`:

- **D-07-01** — The toggle defaults to **enabled**. Existing deployments have this page today, and a
  silent feature removal on upgrade is worse than the cost it saves.
- **D-07-02** — Gating is a handler-level `404` on the first line of each handler, mirroring
  `prometheus_metrics` (`dashboard/app.py:3310`) and `lock_profile_snapshot` (`:3330`) exactly.
  *Rejected: conditional route registration.* It would leave three optional-surface gates in one file
  wearing two different shapes, for no behavioural gain — the criterion asks for 404, and an early
  return produces 404 having done nothing. The rejection is recorded because the alternative is
  genuinely defensible and a later reader should not have to rediscover the argument.
- **D-07-03** — The enabled path is left textually alone wherever possible, so byte-identity is a
  property of the code shape and not only of a test.
</objective>

<plan_review>
**What this plan asserts, and how.** Every guard here is an observable consequence of serving a real
HTTP request through the real application: a response's bytes, a response's status, or a count of
statements SQLite actually executed. None of them reads source, checks that a route is registered,
or asserts that a configuration field exists.

**Where a mechanism is named rather than an outcome, and why.** Two places.

1. D-07-02 names the gating mechanism (a handler-level early return) rather than only the outcome
   (404). The outcome alone would permit conditional route registration, which is a defensible
   design; the mechanism is fixed for consistency with the two gates already in the file, and the
   rejection is recorded in the objective so the choice is arguable rather than assumed. What would
   make it wrong: if a future reader finds that a registered-but-404ing route leaks the surface's
   existence in a way that matters — for instance through an `OPTIONS` response or a route
   introspection endpoint — the mechanism, not the criterion, is what must change.
2. Task 3 names `connect_db` as the seam the counter wraps. This is a mechanism claim and it can be
   wrong in one specific way: if any database access in the request path does not go through
   `connect_db`, the counter under-reports and would read zero for work that happened. The task
   requires the executor to confirm both import bindings resolve to the patch, and the second
   sensitivity check — a non-zero count on `/api/stats` — is there to catch exactly this failure. It
   is not a formality; it is the reason the instrument can be believed.

**What is deliberately weaker than it looks, stated openly.** The disabled `GET /` zero-work
assertion in Task 3 is close to vacuous against today's code, because `/` performs no diagnosis work
even with advanced diagnostics fully enabled. Asserting it and presenting it as evidence for
criterion 3 would be the defect class Phase 6 found six times. It is included as a *standing*
guard — it acquires teeth the moment `07-02` gives `/` a conditional branch, and it is the reason
`07-02` cannot deliver the flag to the front page through a database read — and the docstring says
so. The measurement with independent force is the zero-versus-observed contrast on
`/api/advanced/current`, plus `07-03`'s front-page cost equality.

**The harness hazard this module is built around.** `tests/helpers.py`'s `load_app` writes
`extra_env` into `os.environ` and never removes it, and only rewrites its own six baseline keys per
call. Everything after that — `importlib.reload`, a fresh `SETTINGS` — is downstream of a polluted
environment. The consequence is specific and severe: an enabled-side application built without an
explicit value, after any disabled build in the same process, is itself disabled. Most of this
phase's enabled guards would fail noisily in that state, which is survivable. One would not:
`07-03`'s front-page cost equality would compare two disabled applications, find them equal, and
report criterion 3 satisfied while measuring nothing. So the fix is not local to the test that would
be fooled — it is a module rule stated here, in the task that creates the module, and repeated at
every enabled call site in all three plans. The `load_settings({})` test in Task 2 is the sole
evidence for the unset default precisely because it never touches `load_app`.

**No absolute thresholds.** The only literal any count is compared against is zero, which is not a
machine or dataset property. The enabled side is asserted only as "greater than zero" and its
observed value is recorded as evidence rather than pinned as a contract.

**No timing comparisons in this plan**, so the minima-with-alternating-order rule does not bind here.
If a later round wants to claim the disabled configuration is *faster*, that claim needs the
alternating-order minima discipline and it is not made anywhere in this phase.

**Reversibility.** Nothing in this plan is one-way. A dataclass field with a default, one early
return, one environment line, one README row and one test module. No migration, no schema change, no
write to the database, no destructive step. `REVERSIBILITY_GATES` is enabled and no
`checkpoint:decision` is warranted; `07-03` records the reversibility proof as a measurement rather
than an assertion.
</plan_review>
