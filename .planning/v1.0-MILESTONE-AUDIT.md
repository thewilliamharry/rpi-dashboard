## The two real gates

### 1. Phase 7 was never verified (DIA-09)

Phase 7 is the only phase with no VERIFICATION.md. The implementation is present and I confirmed
it directly: `ENABLE_ADVANCED_DIAGNOSTICS` at `dashboard/app.py:105`, all four routes gated
(`:2544`, `:2557`, `:2570`, `:2581`), and the front-page entry point excised server-side at
`:2535`. Its tests pass inside the green suite.

So DIA-09 is not unsatisfied on the evidence — it is **unverified by the gate this project's own
convention requires**, exactly as ROADMAP.md anticipated when it wrote that promotion "belongs to
an independent verification round". Closing it needs a verification round, not new code.

### 2. Phase 6's verification describes a tree that no longer exists

`06-VERIFICATION.md` is dated 2026-09-02 and reads `gaps_found`. Phase 6 then ran through 06-28 on
2026-09-06. **Both defects it records as open are now closed**, and I verified both against
current HEAD rather than trusting the summaries:

- **The uptime regression is fixed.** 06-13 had extended the 20,000-row
  `_OFFLINE_INTERVALS_BULK_ROW_LIMIT` onto the uptime path, silently reporting a service with
  20.833% true uptime as 100.0%. The query at `dashboard/app.py:2928` now carries **no LIMIT
  clause**, under a 26-line comment marking it deliberately unbounded and naming why its two
  consumers cannot share one bound. Shipped in `bcad398`, recorded closed in D-DEBT-06-10.
- **The missing test now exists.** `tests/test_services_route_scaling.py:439` —
  `test_uptime_pct_is_not_affected_by_the_offline_interval_row_cap` — asserts the *output*, not
  merely that a LIMIT clause is present, which is precisely how the defect shipped green the first
  time.

Re-running `/gsd-verify-work 6` should move Phase 6 off `gaps_found`. Until it runs, the milestone
carries a phase verification that is simply out of date.

Verified wired: telemetry API → history UI (HIS-01…06, DIA-04…07); advanced workspace → Phase 7
gating (DIA-09); maintenance attribution → history and uptime (MNT-01…04); Phase 1 foundations →
all consumers; and the Phase 6 row-cap seam, now confirmed safe for `uptime_pct`.

**One warning, unchanged since 2026-08-24.** `dashboard/beacon/diagnosis.py:448` hardcodes
`resolution_policy` as `{60, 300, 3600}` against `telemetry.py:11`'s ten-step
`RESOLUTION_LADDER_SECONDS`. It is a parallel source of truth that can drift silently. It does not
break TEL-06: the requirement's "displayed resolution" clause is carried by a different and

`effective_resolution_seconds`, which `advanced.js` consumes at five sites. The hardcoded field
has **zero production consumers**; only tests and response goldens read it. Cleanup is low
priority and golden-affecting.

All four E2E flows complete: current host diagnosis; service history with maintenance
attribution; dashboard service list with uptime and maintenance; worker-health banner in both
themes.
